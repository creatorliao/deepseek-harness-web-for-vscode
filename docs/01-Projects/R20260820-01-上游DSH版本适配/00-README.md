# R20260820-01 · 上游 DSH 版本适配

**起始**: 2026-08-20 ｜ **状态**: 持续维护（上游一发新版就会追加文件）｜ **属性**: 历史记录 + 现场记录

## 本夹是什么

**本项目最重要的一类工作**：上游 `@deepseek-ai/dsh` 每次破坏性变更后，扩展怎么跟上。

dsh 迭代极快（rc.6 → rc.8 → 0.1.1-rc.2 → 0.1.2-rc.1 → 0.1.5-rc.2 在约一个月内走完），且**三次破坏的用户可见报错高度相似（都表现为 "Failed to load plugins"），但根因完全不同**。本夹把这些事件的完整证据链留在一起，避免下次误判。

> **换内核版本的实操 SOP（含命令、回滚、事故教训）**：见 [02-Areas/20260915-01-内核升级最佳实践.md](../../02-Areas/20260915-01-内核升级最佳实践.md)。

## 沉淀出的教训（下次务必先看）

1. **不要用"报错文案"判断根因**——三次都是 "Failed to load plugins"，根因分别是 preload 标签未绝对化 / BOOT 正则失配 / dist 布局与认证全换。
2. **不要用 CLI 版本号当权威**——CLI 版本与传递依赖版本可能错配（rc.7 CLI + rc.8 web-app），`--no-open` 的门控因此改为 `dsh web --help` 现场探测 + 版本判断兜底。
3. **每次上游升级都要同时核四个面**：boot 注入形态、dist 资产路径、`/api` 认证与 RPC 协议、CLI flags。规范见 Areas。
4. **不要用"CLI 是否响应"判断内核是否可用**——`dsh --version` / `dsh web --help` 都不加载插件树，全局树被装坏（如 koffi 原生与 JS 包装错配）时它们照样正常，只有真正起服务才炸。见 [12](12-修复_全局dsh半装koffi错配导致启动即退码1.md)。
5. **`npm i -g` 的成功/失败要看退出码，不要看"版本号变了"**——Windows 上被运行中实例锁住原生二进制时，npm 会写出新的 `package.json` 却以 `EBUSY` 失败退出，留下**半新半旧**的树。装完必须自检原生/JS 版本一致性。
