# 修复 — 主题同步静默失效：扩展用 pre-0.1.2 的 RPC 面写设置（`settings.update` 401）

**日期**: 2026-09-18
**扩展版本**: 影响 v0.3.4 → v0.5.3（自 dsh 0.1.2-rc.1 适配起一直存在）；修复 v0.6.0
**dsh 版本**: 适配 `0.1.5-rc.2` 与 `0.1.6-alpha.2`（两版本实测形态一致）
**影响面**: 扩展把 VS Code 深浅色写进 DSH 设置的通道（`deepseekHarness.themeSync`）**从未真正落盘**；无报错、无可见症状
**范围**: `src/serverManager.ts`（新增 `updateSettings`）、`src/themeSync.ts`（改走 manager）、`src/extension.ts`（传 manager）、`test/serverManager.test.js`（新增回归断言）
**根因归属**: 本项目代码（未跟上上游 0.1.2-rc.1 的 RPC 改造）
**关联**: [../../03-Resources/20260918-01-官方DSH发布说明_0.1.5-rc.2到0.1.6-alpha.2.md](../../03-Resources/20260918-01-官方DSH发布说明_0.1.5-rc.2到0.1.6-alpha.2.md) ｜ [../R20260918-04-上游0.1.6-alpha差距与升级/03-分析_0.1.5-rc.2到0.1.6-alpha.2差距.md](../R20260918-04-上游0.1.6-alpha差距与升级/03-分析_0.1.5-rc.2到0.1.6-alpha.2差距.md)

## 现象

**没有任何用户可见症状。** 这正是它藏了 5 个版本的原因：

- 内嵌面板的主题**看起来一直是对的**——因为 `media/bridge-client.js` 注入了 `matchMedia` shim，让 DSH 前端的 "system" 解析无条件跟随 VS Code 主题，**与扩展写没写设置无关**；
- 失败被 `try/catch` 吞掉，只打一行 `console.log("[dsh] theme sync failed: …")` 到扩展宿主日志；
- 真正发生的事：**`$DSH_HOME/settings.yaml` 里从来没有扩展写进去的 `ui-theme.preference`**。

发现路径：2026-09-18 拉取上游扩展仓（原作者 Liming Xie 的 `floatinghotpot/deepseek-harness-web-for-vscode`）的 `v0.3.5` 构建时，看到其修复记录 `fix/20260915-vscode-settings-loopback` 提到同一条。**本项目随即用探针独立复现**（见「验证」），确认不是"上游专属"问题，而是我们同样中招。

## 根因

### A. 扩展发的是已被移除的点号方法，且不带会话 Cookie

修复前 `src/themeSync.ts:22-31`：

```ts
await fetch(base + "/api/settings.update", {
  method: "POST",
  headers: { "content-type": "application/json" },   // ← 没有 cookie
  body: JSON.stringify({
    type: "client-request",
    method: "settings.update",                        // ← 点号方法
    payload: { ns: SETTINGS_NS, patch: { preference } }, // ← 平铺，不套 args
  }),
});
```

dsh `0.1.2-rc.1` 起 RPC 面整体改过：`POST /api/<namespace>/<method>`、参数包在 `payload.args` 里、且 `/api` 全部要求 **authority 绑定签名 Cookie**。**这件事本项目自己是知道的**——`src/serverManager.ts:90-92` 的 `MIN_DSH_VERSION = "0.1.2-rc.1"` 注释、以及 `:713-720` 的 `api()` 文档注释都写着同一结论。0.3.4 那次适配也确实改对了 `workspace/*`、`session/*` 那几条。

**漏掉 `themeSync` 的原因**：它是全项目**唯一一处绕过 `api()`、自己裸 `fetch` 打 `/api`** 的调用点。`api()` 同时持有「正确的信封」与「会话 Cookie」两样东西，绕过它就没有任何统一入口把这类调用兜住——既没有类型约束，也没有单测覆盖（`themeSync.ts` 至今无单测）。

### B. 三个"看起来正常"叠在一起，把失效藏住了

| # | 掩盖物 | 证据 |
|---|---|---|
| 1 | 失败被吞 | `src/themeSync.ts` 的 `catch` 只 `console.log`，不抛不报 |
| 2 | 视觉结果由 shim 保证 | `media/bridge-client.js` 的 `matchMedia` shim；`src/documentAssembly.ts:236` 注入 `bridge.dark`；`src/dshPanel.ts:47-53` 推 `theme-preference` |
| 3 | 设置页自身可用 | `media/bridge-client.js:136` 的 `__DSH_TRANSPORT__.ownsHost = true` 让页面按 loopback 处理、设置持久化走 host 模式——**用户在设置页里手动改的偏好确实会落盘**，只有扩展代写的那一条没落 |

## 修复

| # | 文件 | 改动 |
|---|---|---|
| 1 | `src/serverManager.ts` | 新增 public `updateSettings(ns, patch)` → `this.api("settings/update", { ns, patch })`，复用 `api()` 的 Typert 信封与 `authCookie` |
| 2 | `src/themeSync.ts` | 签名由 `getServerBase: () => string \| undefined` 改为 `manager: DshServerManager`；写入改调 `manager.updateSettings(SETTINGS_NS, { preference })`；开关与失败日志保持不变 |
| 3 | `src/extension.ts` | `registerThemeSync(context, manager)`（原为 `() => manager?.serverUrl`） |
| 4 | `test/serverManager.test.js` | 新增断言：`method === "settings/update"`、`payload.args === {ns, patch}`、**Cookie 必须随行** |

**决策理由**：

- **不复制上游的字节补丁路线**。上游姊妹项目 `remote-dsh` 走的是"把转发 JS 里的 `isLoopbackHostname(...)` 替换成 `true`"，代价是 gzip 编码感知与缓存头改写；本项目的 loopback 问题早已用 `__DSH_TRANSPORT__` 接缝解决（见 [../R20260817-01-桥架构与IDE内嵌/14-修复_面板内图片不显示与内测声明反复出现.md](../R20260817-01-桥架构与IDE内嵌/14-修复_面板内图片不显示与内测声明反复出现.md)），本次只处理 RPC 面，**不引入第二套机制**。
- **收敛到既有入口**。修复后全项目**再无裸 `fetch` 打 `/api` 的调用点**，与 `AGENTS.md §7`「所有"打开界面"的路径必须收敛到 `openUi()` 这一个路由点」是同一条纪律。
- **顺带纠正一处文档**：`README.md` 的兼容矩阵把"扩展代写 DSH 设置"当作可用能力来描述，修复前它其实没生效。
