# 分析 — `0.1.6-alpha.2` → `0.2.0-rc.1` 的差距清单（含整个被跳过的 `0.1.7` 系列）

**日期**: 2026-09-29
**定位**: 版本间**差异清单**与影响判定。回答"上游到底改了什么、哪些对我们承重"
**证据底本**: [../../03-Resources/20260929-01-官方DSH发布说明_0.1.6-alpha.2到0.2.0-rc.1.md](../../03-Resources/20260929-01-官方DSH发布说明_0.1.6-alpha.2到0.2.0-rc.1.md)（5 个发布的**中文段逐字留档**，脚本机械抓取）
**触发事件**: 现场把内核升到 `0.2.0-rc.1` 后面板全挂 → [14-修复_dsh0.2.0插件URL改相对形态.md](14-修复_dsh0.2.0插件URL改相对形态.md)
**采集命令**: `GET https://api.github.com/repos/deepseek-ai/deepseek-harness/releases/tags/<tag>`（官方**没有 `CHANGELOG.md`**，Releases 即 changelog）

## 0. 结论先行

1. **这次破坏不在官方发布说明里。** `0.2.0-rc.1` 的三段说明（体验优化 10 条 / 问题修复 7 条 / 其他变更 2 条）**一个字都没提**插件地址或 HTML 形态；把它逐条读完也预测不到 `Failed to load plugins`。
2. **版本号"大跳"的主角其实是 `0.1.7` 系列。** 成批的破坏性调整（设置存储换代、会话日志 V4、Agent 预设改插件包、`readBytes`、Messages API only…）首次出现在 `dsh-v0.1.7-alpha.1`，并在 `dsh-v0.1.7-rc.1` 的汇总节里重述。我们的适配基线停在 **`0.1.6-alpha.2`**，等于**整段跳过**。
3. **对"IDE 内嵌"这一类消费者，官方层唯一承重的差异是一条没写进说明的产物形态变更**：插件引用由根绝对变文档相对（见 §3）。
4. **依赖树层面看不出任何异常**：`0.1.7-rc.2` → `0.2.0-rc.1` 只**新增 1 个包**（见 §4）。
5. 本仓此前**只留档到 `0.1.6-alpha.2`**：这 5 个发布（`0.1.7-alpha.1` / `alpha.2` / `rc.1` / `rc.2` / `0.2.0-rc.1`）在今天之前**零留档、零分析**——这是本次故障能"被打到才发现"的结构性原因。

## 2. 官方差异清单 × 对我们的影响判定

### 2.1 `0.2.0-rc.1` 自身（相对 `0.1.7-rc.2`）— 全部三段

| 段 | 条数 | 代表项 | 对我们（IDE 内嵌层） |
|---|---|---|---|
| 🎨 体验优化 | 10 | 对话动画/用时/间距；图片失效自动重传；无标题会话显示「未命名」；插件管理与内置插件界面；**账号模型可直接联网搜索，无需额外 API Key** | 无接口影响（纯前端/服务端行为） |

**关键否定事实**：这三段里**没有一条**属于"扩展必须改代码"的类别。

## 3. 承重差异（官方**没写**、我们实测到的）— 只有一个面破了

方法：起真实 `0.2.0-rc.1`（隔离 `DSH_HOME`），抓 `GET /` 的真实 HTML 逐条比对；对照物是 baseline `verified` 里的 `0.1.6-alpha.2`。

| 面 | 检查项 | `0.1.6-alpha.2`（我们已验证） | `0.2.0-rc.1`（现场） | 判定 |
|---|---|---|---|---|
| A | boot 赋值前缀 | `globalThis["__DSH_BOOT__"] =` | 同左 | ✅ 未变 |
| A | `batches[]` | 有 | 有（3 条） | ✅ 未变 |
| A | **boot 里的插件 url 形态** | `/plugins/…`（根绝对） | **`plugins/…`（文档相对）** | ❌ **破了** |
| B | 资产引用 | `./assets/…` ×4 | 同左 | ✅ 未变 |
| B | `<base href>` | `/` | **`./`** | ⚠️ **变了** |
| B | 阻塞式引导脚本 | `<script src="/plugins/??…">` | **`<script src="plugins/??…">`** | ❌ **破了** |
| B | `<link rel="preload" as="script">` | 0 个 | **2 个，href 同为相对** | ❌ **新增形态** |
| C | 认证（`/`、`/api`、WS `/api/remote.mux`） | 无 Cookie 401 / 带 Cookie 200·opened | 完全相同 | ✅ 未变 |
| C | RPC（`session/list`、`session/create`） | 200 ok | 完全相同 | ✅ 未变 |
| D | `dsh web --help` 的 `--no-open`/`--port`/`--host` | 三个都在 | 三个都在 | ✅ 未变 |
| D | 就绪行格式 `dsh web: http://127.0.0.1:<port>/?token=…` | — | 完全同格式 | ✅ 未变 |

**为什么这一条足以打死面板**：组装后的文档活在 `vscode-webview://` 源上，`<base href="./">` 把相对 `plugins/…` 解析成 webview 自己的地址（而不是 DSH 服务器）→ 404 → 模块队列收不到 `@deepseek-ai/dsh-client-modules` 注册 → `client-modules: HTML did not preload …`。
**为什么说明里看不到**：它是**服务端拼 HTML 时的产物形态**，不是"功能变更"，官方没有理由把它写进用户向发布说明。

**对照实验（机器可判定）**：同一份产物只改"插件地址是否绝对化"这一个变量 → 修复前 `__ModuleLoader__.mode=queue`、3 个插件请求全 404、body 逐字复现该报错；修复后 `mode=live`、3 个请求全 200、`#root` 渲染 38,662 B。脚本：`spike/verify-020-render.js`。

## 4. 依赖树差异（`npm view` 实测）

| 项 | `0.1.7-rc.2` | `0.2.0-rc.1` |
|---|---|---|
| `dependencies` 包名集合 | 与右侧几乎相同 | 唯一新增 **`@deepseek-ai/dsh-experimental-schedule-bundle`** |
| 其余 | 约 80 个 `@deepseek-ai/*` 包 | 同名单调整体升版 |
| 可见含义 | — | 对应 §2.1 的"自动化任务改由可选插件包提供" |

→ **结论：从 CLI 包的依赖清单看不出这次的破坏**。承重变更只在**构建产物**里，必须抓真 HTML（或跑真机渲染）才看得见。这也解释了为什么"读一遍官方说明 + 看一眼依赖树"这种低成本跟随法本次必然失效。

## 5. 对扩展的三条结论

1. **判据要认语义、不认形态**：`src/documentAssembly.ts:78` 的正则与 `:134` 的 `absolutePluginUrl()` 现在同时接受 `/plugins/…`、`./plugins/…`、`plugins/…`，且幂等；只认当前形态的设计在本次翻车（历史上是第 2 次改形态）。
2. **`<base href>` 不必跟着改**：资产已改写为同源 URI、插件地址已绝对化，页面里不再有依赖 `<base>` 的相对引用；动它属于无收益地扩大改动面。
3. **跟随机制要挂到"必经之路"上**：`npm run check:dsh` 只比版本号（且对 `latest` 用"水位覆盖"语义，会把**没探过**的 `0.1.7-rc.2` 报成 ✅）；真正能提前发现本次问题的，是"抓一次真 `GET /` 过一遍改写链"。
