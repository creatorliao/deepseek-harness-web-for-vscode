# 修复 — dsh 0.2.0-rc.1 把插件引用改成文档相对（`Failed to load plugins` / `HTML did not preload client.js`）

**日期**: 2026-09-29
**扩展版本**: 影响 v0.3.1 – v0.6.1（凡把本机 dsh 升到 `0.2.0-rc.1` 的用户）→ 修复 v0.6.2
**dsh 版本**: 适配 `0.2.0-rc.1`（上游把内嵌页 HTML 里的插件引用由**根绝对**改为**文档相对**）
**影响面**: 面板（次级侧边栏与编辑器页签两种形态）**完全打不开**——boot 遮罩报 `Failed to load plugins`，DSH 界面进不去；扩展自身进程、API 直连、主题同步均正常
**范围**: `src/documentAssembly.ts`（`PLUGIN_PRELOAD_RE` → `PLUGIN_REF_RE` + 新增 `absolutePluginUrl()`）、`test/documentAssembly.test.js`（+3 用例）、`docs/02-Areas/dsh-baseline.json`、`README.md` / `README.en.md` 兼容矩阵、`CHANGELOG.md` / `CHANGELOG.en.md`
**根因归属**: 上游 dsh 版本变更
**关联**: [../../03-Resources/VOC20260929-02-升级dsh0.2.0后页签插件加载失败.md](../../03-Resources/VOC20260929-02-升级dsh0.2.0后页签插件加载失败.md) ｜ [10-修复_dsh0.1.2-rc1认证与RPC.md](10-修复_dsh0.1.2-rc1认证与RPC.md)（同一条改写链的前一次破坏）

## 现象

用户把本机全局 `dsh` 从 `0.1.7-rc.2`（`latest`）升到 **`0.2.0-rc.1`**（`next`）后，在 VS Code 1.105.1（`deepseekHarness.openTarget = "editorTab"`）里打开 DSH 页签：

```text
HARNESS
Failed to load plugins
client-modules: HTML did not preload @deepseek-ai/dsh-client-modules/client.js
```

**报错文案与根因无关**（本项目第 4 次出现同一句文案，前三次根因分别是 preload 未绝对化、boot 正则失配、dist 布局 + 认证全换）：
现场那份 HTML 里 preload 标签**是存在的**，只是它的 URL 变成了相对路径。

## 根因

### A. 上游把整份 HTML 的插件引用从"根绝对"改成了"文档相对"

对真实 `0.2.0-rc.1` 的 `GET /` 响应（隔离 `DSH_HOME` 实测，产物留档 `spike/probe/0.2.0-rc.1/index.html`，34,748 B）逐条比对：

| 引用 | ≤ `0.1.6-alpha.2` | `0.2.0-rc.1` |
| --- | --- | --- |
| `<base href>` | `/` | **`./`** |
| 引导脚本 | `<script src="/plugins/??@deepseek-ai/dsh-client-modules/client.js&rev=…">` | **`<script src="plugins/??…">`**（去掉前导 `/`） |
| 插件预载 | 无此形态 | **2 个 `<link rel="preload" as="script" href="plugins/??…">`** |
| boot JSON | `entries[].url = "/plugins/…"` | **65 个 `entries[]` + 3 个 `batches[]` 全部为 `plugins/…`** |

### B. 我们的两处判据写死了"根绝对"，一条都匹配不上

`src/documentAssembly.ts`（修复前）：

1. `PLUGIN_PRELOAD_RE = /(src|href)="(\/plugins\/[^"]+)"/`（旧 `:69`）——**要求前导 `/`**，`src="plugins/…"` 不匹配 → 引导脚本原样留在文档里；
2. `rewriteBootPluginUrls` 的 `if (entry.url?.startsWith("/"))`（旧 `:128`）——0.2 的 url 全部不以 `/` 开头 → **整个插件图原样返回，函数等于空转**。

### C. 为什么必然崩在这句话上

组装后的 webview 文档 origin 是 `vscode-webview://…`，`<base href="./">` 把相对 `plugins/??…` 解析到 **webview 自己的目录**（而不是 DSH 服务器）→ 404 →
`__ModuleLoader__` 的 `pendingQueue` 里永远收不到 `@deepseek-ai/dsh-client-modules` 的注册 →
`create()` 抛出 `client-modules: HTML did not preload @deepseek-ai/dsh-client-modules/client.js`（该错误原文已在留档 HTML 的引导脚本里逐字核对）。

## 修复

**判据从"只认绝对形态"改成"两种形态都认"**，而不是把 0.2 的形态抄进来——上游已经来回改过一次形态（rc.8 加 preload 标签、0.1.2 改 mux、0.2 去前导斜杠），只认当前形态等于把下一次变更预支成下一次事故。

| 改动 | 内容 |
| --- | --- |
| `PLUGIN_REF_RE`（`:78`） | `/"(?:\.\/\|\/)?plugins\/[^"]+"/`——同时匹配 `/plugins/…`、`./plugins/…`、`plugins/…`；函数名 `rewriteBootPluginPreloads` 保留（它覆盖的就是"引导脚本 + preload 提示"这一类元素） |
| 新增 `absolutePluginUrl()`（`:134`） | 归一化后**只对 `plugins/` 开头的 url** 前缀 `serverBase`；**幂等**（二次调用是 no-op，产不出 `…//plugins/…`）；非插件 url 原样返回 |
| `rewriteBootPluginUrls`（`:148`） | `entries[]` / `batches[]` 的 url 走同一个 `absolutePluginUrl`，删除 `startsWith("/")` 判据 |

**没有动 `<base href="./">`**：资产引用本就被改写成同源 webview URI，插件引用绝对化后页面里不再有依赖 `<base>` 的相对引用；改 `<base>` 属于无收益地扩大改动面。
