# 教程 · 启动流程全链路

**日期**: 2026-09-14 ｜ **状态**: 当前 ｜ **回答**: Q3「它是怎么启动起来的？」
**事实基准**: 代码 commit `7918816` 之后的工作区

---

## 1. 四个入口，一条链路

用户可以从不同的地方把 DSH 叫起来，但最终都会汇到同一条链路：

| 入口 | 触发 | 代码 |
|---|---|---|
| **活动栏图标**（点击左侧 DeepSeek 图标） | 侧边栏视图被 resolve → 自动 `start()` | `launcherView.ts:518-522` |
| **命令面板** → `DeepSeek Harness: Start` | `manager.start()` → 开面板 | `commands.ts:18-27` |
| **状态栏按钮**（左下方） | `stopped` 时点它等价于 Start | `statusBar.ts:24-27` |
| **面板覆盖层的「启动」按钮** | 面板已开着但服务没起 | `dshPanel.ts:151-154` |

> ⚠️ 另外还有一个**自动**入口：`activationEvents: ["onStartupFinished"]`。扩展在 VS Code 启动完成时就激活了，如果**上一次同一个工作区里 dsh 是运行着的**，它会自动把 dsh 重新拉起来并恢复面板（见 §4）。

## 2. 八个阶段

```
① activate            扩展激活，装配部件，读 workspaceState
      │
② 解析 dsh 二进制      resolveDshPath()  六处候选，跨平台
      │
③ 解析版本 + 硬门      resolveDshVersion() → 低于 0.1.2-rc.1 直接拒绝
      │
④ 探测 --no-open      probeNoOpenSupport()  跑 dsh web --help（带缓存）
      │
⑤ spawn               dsh web --port 0 [--no-open]，cwd = IDE 工作区根
      │
⑥ 等就绪行            正则匹配 stdout 的 "dsh web: http://127.0.0.1:<port>"
      │                （10s 超时 → 报错 + 强杀）
      │
⑦ 换会话 Cookie       GET /?token=… → 读 Set-Cookie（必须在就绪之前完成）
      │
⑧ 就绪后              同步主题 → 保证工作区会话 → 组装文档 → 渲染面板
```

### 阶段 ② 二进制解析的候选顺序

`resolveDshPath()`（`serverManager.ts:319-348`）按顺序试，命中即停：

1. 环境变量 `DSH_BIN`
2. **npm 全局 bin**（`npm prefix -g`；Windows 是 `%AppData%\npm`，取 `dsh` 与 `dsh.cmd`）
3. macOS Homebrew：`/opt/homebrew/bin/dsh`
4. `/usr/local/bin/dsh`
5. `~/.npm-global/bin/dsh`
6. **nvm**：`~/.nvm/versions/node/*/bin/dsh`
7. **npx 缓存**：`~/.npm/_npx/*/node_modules/.bin/dsh`（Windows：`%LocalAppData%\npm-cache\_npx\*`）

**为什么要探测这么多**：GUI 启动的编辑器**不继承 shell 的 PATH**（nvm / Homebrew 的路径不在里面），所以直接 `spawn("dsh")` 会 `ENOENT`。这条经验来自真实故障记录：[修复_跨平台dsh解析与spawn](../R20260817-01-桥架构与IDE内嵌/10-修复_跨平台dsh解析与spawn.md)。

全部失败时不会静默：错误信息会把 `tried` 列表原样打出来，并提示 `npm i -g @deepseek-ai/dsh`。

### 阶段 ③ 版本硬门

```ts
const MIN_DSH_VERSION = "0.1.2-rc.1";     // serverManager.ts:77
```

`0.1.2-rc.1` 之前的 dsh 说的是完全不同的 API 面（没有令牌认证、RPC 不是 Typert、dist 布局也不同）。**与其让用户看到白屏，不如直接拒绝并告诉他去升级。**

### 阶段 ④ 为什么不用版本号判断 `--no-open`

`--no-open` 这个 flag 属于 **`dsh-web-app`**，不属于 CLI。历史出现过 "CLI 是 rc.7、但传递依赖已解析到 rc.8" 的错配——按 CLI 版本判断就会判错（要么漏传导致弹浏览器，要么多传导致旧版启动失败）。

所以改成**现场探测**：跑一次 `dsh web --help`，看输出里有没有 `--no-open`（结果按二进制路径缓存）。探测本身失败时，才回退到版本号判断。

### 阶段 ⑤ spawn 的实际参数

```ts
args = ["web", "--port", "0"];                    // 端口交给 OS 分配，避免冲突
if (passNoOpen) args.push("--no-open");           // 抑制自动开浏览器
args.push(...(opts.extraArgs ?? []));
spawn(bin, args, {
  cwd,                                            // = IDE 工作区根 → DSH 默认工作区
  env: { ...process.env, DSH_HOME? },             // 需要隔离时覆盖状态目录
  stdio: ["ignore", "pipe", "pipe"],
  shell: process.platform === "win32",            // Windows 的 .cmd 需要 shell
});
```

### 阶段 ⑥ 就绪行解析

```ts
const URL_LINE_RE = /dsh web: (http:\/\/127\.0\.0\.1:\d+)(\/\?[^\s]+)?/;   // :72
```

- 第 1 组 = 端口 → 得到 `serverUrl`（面板和桥都用它）
- 第 2 组 = `/?token=…` → 得到 `authUrl`（**0.1.2 起才有**，用于换 Cookie 与"在浏览器打开"）

10 秒（`DEFAULT_READY_TIMEOUT_MS`）没等到就报错并强杀；`SIGKILL_GRACE_MS = 6s` 是停机时的强杀宽限。

### 阶段 ⑦ 令牌换 Cookie

```ts
// exchangeCookie: 用 node:http（不是 fetch）GET 那个带 token 的 URL
// 为什么不用 fetch：fetch 的 redirect:"manual" 返回 opaque-redirect，读不到头
GET /?token=<launchToken>  →  303 + Set-Cookie: dsh-auth-<hash>=…
→ 只取第一段 "name=value"，存为 this.authCookie
```

**顺序很关键**：换 Cookie 必须在 `settleReady()` **之前**完成，这样所有消费者（面板组装、桥转发、RPC）一拿到 `ready` 就已经带着 Cookie 了。换失败不阻断（降级为无 Cookie，让真实的 401 暴露出来），因为离线/异常时不该把整个启动卡死。

### 阶段 ⑧ 就绪之后（`extension.ts:69-97` 的 state 监听器）

严格按这个顺序，每一步的顺序都有原因：

```
state === "ready"
  1. await theme.syncNow()                 ← 先同步主题，页面加载时就是正确配色（R7）
  2. wsSessionId = ensureWorkspaceSession()← 保证 IDE 工作区在 DSH 里存在且有会话
  3. preset = {"sessionId": wsSessionId}   ← 让前端选中"当前文件夹"而不是"最近活跃"
  4. autoRestart 且之前有面板？→ 逐个恢复（每个绑自己的会话）
     否则                     → 打开一个绑 IDE 工作区会话的面板
  5. 后台跑 dsh 版本软校验（24h 门控），结果回来再刷新侧边栏
```

## 3. 状态机

```
        start()                 就绪行 + Cookie 成功
stopped ────────► starting ──────────────────────────► ready
   ▲                 │                                   │
   │                 │ 就绪超时 / 子进程提前退出 / ENOENT    │ 子进程退出
   │                 ▼                                   ▼
   │               error ◄───────────────────────────── error
   │                 │
   └─────────────────┴── stop() ──► stopping ──► stopped
```

- 每次转换都会打一行带 pid 的日志（`serverManager.ts:417`），方便排查睡眠唤醒类问题。
- `ready` 时子进程意外退出 → 直接进 `error`（绝不会对外暴露一个已死的 URL，`:520`）。
- `stop()` → SIGTERM，6 秒后升级 SIGKILL；Windows 下杀**整棵进程树**（`taskkill /T /F`），否则 `cmd.exe` 包装器会留下孤儿 `node` 进程。

## 4. 三种"再次启动"的场景

| 场景 | 判定依据 | 行为 |
|---|---|---|
| **同一工作区 reload**（改了设置 / 装了扩展） | `workspaceState` 里的 `dsh.wasRunning` 为 `true`（**按工作区隔离存储**） | 自动重启 dsh，并**恢复之前打开的所有面板**（每个面板绑回它自己的会话） |
| **打开不同文件夹** | 新工作区没有 `dsh.wasRunning` 记录 | 冷启动，等你显式打开 |
| **多根工作区增删子文件夹** | 只有**主根**（`workspaceFolders[0]`）真的变了才处理 | 主根变了 → 关闭所有面板（它们绑的是旧工作区的会话）；只增删附加根 → 不动，别打断你的对话 |

**为什么 `dsh.wasRunning` 不写在 `deactivate()` 里**：进程退出时浮动 Promise 可能丢失。改成在**每次状态转换**时写（`extension.ts:48-53`）。

## 5. 失败模式速查

| 现象 | 根因 | 去哪看 |
|---|---|---|
| `dsh not found. Tried: …` | 二进制没找到（GUI 不继承 PATH 是最常见原因） | 错误信息里的 `tried` 列表；设 `DSH_BIN` 兜底 |
| `dsh x.y.z is not supported` | 版本低于硬门 | 按提示 `npm i -g @deepseek-ai/dsh@latest` |
| `dsh did not become ready within 10000ms` | 启动行格式变了 / 进程卡住 | 看 `[dsh]` 前缀的 stderr 转发 |
| 面板起来但报 401 | Cookie 没换成 | 日志 `cookie exchange: no set-cookie on …` |
| 面板白屏 / "Failed to load plugins" | 文档层改写失效（boot 前缀 / dist 布局变了） | 见 [上游兼容规范](../../02-Areas/20260914-06-上游兼容规范_跟随最新官方DSH.md) 四个破坏面 |
| 侧边栏停在 "Starting…" | webview 消息早于监听器注册 | 已有 `view-ready` 握手兜底；若复现见[修复记录](../R20260817-01-桥架构与IDE内嵌/12-修复_侧边栏状态卡在Starting.md) |

**所有日志都带 `[dsh]` 前缀**，在 VS Code 的「帮助 → 切换开发人员工具 → Console」或输出面板里过滤即可。

---

## 6. 一句话总结

> **启动 = 「找到一个能用的 dsh」+「用正确的参数和 cwd 把它拉起来」+「从它的启动行里拿到端口和令牌」+「把令牌换成 Cookie」+「先同步主题、再保证工作区会话，最后才组装页面」。**
> 前四步在 `serverManager.ts`，最后一步在 `extension.ts` 的 `ready` 处理器里，顺序不能换。
