**日期**: 2026-09-14 ｜ **状态**: 当前 ｜ **回答**: Q1「它的工作原理是什么？」
**事实基准**: 代码 commit `7918816` 之后的工作区；dsh 适配基线见 [00-README](00-README.md)

## 1. 一句话

**扩展不写 Agent，也不改 DSH 的代码。它做三件事：帮你把 `dsh web` 进程跑起来；把 DSH 的前端页面"搬"进 VS Code 的 webview 里；然后在页面和本地 dsh 服务之间架一条 `postMessage` 通道，替页面发所有网络请求。**

```
   ┌──────────────────────── VS Code ────────────────────────┐
   │                                                          │
   │  扩展宿主（Node，有网络与文件权限）                        │
   │   ├─ DshServerManager ──spawn──► dsh web --port 0        │
   │   │        ▲                            │                │
   │   │        │ HTTP/WS（普通 Node 请求）    │ 127.0.0.1:<随机端口>
   │   │        │                            ▼                │
   │   │   BridgeHost ◄──postMessage──┐   dsh 本地服务          │
   │   │        │                     │   （前端 dist + /api）  │
   │   │        │ 组装文档             │                       │
   │   └────────┼─────────────────────┼───────────────────────┘
   │            ▼                     │
   │   WebviewPanel（编辑器标签页）      │
   │    ┌──────────────────────────────────────────┐
   │    │ DSH 官方前端（原样加载，同源 webview 资源）│
   │    │  + bridge-client.js（我们注入的 shim）    │
   │    │    · window.fetch      → postMessage     │
   │    │    · window.WebSocket  → postMessage     │  ──┘
   │    │    · navigator.clipboard → postMessage   │
   │    │    · matchMedia(dark)  ← 宿主推送主题     │
   │    └──────────────────────────────────────────┘
   └──────────────────────────────────────────────────────────┘
```

## 2. 三个决定性约束（理解一切的前提）

这三个约束不是"设计偏好"，是**外部事实逼出来的**。不先理解它们，后面所有代码看起来都会很奇怪。

### 约束一：不能直接用 `<iframe>` 嵌 DSH

VS Code webview 里，**跨源 iframe 的 `navigator.clipboard` 一律 `Write permission denied`**，`allow="clipboard-read; clipboard-write"` 无效；原生 `Cmd+C/V` 同样不可用。

- 上游 issue：[microsoft/vscode#182642](https://github.com/microsoft/vscode/issues/182642)（open）、[#129178](https://github.com/microsoft/vscode/issues/129178)
- 后果：聊天窗里复制代码块、粘贴长文本全废——**核心交互缺失，iframe 方案被否决**
- 证据：[Phase 0 实测笔记 V8](../R20260817-01-桥架构与IDE内嵌/08-事实_Phase0实测笔记.md)

> 👉 所以架构从"iframe 内嵌"改成了"**把 DSH 前端直接加载进 webview 文档本身**"——没有 iframe，剪贴板就能被我们自己的 shim 接管。

### 约束二：webview 页面不能直连 DSH 的 `/api`

DSH 的 `/api` 有一道**信任围栏**（0.1.0-rc.6 实测，见 [DSH 上游事实](../../03-Resources/20260914-01-DSH上游事实与协议速查.md) §2）：

| 请求形态 | 结果 |
|---|---|
| 普通 Node 请求（无 `Origin`、无 `sec-fetch-site`） | **200 放行** |
| 同源浏览器请求 | 200 |
| **webview 的 `Origin: vscode-webview://…` + cross-site** | **403** |
| 无 Origin 但 `sec-fetch-site: cross-site` | **403** |

> 👉 所以页面里的每一次请求，都必须**转交给扩展宿主**，由宿主用"普通 Node 请求"的形态发出去。这就是"传输桥"的存在理由。

### 约束三：DSH 前端的资产必须同源加载

DSH 的前端 dist 是 Vite 产物：主 bundle 用**相对 import** 引 `./vendor-*.js`、`./langs/*.js`，CSS 里 `url("./fonts/...")` 引 KaTeX 字体。浏览器对**跨源 module / font** 要求 CORS，而 DSH 服务器不发这些头。

> 👉 所以扩展把整个 `/assets` 树**下载到本地**（`globalStorage/dsh-dist`），再用 `webview.asWebviewUri()` 以同源资源的形式提供给页面。

## 4. 一次"发一条消息"的完整旅程

以你在内嵌界面里发一条聊天消息为例：

```
1. DSH 前端调用 fetch("/api/session/prompt", {method:"POST", body:...})
        │  （前端认为自己在和 location.origin 说话）
        ▼
2. media/bridge-client.js 的 fetch shim 拦截
   · isSameOrigin("/api/...") 为真 → 不真的发请求
   · post({type:"http", id:7, method, url:"/api/...", headers, body})
        ▼
3. 扩展宿主 BridgeHost.handle() 收到
   · relayHttp(serverBase + url, msg, fetch, authCookie)
   · 关键：这是一个「普通 Node fetch」，没有 Origin / sec-fetch-site
     → 通过 /api 信任围栏
   · 同时带上启动时换来的浏览器会话 Cookie（dsh 0.1.2+ 必需）
        ▼
4. dsh 本地服务处理，返回响应
        ▼
5. BridgeHost 回传 post({type:"http-res", id:7, status, headers, body:ArrayBuffer})
        ▼
6. bridge-client.js 收到后 new Response(...) 交给 resolve
   → DSH 前端拿到一个"看起来正常"的 fetch 响应，完全不知道中间有桥
        ▼
7. 流式回复走 WebSocket：前端 new WebSocket("ws://.../api/remote.mux")
   → shim 拦截 → post({type:"ws-open", id, path})
   → 宿主 WsRelay 用 ws 库连真正的服务端（带同一个 Cookie）
   → 每帧回传 post({type:"ws-frame", id, data}) → shim 派发给监听器
```

**注意第 6 步和最后一步**：DSH 前端**完全不知道**自己被桥接了。这是"零 fork"的关键——我们不 patch 官方代码，只替换它依赖的**浏览器全局对象**。

## 5. 桥的消息协议（完整）

**webview → 宿主**

| 消息 | 字段 | 语义 |
|---|---|---|
| `http` | `id, method, url, headers?, body?` | 代发一次 HTTP 请求 |
| `http-abort` | `id` | 请求取消（宿主尽力而为；客户端另有 30s 超时兜底） |
| `ws-open` | `id, path` | 建立到服务的 WebSocket |
| `ws-send` | `id, data` | 发一帧 |
| `ws-close` | `id` | 关连接 |
| `clipboard-write` | `id, text` | 写系统剪贴板（走 `vscode.env.clipboard`） |
| `clipboard-read` | `id` | 读系统剪贴板 |
| `start` / `stop` | — | 覆盖层上的启停按钮（只有占位页用） |

**宿主 → webview**

| 消息 | 语义 |
|---|---|
| `http-res` / `http-err` | 请求结果 / 失败 |
| `ws-open-res` / `ws-frame` / `ws-close` | WebSocket 生命周期与数据 |
| `clipboard-res` | 剪贴板结果（`ok` / `text` / `message`） |
| `server-status` | 服务状态变化，驱动覆盖层（`ready` 时隐藏） |
| `theme-preference` | VS Code 主题切换（**不重载页面**） |

## 6. 覆盖层：绝不出现白屏

`dshPanel.ts` 会在真正的 DSH 页面**之前**先渲染一个极简壳（`placeholderHtml()`），并往最终文档尾部注入一段 `statusChromeHtml()`：

- 三态：`starting`（转圈文案）/ `error`（错误信息 + 重试）/ `stopped`（启动按钮）
- 服务 `ready` → 覆盖层 `hidden`
- 这套覆盖层是**状态驱动**的，不是"加载失败才显示"，所以任何异常都不会是白屏。

## 7. 主题跟随为什么要 shim `matchMedia`

嵌入式页面的 origin 是 `vscode-webview://`（**不是回环地址**），导致 DSH 前端的连接层判断自己运行在"非本地作用域"，设置进入 memory 模式，**永远不会采用 `ui-theme.preference`**，主题停在 `"system"`，而 `system` 最终走 `matchMedia("(prefers-color-scheme: dark)")`。

所以扩展走两条路同时兜：

1. **宿主侧**：往 DSH 写设置 —— `POST /api/settings.update`，`payload: { ns: "ui-theme", patch: { preference: "dark"|"light" } }`（`src/themeSync.ts:22`）
2. **页面侧**：`bridge-client.js` 把 `matchMedia` 对 `(prefers-color-scheme: dark)` 这一个 query 做 shim，值由宿主推送；主题切换时宿主发 `theme-preference`，shim 直接触发监听器回调——**不重载页面**

## 8. 失败模式与兜底（都是真实踩过的）

| 失败模式 | 兜底 |
|---|---|
| dsh 二进制找不到（GUI 启动的编辑器不继承 shell PATH） | 多级探测：`$DSH_BIN` → npm global → Homebrew/`/usr/local/bin` → nvm → npx 缓存；失败时把 `tried` 列表打进错误信息 |
| dsh 太旧（< `0.1.2-rc.1`） | **硬门**：直接拒绝启动并提示升级命令，而不是进半坏状态 |
| 启动行正则匹配不上（上游改过格式） | 10s 就绪超时 → 报错 + 强杀子进程 |
| Cookie 换取失败 | 只记日志、不阻断就绪；面板组装时暴露真实的 401 |
| `__DSH_BOOT__` 前缀变了导致改写失效 | 正则同时接受 `window.__DSH_BOOT__` 与 `globalThis["__DSH_BOOT__"]`（历史上变过一次） |
| 多面板同时恢复 → 并发下载 dist 互相踩踏 | 共享一次 in-flight 下载（`distDownloadInFlight`），缓存键是 boot manifest 的 `rev` |
| 侧边栏状态卡在 "Starting…" | 页面加载完主动发 `view-ready` 握手，宿主再补推当前状态 |
