## 0. 先给结论

**现在为什么不在右侧**（代码事实）：

| 事实 | 位置 |
|---|---|
| 左侧活动栏里挂的是**启动器侧边栏**（DeepSeek 图标） | `package.json` 的 `viewsContainers.activitybar` + `src/launcherView.ts` |
| DSH 的 UI 是**编辑器标签页 webview**，不是侧边栏 | `src/dshPanel.ts` 的 `createWebviewPanel(...)` |
| 打开时的列：默认 `ViewColumn.Beside`，但**新建会话 / 打开会话 / reload 恢复**都硬编码成 `ViewColumn.Active` | `dshPanel.ts:121`、`sessionPanels.ts:13,45,95`、`extension.ts:135,145` |

`ViewColumn.Active` = **叠在当前活动编辑器组上**——你的活动组在哪，面板就在哪。这就是"它跟着左边跑"的根源。

**要做到"Cursor 那样固定右侧"，有三档方案：**

| 档 | 做法 | 像 Cursor 的程度 | 代价 |
|---|---|---|---|
| **A** | 把 DSH UI 做成**次级侧边栏**（Secondary Side Bar）里的 webview 视图 | ★★★★★ 结构上永远在右侧 | **要抬 `engines.vscode`**；多面板模型要重做 |
| **B** | 保留编辑器标签页，但每次打开都**强制落到最右的编辑器组** | ★★★☆☆ 位置对了，但还是标签页 | 改动小；用户仍能拖走 |
| **C** | 加一个设置项，让"新会话/打开会话/恢复"统一走同一个列策略，默认最右 | ★★★☆☆ | 改动最小、可回退 |

**我的建议：先做 C+B（低风险、当天可验证），确认手感后再决定要不要上 A。**

## 1. 现状：三个地方决定了面板落在哪

```ts
// src/dshPanel.ts:119-122
open(sessionPreset?: string, viewColumn: vscode.ViewColumn = vscode.ViewColumn.Beside)

// src/sessionPanels.ts:13-15
export const VIEW_COLUMN_ACTIVE = -1;   // vscode.ViewColumn.Active —— 叠在当前组
export const VIEW_COLUMN_BESIDE = -2;   // vscode.ViewColumn.Beside —— 活动组旁边

// src/sessionPanels.ts:45  open() 默认 BESIDE
// src/extension.ts:135,145 onNewSession / onOpenSession 传 ACTIVE
// src/sessionPanels.ts:95  restore() 传 ACTIVE
```

`ViewColumn.Beside` 的真实语义（VS Code 源码核对）：**"活动组旁边"的新组**，方向默认向右（受 `workbench.editor.openSideBySideDirection` 影响）。

- **只有一个编辑器组时**：Beside 恰好=最右，观感是对的；
- **有多个组、且活动组不在最右时**：它插在**活动组旁边，不保证最右**。

所以现在的行为是"**跟着你的活动组跑**"，而不是"永远在最右"。

## 2. A 档 · 把 DSH UI 放进次级侧边栏（最像 Cursor）

Cursor 的聊天面板就在右侧的**次级侧边栏**。VS Code 从 1.100 起支持扩展把视图容器贡献到这个位置。

### 2.1 事实核对（重要，含一个坑）

| 项 | 结论 |
|---|---|
| `contributes.viewsContainers.secondarySidebar` | **源码支持**：`viewsExtensionPoint.ts` 的 schema 有 `activitybar` / `panel` / `secondarySidebar` 三个键（映射到 `Sidebar` / `Panel` / `AuxiliaryBar`） |
| **版本门槛** | **1.90 / 1.95 / 1.98 / 1.99 都不支持**（已逐版核对源码，且 schema 是 `additionalProperties: false`，写了也不注册）；main 支持。**推断引入版本为 1.100** |
| ⚠️ 对本仓库的后果 | 现在是 `"engines": { "vscode": "^1.90.0" }` → **要用就必须抬到 `^1.100.0`**，并确认 **Antigravity 的 VS Code 基线够不够** |
| 官方文档 | ⚠️ `contribution-points` / `tree-view` **至今没记录 `secondarySidebar`** —— 属于"源码支持、文档未覆盖"，别指望 JSON 智能提示会给你补全 |

### 2.2 package.json 写法

```jsonc
"contributes": {
  "viewsContainers": {
    "secondarySidebar": [
      { "id": "deepseekHarnessChat", "title": "DeepSeek Harness", "icon": "media/icon.svg" }
      // id / title / icon 三者必填；icon 建议 24x24 SVG
    ]
  },
  "views": {
    // key 是「容器 id」，不是 workbench.view.extension.<id>
    "deepseekHarnessChat": [
      { "type": "webview", "id": "deepseek-harness.chatView", "name": "DeepSeek Harness" }
    ]
  }
}
```

### 2.3 怎么把它显示出来

```ts
// 推荐：视图级命令（自动注册）
await vscode.commands.executeCommand("deepseek-harness.chatView.focus");
// 或容器级命令
await vscode.commands.executeCommand("workbench.view.extension.deepseekHarnessChat");
```

⚠️ **不要**用 `workbench.action.toggleAuxiliaryBar` 来"显示我的面板"——它只切**整个次级侧边栏 part 的显隐**，不保证显示的是你的容器（可能是用户上次在那儿用的别的视图）。它适合做"开关侧边栏"，不适合做"打开我的面板"。

### 2.4 A 档的真实代价（必须想清楚）

| 代价 | 说明 |
|---|---|
| **抬高 engines** | `^1.90.0` → `^1.100.0`，会挡掉一部分老编辑器用户；Antigravity 的基线需先确认 |
| **多面板模型要重做** | 侧边栏里**一个视图 = 一个 webview 实例**。当前"一个会话一个编辑器标签页、多个并排"的能力**放不进去**。要保留多会话，就得改成"**单视图 + 视图内的会话切换器**"——这反而更接近 Cursor 的形态，但这是一次**架构级改造**，牵动 `sessionPanels.ts`、`dshPanel.ts`、`launcherView.ts` |
| 可见性由 workspace state 决定 | 次级侧边栏的显隐会被编辑器记成工作区状态，**不能假设它可见**，必须显式调用 §2.3 的命令 |
| 收益（顺手解决 Q4） | 侧边栏通常 < 1024px → **DSH 自己的侧边栏会自动收成 56px 轨道**，见 [04-方案 §3-S1](04-方案_DSH界面调整与侧边栏收纳.md) |

## 3. B 档 · 编辑器标签页强制最右（改动最小）

### 3.1 先把"不存在的命令"划掉（省得白写）

我原本准备用的一批命令，经 VS Code 源码逐条核对后**有真有假**：

| 命令 id | 是否存在 | 说明 |
|---|---|---|
| `workbench.action.moveEditorToRightGroup` | ✅ 存在 | 找右侧组，**没有就新建**，移过去并聚焦 |
| `workbench.action.moveEditorToLeftGroup` / `…ToAboveGroup` / `…ToBelowGroup` | ✅ 存在 | 同族 |
| `moveActiveEditor` | ✅ 存在 | **注意：没有 `workbench.action.` 前缀**。参数 `{ to: 'left'\|'right'\|'up'\|'down'\|'first'\|'last'\|'center'\|'position'\|'previous'\|'next', by: 'tab'\|'group', value?: number }`；`{to:'last',by:'group'}` 移到最后一个组，但**没有别的组时是 no-op** |
| `workbench.action.splitEditorRight` / `…Left` / `…Up` / `…Down` | ✅ 存在 | 新建组 + 把当前编辑器 **copy** 过去（不是搬走） |
| `workbench.action.moveActiveEditorToLastGroup` | ❌ **不存在** | 别写 |
| `moveEditorToLastGroup` | ❌ **不存在** | 别写 |
| `workbench.action.newGroupRight` | ❌ **不存在** | 别写 |

并且：**不要用 `ViewColumn.Nine` 去"顶到最右"** —— `columnToEditorGroup` 会把中间所有不存在的列**逐个创建出来**，副作用很大。

### 3.2 可靠做法：自己算最右列

`vscode.window.tabGroups.all` 能拿到所有编辑器组及其 `viewColumn`（本机 `@types/vscode` 1.125 已确认该 API 存在）。所以：

```ts
/** 最右编辑器组的列号（没有组时回落到 One）。 */
function rightmostColumn(): vscode.ViewColumn {
  const cols = vscode.window.tabGroups.all.map((g) => g.viewColumn);
  return cols.length ? (Math.max(...cols) as vscode.ViewColumn) : vscode.ViewColumn.One;
}

/** 把面板放到最右，必要时先开一个新组。 */
function openAtRight(panel: vscode.WebviewPanel): void {
  const target = rightmostColumn();
  const active = vscode.window.tabGroups.activeTabGroup.viewColumn;
  if (target === active) {
    // 活动组就是最右组 → 开在旁边（新组落在最右）
    panel.reveal(vscode.ViewColumn.Beside);
  } else {
    panel.reveal(target);
  }
  // 兜底：Beside 在多组场景只保证"活动组旁边"，再补一次强制右移
  void vscode.commands.executeCommand("workbench.action.moveEditorToRightGroup");
}
```

调用点就是 §1 里那三个：`sessionPanels.open()`、`extension.ts` 的 `onNewSession` / `onOpenSession`、`sessionPanels.restore()`。

**边界**：用户仍可以把标签页拖到左边；扩展无法阻止（VS Code 没有"锁定列"的 API）。所以 B 档只能保证"**每次打开时**在最右"。

## 4. C 档 · 加设置项，把列策略收成一处（建议与 B 一起做）

现在列策略**散在四处硬编码**（两处 `ACTIVE`、两处 `BESIDE`）。建议：

1. `package.json` 加设置：
   ```jsonc
   "deepseekHarness.panelLocation": {
     "type": "string",
     "enum": ["rightmost", "active"],
     "default": "rightmost",
     "description": "%setting.panelLocation.description%"   // 9 语言同步，见扩展与 Webview 规范 §4
   }
   ```
2. `sessionPanels.ts` 里把 `VIEW_COLUMN_ACTIVE` / `VIEW_COLUMN_BESIDE` 两个常量换成一个 `resolveColumn()` 策略函数，四个调用点全部走它；
3. 加单测：给定"1 个组 / 多个组 / 活动组在最右"三种布局，断言算出的列号（纯函数，可直接用 `node:test` 覆盖，不需要 vscode 运行时——把 `tabGroups` 的取值做成注入参数，照抄 `workspaceTracker.ts` 的写法）。

**收益**：改动可控、可回退、不碰 `engines`、不重做多面板；先验证"右侧是不是真的好用"，再决定要不要上 A。

## 5. 三档对照

| 维度 | A 次级侧边栏 | B 强制最右列 | C 设置项 + B |
|---|---|---|---|
| 位置是否"永远右侧" | ✅ 结构保证 | ⚠️ 每次打开时保证 | ⚠️ 同 B |
| 还是编辑器标签页吗 | ❌ 变成侧边栏视图 | ✅ 是 | ✅ 是 |
| 用户能否拖走 | 只能拖到主侧边栏 | 能拖到任意列 | 能拖到任意列 |
| 要不要抬 `engines.vscode` | **要（≥1.100）** | 不要 | 不要 |
| 多会话多面板 | **要重做（单视图内切换）** | 保持现状 | 保持现状 |
| 工作量 | 高（架构级） | 低 | 低 |
| 顺手解决 Q4 侧边栏 | ✅ 面板天然窄 → 自动收起 | ❌ 视宽度而定 | ❌ |
| 风险 | 中（用户基数、Antigravity 基线） | 低 | 低 |

## 6. 建议路线

```
第一步（低风险，建议立刻做）
  C + B：加 deepseekHarness.panelLocation（默认 rightmost），把四个调用点收成一个策略函数，
         补三条布局单测。→ 每次打开都在最右，手感立刻改善，且完全可回退。

第二步（用几天再决定）
  如果"还是标签页"这件事本身让你不舒服 → 上 A 档：
    · 先确认你的 VS Code 与 Antigravity 版本 ≥ 1.100
    · 抬 engines.vscode
    · 把 DshPanel（编辑器 webview）改造成 WebviewViewProvider，
      桥与文档组装可以原样复用（它们不依赖面板形态）
    · 决策点：多会话怎么办 —— 单视图内做会话切换器（推荐，像 Cursor），
      还是砍掉并排能力
```

## 8. 依据说明

- **VS Code 侧**：`contributes.viewsContainers` 的 schema、命令 id、`ViewColumn` 语义均**逐版核对源码**（`viewsExtensionPoint.ts`、`viewsService.ts`、`editorCommands.ts`、`auxiliaryBarActions.ts`、`extHostTypes.ts`、`extHostWebviewView.ts`），未取得官方散文文档的部分已标注为推断。⚠️ 官方 `contribution-points` 文档**至今未记录 `secondarySidebar`**。
- **本仓库侧**：列策略与调用点来自 `src/dshPanel.ts:119-122`、`src/sessionPanels.ts:13-15,45,95`、`src/extension.ts:135,145`；`vscode.window.tabGroups` 的可用性已在 `node_modules/@types/vscode/index.d.ts:19377-19421` 核实。
- ⚠️ **顺带发现的一个隐患**：`package.json` 的 `engines.vscode` 是 `^1.90.0`，而 `devDependencies` 的 `@types/vscode` 是 `^1.125.0`。**编译期类型比引擎下限新**，意味着用到高版本 API 时 `tsc` 不会报错，但 1.90 用户会运行时报错。建议把 `@types/vscode` 降到与 `engines` 匹配（如 `^1.90.0`），或明确抬高 `engines` —— 这件事**应该在 A 档动手前先定**。
