# 官方 DSH 0.1.6-alpha 差距分析与升级（upstream-016-gap）— 需求（req）

**日期**: 2026-09-18
**来源**: 用户 2026-09-18 直接需求（同日已确认**比对轴**与**读者口径**，见 §3 D1/D2）
**状态**: ⏳ 待用户批准

> 本文件只定义 **做什么（WHAT）** 与 **验收标准**，不含实现细节（HOW）。

---

## 0. 审题（问题界定卡）

| 项 | 内容 |
|---|---|
| **一句话问题陈述** | 官方 `@deepseek-ai/dsh` 已经发布了比我们在用的更新的版本，但我们**没有任何一份从用户视角写清楚的"差了什么"**，也没有一条**下次还能照着走**的升级路径——所以用户升级与否只能靠猜，下一次上游发版又要从零查一遍。 |
| **比对两端**（用户已确认） | 左端「当前」= `@deepseek-ai/dsh@0.1.5-rc.2`（本机全局安装 + `dsh-baseline.json` 适配基线，2026-09-10 发布）；右端「官方最新」= `@deepseek-ai/dsh@0.1.6-alpha.2`（npm `alpha` 通道，2026-09-17 发布）。 |
| **读者**（用户已确认） | **终端用户**（升级说明 / 发布公告口径）：体感差异、功能变化、修了哪些问题、升级价值。内部实现细节只作为佐证，不作为主线。 |
| **递交物长相** | ① 一份**差距分析报告**（用户视角，可直接改写成发布公告）；② 一份**升级方案**（本次怎么升 + 下次怎么复用）；③ 本需求文档；④ 主题夹 `00-README.md` 索引。 |
| **判定标准** | 见 §6。核心两条：**每条"变了"都带官方来源**；**方案能被下一次上游发版直接复用**（不是只对 0.1.6-alpha.2 有效的一次性步骤）。 |
| **明确不做** | 不擅自把 `alpha` 通道写进适配基线；不擅自升级本机全局内核；不改扩展代码（本轮无代码交付，除非探测发现破坏面破裂——见 §4 N4）。 |

## 1. 背景

- 上游迭代极快：约一个月内走完 `0.1.0-rc.6 → 0.1.5-rc.2`，其中 3 次破坏性变更都让内嵌面板不可用（[上游兼容规范](../../02-Areas/20260914-06-上游兼容规范_跟随最新官方DSH.md)）。
- 现有机制只回答"**跟上了没有**"（`npm run check:dsh` 比对 `latest` / `next` 与基线），**不回答"跟上去能拿到什么"**——`0.1.5-rc.1/rc.2` 在时间线里只留了一句"实测通过，无需改代码"，上游到底改了什么**从未落档**（[演进时间线](../R20260914-01-演进总览/01-演进时间线.md) §「记录缺口」）。
- 2026-09-17 官方又发了 `0.1.6-alpha.2`，与我们在用的 `0.1.5-rc.2` 之间隔了 **alpha.1 + alpha.2 两个版本、7 天**的改动量，其中包含结构性变化（依赖树 520 → 488 包，新增 58 / 移除 90）。

## 2. 范围（3 项需求）

### R1 — 差距分析报告（终端用户口径）

把 `0.1.5-rc.2 → 0.1.6-alpha.2` 的差异整理成**用户能读懂**的一份报告，至少覆盖：

1. **体感/功能变化**：新增了什么用户可感知的能力、哪些交互变了；
2. **修复了什么**：用户可能踩过的问题，哪些在这一版被修掉；
3. **升级的价值与代价**：升上去能拿到什么、要付什么代价（含破坏性变更与迁移动作）；
4. **对本扩展的影响**：用户通过 VS Code 面板使用时，哪些变化看得到、哪些看不到。

**验收**：
- 报告里**每一条"变了"都带官方来源**（GitHub Release 条目或实测命令输出），不允许出现"应该是""通常"；
- 官方原文（中英双语发布说明）单独留档并可点开，报告不复制原文而是**做归类与影响判断**；
- 明确区分**「官方发布说明声称」**与**「我们实测确认」**两种可信度，未实测的必须标注；
- 至少包含一张"用户视角差异总表"（能力 / 变化 / 用户能感知到什么 / 需要做什么）。

### R2 — 升级方案（可重复，非一次性）

给出一条从当前版本升到目标版本的完整路径，且**下一次上游发版时能直接复用**。

**验收**：
- 方案覆盖完整链路：**定版本 → 停会话 → 装 → 重启 → 四破坏面核对 → 验证 → 登记 → 回滚预案**；
- 方案里的每一步都是**可执行的具体动作**（命令 / 判定口径），不是"注意一下"；
- **适配性自检**：明确指出方案中哪些地方是"绑定本次版本号的"、哪些是"结构上可复用的"，并给出下次复用时**必须重新确认的最小清单**；
- 包含**回滚预案**（回到哪个版本、怎么回、怎么验证回滚成功）；
- 明确 `alpha` 通道与 `latest`/`next` 通道在方案里的不同处理方式，并给出"要不要跟进 alpha"的决策依据（决定权在用户）。

### R3 — 需求与证据落盘

**验收**：
- 需求、差距分析、升级方案三份文档落在同一个主题夹，命名与编号符合[文档与 PARA 规范](../../02-Areas/20260914-03-文档与PARA规范.md)；
- 官方发布说明原文留档在 `03-Resources/`；
- 主题夹 `00-README.md` 说明每份文件记什么、建议阅读顺序、当前状态与未闭环项；
- `npm run check:docs` 通过。

## 3. 决策项

| # | 决策项 | 决定 | 来源 |
|---|---|---|---|
| D1 | 比对轴（哪两条版本线） | **上游官方包 `0.1.5-rc.2` → `0.1.6-alpha.2`** | 用户 2026-09-18 选择 |
| D2 | 读者口径 | **终端用户**（升级说明 / 发布公告） | 用户 2026-09-18 选择 |
| D3 | 落盘位置 | **新建 `R20260918-04-上游0.1.6-alpha差距与升级`**，不追加进 `R20260820-01-上游DSH版本适配` | 见下 |
| D4 | `alpha` 通道是否进基线 | **本轮不进**；只做分析与方案，是否跟进由用户另行决定 | 既有规范：[上游兼容规范](../../02-Areas/20260914-06-上游兼容规范_跟随最新官方DSH.md) §8「alpha 不纳入基线」 |
| D5 | 是否升级本机全局内核 | **本轮不做**；方案只写清怎么做，动作留给用户 | AGENTS.md §8 铁律：不在活跃会话上热升级 |

**D3 的理由（避免"平行开夹"）**：`R20260820-01-上游DSH版本适配` 的定位是"**上游破坏性变更的现场证据夹**"（其 `00-README.md` 自述为"历史记录 + 现场记录"），且管线槽位 `01–07` 已被"升级渠道"特性占用、`08–12` 已被三次破坏修复与两次操作事件占用。本次交付是**一个新主题的完整管线（需求 → 方案 + 证据）**，追加进去会与既有 `02-需求_升级渠道与版本门控.md` 撞语义、且无处安放管线编号。两夹分工写进本夹 `00-README.md`，并互相链接，**同一事实只维护一份**。

## 4. 非目标

| # | 项 | 原因 |
|---|---|---|
| N1 | 把 `alpha` 通道纳入 `check:dsh` 的跟踪渠道 | 规范明确 alpha 是实验通道、不作适配目标；本次只做分析（D4） |
| N2 | 实际执行本机内核升级 | 用户未要求；且热升级会打死当前会话工具链（AGENTS.md §8） |
| N3 | 写一份"官方发布说明的中文翻译" | 官方发布说明**本来就是中英双语**，翻译无增量；要做的是**归类 + 影响判断** |
| N4 | 改扩展代码 | 本轮是调查与方案。**例外**：若真机探测发现四破坏面破裂，则按[缺陷修复记录规范](../../02-Areas/20260914-05-缺陷修复记录规范.md)另开修复记录，并回到本需求补范围 |
| N5 | 覆盖 `0.1.2-rc.1 → 0.1.5-rc.2` 的历史缺口 | 那是另一条轴（用户本次未选），登记为后续可选项 |

## 5. 约束

- **C1 事实优先**：现状/差距/协议类结论必须带来源——官方条目给 URL，实测给命令与输出关键行；**没读过的不写结论，没测过的不写事实**（[文档与 PARA 规范](../../02-Areas/20260914-03-文档与PARA规范.md) §2）。
- **C2 不弱化既有围栏**：分析与方案不得建议弱化 DSH 的 `/api` 信任围栏、不得建议 `--host 0.0.0.0`（AGENTS.md §7）。
- **C3 不制造第二份真源**：适配基线仍以 `docs/02-Areas/dsh-baseline.json` 为唯一机器可读源；本夹不复制它。
- **C4 探测隔离**：任何"装新版本实测"必须在**隔离目录**进行，不得碰全局那棵 dsh 树、不得用真实 `~/.dsh`（AGENTS.md §8）。
- **C5 文档门禁**：改完 `docs/` 必须跑 `npm run check:docs`。

## 6. 验收总则

- **完成 = R1 + R2 + R3 全部验收通过**。
- 差距分析必须能回答用户问的四个问题：**哪里不一样 / 问题在哪 / 哪些功能变了 / 升级有什么价值和好处**。
- 升级方案的**适配性**以"下一次上游发版时，执行者是否需要重新思考流程"为判据：若仍需重新设计流程，则方案不合格。
- 未实测项必须在文档中显式登记为"待验证"，不得以推测充当结论。
