## 0. Goal

一条**可重复执行**的升级路径，同时满足两条：

1. **风险前移**：在**动全局那棵树之前**，就能判定"这次升级会不会破坏 VS Code 内嵌面板"；
2. **可复用**：下次上游发版时只需**替换一个版本号 + 重跑同一套核对**，不需要重新设计流程。

## 3. 升级操作（本次：`0.1.5-rc.2` → `0.1.6-alpha.2`）

> 命令为 **PowerShell**（本机平台）。**唯一需要改的变量是 `$TARGET`**。
> 每一步都有**判定标准**——不满足就**停**，不要往下走。

### S0 — 通道决策（先想清楚再动手）

| 通道 | 含义 | `check:dsh` 是否跟踪 | 本次 |
|---|---|---|---|
| `latest` / `next` | 官方稳定承诺区 | ✅ 跟踪（`TRACKED_CHANNELS`） | 当前都还指向 `0.1.5-rc.2` |
| **`alpha`** | **官方实验通道**，不保证向后兼容 | ❌ **不跟踪** | **本次目标在这里**（`0.1.6-alpha.2`） |

**必须先接受两个后果**：
1. 升到 alpha 后，`npm run check:dsh` **仍会报"已跟到上游最新"**——这是**设计如此，不是 bug**（基线只看 `latest`/`next`）。你的实际安装会**跑在兼容矩阵之外**。
2. 官方可能在下一个 alpha 里再改一次；`alpha` 不属于任何稳定承诺。

> 想稳定 → 停在 `0.1.5-rc.2`，等 `0.1.6-*` 进 `next`/`latest` 再升。**这个决定权在用户**（见 §4.3）。

### S1 — 定版本（显式版本号，禁止浮动 tag）

```powershell
$TARGET = "0.1.6-alpha.2"                     # ← 下次升级只改这一行

npm view @deepseek-ai/dsh dist-tags           # 三个通道现在各指向谁
npm view "@deepseek-ai/dsh@$TARGET" version   # 确认该版本真实存在
```

**判定**：第二条回显等于 `$TARGET`。**禁止**用 `@latest` / `@next` 这类浮动 tag（SOP §1 硬规矩 1）。

### S2 — 隔离预演（**本方案新增的关键步骤**）

目的：**不碰全局那棵树**，先把"这次升级会不会破坏内嵌"验出来。

```powershell
$PREVIEW  = Join-Path $env:TEMP "dsh-preview-$TARGET"
$PREVHOME = Join-Path $env:TEMP "dsh-preview-home"
npm install --prefix $PREVIEW "@deepseek-ai/dsh@$TARGET" --no-audit --no-fund

# 只改这两个环境变量，就能让扩展自己的代码去驱动隔离安装
$env:DSH_BIN  = Join-Path $PREVIEW "node_modules\.bin\dsh.cmd"   # Windows；macOS/Linux 去掉 .cmd
$env:DSH_HOME = $PREVHOME

node scripts\smoke.js        # 期望末行 `smoke OK: http://127.0.0.1:<port> cwd=…`，exit=0
& $env:DSH_BIN --version     # 期望回显 $TARGET
& $env:DSH_BIN web --help    # 期望含 --no-open / --port / --host
```

**判定**：三条全过 → 进 S3。**任一条不过 → 停在预演，不要动全局树**，按[缺陷修复记录规范](../../02-Areas/20260914-05-缺陷修复记录规范.md)另开修复记录。

**本次实测**：两个版本都 `smoke OK`、`--version` 正确、`--help` 三个 flag 齐全（`node scripts/smoke.js` 在 `DSH_BIN` 指向隔离安装时 exit=0，2026-09-18）。

**A/B 面（boot 注入形态 / dist 资产路径）在预演里怎么核**——**不需要任何扩展代码，下面这段 PowerShell 就够**（2026-09-18 在两个版本上实测跑通，`303 → 200 / 401` 与扩展自己取到的 HTML 逐字节一致）：

```powershell
# 用隔离安装的 dsh：读启动行里的 ?token= → 换 Cookie → 取扩展真正会拿到的 HTML
$out = Join-Path $env:TEMP "dsh-ab.out"; $err = Join-Path $env:TEMP "dsh-ab.err"
$p = Start-Process $env:DSH_BIN -ArgumentList "web","--port","0","--no-open" `
      -RedirectStandardOutput $out -RedirectStandardError $err -PassThru -NoNewWindow
$t = ""
for ($i = 0; $i -lt 60 -and $t -notmatch 'dsh web: \S+'; $i++) {
  Start-Sleep -Milliseconds 500; $t = Get-Content $out -Raw -ErrorAction SilentlyContinue
}
$auth = [regex]::Match($t, 'dsh web: (\S+)').Groups[1].Value   # 带 ?token=
$base = $auth.Split('/?')[0]
try {
  Invoke-WebRequest $auth -SessionVariable s -MaximumRedirection 0 -SkipHttpErrorCheck -ErrorAction SilentlyContinue | Out-Null
  $html = (Invoke-WebRequest "$base/" -WebSession $s -SkipHttpErrorCheck).Content
  $noCookie = (Invoke-WebRequest "$base/" -SkipHttpErrorCheck).StatusCode
  "A  boot globalThis=$([bool]($html -match 'globalThis\["__DSH_BOOT__"\]'))  batches=$([bool]($html -match '"batches"\s*:'))"
  "B  ./assets/=$(([regex]::Matches($html,'(src|href)="\./assets/')).Count)  /assets/=$(([regex]::Matches($html,'(src|href)="/assets/')).Count)  base=$([regex]::Match($html,'<base\s+href="([^"]*)"').Groups[1].Value)"
  "B  preloads=$(([regex]::Matches($html,'<script[^>]+src="/plugins/[^"]*"')).Count)  mux=$(([regex]::Matches($html,'/plugins/\?\?')).Count)"
  "C  GET / 无 Cookie = $noCookie（期望 401）"
} finally { taskkill /PID $p.Id /T /F | Out-Null }   # dsh.cmd 是 cmd 垫片，必须整树杀，否则留下孤儿 node
```

**本次实测的形态基准**（下次对照；**形态变了才要警觉，数值变了不算**）：

| 面 | 本次形态（两个版本一致） |
|---|---|
| A | `globalThis["__DSH_BOOT__"] =` + 含 `"batches"[]` |
| B | 相对 `./assets/…` ×4、绝对 `/assets/` ×0、`<base href="/">`、阻塞式 preload **1 个**且为 `/plugins/??@deepseek-ai/dsh-client-modules/client.js&rev=…` |
| C | 无 Cookie 取 `/` = **401**；带 Cookie = **200**（0.1.5-rc.2 = 27,660 B；0.1.6-alpha.2 = 31,188 B） |
| — | ⚠️ boot `rev` **不要比对**：上游每次服务进程启动都重新生成（实测） |

> 长期应把它固化成一条命令（§5 的 **T1**）；`npm run probe:composer`（需 `playwright`）是更强的端到端验证，但它验证的是写入面，不能替代 A/B 形态断言。

### S3 — 停会话（最容易漏、代价最大的一步）

关掉：IDE 里的 DSH 面板、终端里的 `dsh web`、DSH Desktop。然后确认没有残留：

```powershell
Get-CimInstance Win32_Process -Filter "Name='node.exe'" |
  Where-Object { $_.CommandLine -match 'dsh' } |
  Select-Object ProcessId, CommandLine
```

**判定**：输出**为空**才继续。非空 → 先关掉那些进程，否则 S4 会撞上 SOP §4 的 `EPERM`/`EBUSY` **半装树**（JS 包装是新版、原生二进制还是旧版 → 之后每次 `dsh web` 启动即退码 1）。

### S4 — 安装（显式版本，看退出码）

```powershell
npm i -g "@deepseek-ai/dsh@$TARGET"
"exit=$LASTEXITCODE"
```

**判定**：**退出码必须为 0**。不要只看"版本号变了"（SOP §4 教训 5：npm 可能写出了新 `package.json` 却以 `EBUSY` 失败退出）。出现 `npm warn cleanup EPERM/EBUSY` → **停**，回 S3 清进程后重装。

### S5 — 原生一致性自检（SOP §4.1 原样照跑）

```powershell
$dsh = "$env:APPDATA\npm\node_modules\@deepseek-ai\dsh"
node -e "const p=process.argv[1];const {createRequire}=require('node:module');const r=createRequire(p+'/node_modules/koffi/src/koffi/src/static.js');console.log('koffi pkg :',require(p+'/node_modules/koffi/package.json').version);console.log('koffi native:',r('@koromix/koffi-win32-x64').version)" $dsh

dsh web --port 0 --no-open      # 期望打印 `dsh web: http://127.0.0.1:<port>/?token=…`
```

**判定**：koffi 两行版本号**相同**，且启动行打印出来。⚠️ `dsh --version` / `dsh web --help` **不算数**——它们不加载插件树，半装树照样正常。

### S6 — 重启内核 + 四破坏面核对

重开 DSH 面板 / 会话（**新进程 = 新树**，旧进程不会自动切换）。然后逐面对照 §1.3 的**形态**（看形态，不是看数值）：

| 面 | 判据（形态） | 本次实测 |
|---|---|---|
| **A** boot 注入 | 前缀是 `window.` 还是 `globalThis[…]`；是否含 `batches[]` | `globalThis["__DSH_BOOT__"]` + `batches[]` ✅ |
| **B** dist 资产 | 绝对 `/assets/` 还是相对 `./assets/` + `<base href>`；阻塞式 preload 与 mux 形态 | 相对 + `<base href="/">` + `/plugins/??…&rev=` ✅ |
| **C** `/api` 认证与 RPC | 无 Cookie 是否 401；带 Cookie 是否 200；`session/list`、`session/create` 是否可用；WS 升级是否也要 Cookie | 401 / 200 / 可用 / 需要 ✅ |
| **D** CLI 与输出 | `--no-open` 在不在；启动行是否仍带 `?token=` | 在；带 ✅ |

**判定**：形态全同 → **无需改代码**；任一形态变了 → 按 SOP §2 与[上游兼容规范](../../02-Areas/20260914-06-上游兼容规范_跟随最新官方DSH.md)开修复记录，**并补一条锁定该形态的回归单测**。

> ⚠️ **不要用报错文案判断根因**：历史上三次事故报错都是 "Failed to load plugins"，根因完全不同。

## 4. 适配性设计（"下次还能用"靠的是这一节）

### 4.1 不变量 / 变量

| 类别 | 内容 | 下次升级 |
|---|---|---|
| **结构不变量** | S0→S9 的步骤与顺序；"隔离预演 → 停会话 → 装 → 自检 → 重启 → 四面 → 验证 → 登记 → 回滚"这条链；四个破坏面的**定义**；三条禁忌（不停会话不装、不看退出码不算成功、不在活跃会话上热升级） | **不改**——这就是可复用的部分 |
| **每版只变一个参数** | `$TARGET`（版本号）；`$PREVIEW` / `$PREVHOME` 路径 | 改一行 |
| **每版必须重新确认** | 四破坏面的**形态**；baseline `fragilePoints` 的 token；`--help` 的 flag 集；启动行格式 | 重跑 S2/S6 |
| **会过期、只当基准** | §1.3 里的实测数值（包数、耗时、占用） | **不当永久事实**，只当"上一次的基准" |
| **明确不可比对** | boot `rev` —— 上游每次服务进程启动都重新生成 | **不要把它写进任何基线**（本文档早期草稿曾误当版本指纹，已更正） |

### 4.2 下次复用的最小重确认清单（7 条）

1. `npm view @deepseek-ai/dsh dist-tags` —— 是哪个通道动了
2. 读新版本的官方 Release 说明（**Releases 就是 changelog，仓库里没有 `CHANGELOG.md`**）
3. S2 隔离预演的三条命令是否全过
4. 四破坏面形态是否与 §1.3 一致
5. baseline `fragilePoints` 的 token 是否都还在
6. 启动耗时与磁盘占用是否可接受
7. 有没有新的破坏性变更需要通知用户

> 这份清单就是"复用时**必须**重新确认的最小集"。清单之外的步骤可以照着走，不用重新思考。

### 4.3 什么时候必须停下来问人（不要自己决定）

| 情形 | 为什么不能自己定 |
|---|---|
| 四破坏面**有面破了** | 要改代码，超出"升级"范围，走缺陷修复流程 |
| 目标版本在 **`alpha`** 通道 | 是否跟进 alpha 是**产品决策**（稳定性 vs 新功能） |
| 依赖体积/磁盘显著上涨（本次 **+325 MiB**） | 值不值得，用户定 |
| 出现**影响既有用户**的破坏性变更 | 是否接受、要不要发公告，用户定 |
