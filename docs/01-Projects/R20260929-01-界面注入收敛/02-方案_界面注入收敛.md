# 方案：界面注入收敛

**日期**: 2026-09-29 ｜ **状态**: 当前
**来源**: [01-需求_界面注入收敛.md](01-需求_界面注入收敛.md)
**定位**: 回答「怎么做」。以下每一句"改为 xxx"都由 §2 核实过的代码/实测事实支撑。

---

## 1. Goal

本扩展往 IDE 界面注入的每一处，都要满足两条：**用户能关**、**不与 IDE 自带界面混淆**；
容器 id 一旦发布就被冻结，改名必须先想清楚旧 pin 的去处。

## 2. Facts（读源码与实测得到的事实）

**F1 · 活动栏孤儿 pin 无程序化解法。**
用户机器 `%APPDATA%\Code\User\globalStorage\state.vscdb` 实测：

```text
workbench.activity.placeholderViewlets：
  workbench.view.extension.deepseek-harness  有 iconUrl
  workbench.view.extension.dsh               无 iconUrl   <- 旧容器 id
  workbench.view.extension.dsh-panel         无 iconUrl   <- 旧容器 id
workbench.activity.pinnedViewlets2：以上三条全部 pinned:true
```

VS Code 1.105.1 的 `resources/app/out/vs/workbench/workbench.desktop.main.js` 全文检索：

| 命令 id | 命中 |
|---|---|
| `workbench.action.pinView` | 0 |
| `workbench.action.unpinView` | 0 |
| `removePinnedViewlet` | 0 |
| `workbench.action.resetViewLocations` | 1 |

→ **扩展没有任何公开 API 能移除一条已 pin 的容器**；能命中的 `resetViewLocations` 会连带重置用户其它视图定制，不能替用户做主调用。
→ 这是 VS Code 的**设计行为**：不认识但被 pin 过的容器被保留为 placeholder，以便扩展装回来时 pin 还在。

**F2 · 投放条无条件常驻。**
`package.json:158-165` 把 `deepseek-harness.contextDrop` 贡献进内置 `explorer` 容器，**没有 `when`**。
`src/extension.ts:201` 无条件注册：

```ts
context.subscriptions.push(new ContextDropView(addUrisToContext).register());
```

`src/contextDropView.ts:57` 用 `vscode.window.createTreeView(ContextDropView.viewId, …)` 创建，`viewId` 见 `src/contextDropView.ts:46`。
`createTreeView` 的前置条件是「视图 id 已被 `contributes.views` 声明」；`when` 只影响布局，不影响声明，所以**加 `when` 不需要改任何调用点**。

**F3 · 两个容器同名同图标。**
`package.json:127-141`：

```json
"activitybar":      [{ "id": "deepseek-harness",      "title": "DeepSeek Harness", "icon": "media/icon.svg" }],
"secondarySidebar": [{ "id": "deepseek-harness-chat", "title": "DeepSeek Harness", "icon": "media/icon.svg" }]
```

容器 **id** 的既有依赖：`src/openTarget.ts:50` `CHAT_VIEW_CONTAINER = "deepseek-harness-chat"` 与 `test/openTarget.test.js:59-77` 的契约用例。二者依赖的是 **id**，不是 `title`/`icon`，因此改标题与图标不触碰这两处。

**F4 · 已有机器兜底的先例。**
`test/openTarget.test.js` 已经在读 `package.json` 做贡献点契约断言（`openTarget.test.js:59-77`），容器 id 的冻结检查放同一模式即可，不需要新机制。

**F5 · 打包与装机路径。**
`scripts/package.js:16` 用 `pkg.publisher.pkg.name-pkg.version` 命名产物，`:20` 先清空 `dist/`，`:41-44` 校验产物恰好 1 份。
`scripts/install-local.js:41-67` 内置 VS Code 与 Cursor 两套 CLI 候选路径，`:119` 用 `--install-extension … --force` 安装。
`package.json:23-34` 的 `files` 白名单含 `media/**`，新增图标会被打进包。

## 3. Gap（要解决的问题就是这些差集）

| 需求 | Goal | 现状 | 差集 |
|---|---|---|---|
| R1 | 活动栏无本扩展产生的无图标条目 | 两个旧容器 id 的 pin 变成无图标 placeholder | **代码无法消除**；只能防复发 + 给用户可执行步骤 |
| R2 | 投放条可关 | 无开关、无 `when` | `configuration` 加一项 + `views.explorer` 加 `when` |
| R3 | 两容器可区分 | `title`/`icon` 完全相同 | 改 `title`，`secondarySidebar` 换独立图标 |
| R4 | 不复发 | 容器 id 改名无任何机器检查 | 新增契约用例锁死 id 集合 |

## 4. Call-site Audit（改契约的调用点逐条核对）

本轮**不改变任何已导出函数的签名或返回语义**，新增的只有 `package.json` 贡献点与一个测试文件。逐条核对受影响处：

| 位置 | 是否冲突 | 判定 |
|---|---|---|
| `src/extension.ts:201`（注册投放条） | 否 | 加 `when` 不改变"视图已被声明"这一前置条件 |
| `src/openTarget.ts:50`（容器 id 常量） | 否 | 只改 `title`/`icon`，id 不动 |
| `test/openTarget.test.js:59-77`（id 契约） | 否 | 断言的 id 不变 |
| `package.json:158-165`（explorer 视图） | 否 | 只加 `when` 字段 |
| `src/contextDropView.ts`（视图实现） | 否 | 不改 |

无冲突项，可进入任务清单。

## 6. 风险与否决项

| 项 | 处置 |
|---|---|
| 改 `when` 导致投放条在 `false` 时仍尝试创建 TreeView 而报错 | 判为**不成立**：视图仍被 `contributes.views` 声明，`createTreeView` 只要求"已声明"。若实测报错，回退方案是改在 `activate()` 里按配置条件注册 |
| 换次级侧边栏图标影响老用户识别 | 可接受：该图标本来就与活动栏那个完全相同，区分是本次目的 |
| 投放条默认关 | **否决**。会让已在用该入口的用户受损，违反 `AGENTS.md` §7.1 对内原则 |
| 用私有存储清 pin | **否决**（N2），越界且不受支持 |
