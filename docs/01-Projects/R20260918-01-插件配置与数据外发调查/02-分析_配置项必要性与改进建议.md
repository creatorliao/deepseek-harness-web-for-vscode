# 分析：配置项必要性与改进建议

**日期**: 2026-09-18 ｜ **状态**: 当前
**定位**: 回答"哪些配置有必要、哪些没必要"，并给出**该补什么、不该加什么**的具体建议（含取舍与反方意见）。

---

## 1. 评估口径（先说判据，避免拍脑袋）

一个设置项该不该存在，用四条判据：

| 判据 | 说明 |
|---|---|
| **A 不可替代性** | 没有它，用户是否有**别的路径**达成同一目标？（能用命令/环境变量替代的，必要性下降） |
| **B 默认安全** | 不填 / 留空 / 非法值时，是否仍能正常工作且不静默走错路？ |
| **C 语义诚实** | 设置生效范围是否与它的描述一致？（**"看起来能关、实际关不掉"比没有这个设置更糟**） |
| **D 维护成本** | 是否引入新的上游契约依赖或额外分支？ |

## 2. 逐项结论

| 配置项 | 结论 | 依据 |
|---|---|---|
| `dshPath` | **必要，保留原样** | A 自动探测有真实失败模式；B 留空=安全默认；C 语义诚实；D 成本≈0 |
| `openTarget` | **有价值，保留**（属"可省但便宜"） | A 命令可替代但每次要手点；B 非法值回落默认；C 一致；D 成本≈0 |
| `themeSync` | **建议整改，不建议直接删** | C **不成立**：`off` 关不掉 `matchMedia` shim（证据见 [01 §3.1](01-分析_配置项清单与含义.md)） |

**一句话回答用户的问题**：**没有任何一项是纯粹的冗余**——三项各有其位；真正的问题是 `themeSync` 的**实现只做了一半**，让一个合理的开关变成了半失效开关。

### 2.1 `dshPath` —— 必要

**为什么不可替代**：自动探测（`src/serverManager.ts:361-374`）覆盖的是"标准安装"，以下场景它必然选错或选不到：

- 同时装了多个 dsh（nvm 多 node 版本、npx 缓存里躺着旧版）——探测按固定顺序取**第一个存在**的（`firstExisting`），未必是用户想要的那个；
- 企业内部镜像 / 私有目录 / 便携版安装；
- `$DSH_BIN` 之外的自定义布局。

**为什么安全**：留空即回到自动探测（`src/commands.ts:19-23`），不需要用户理解探测顺序就能用。

**为什么语义诚实**：配错路径**不会静默**——`ENOENT` 时会指名报错：`dsh not found at the configured path "<路径>" — check the deepseekHarness.dshPath setting`（`src/serverManager.ts:550-556`）。

**反方意见（我考虑过的删掉理由）**：既然探测已经有 7 类候选，是不是可以只留 `$DSH_BIN` 环境变量？——不行：环境变量在 IDE 里**不可按工作区设置**，而"这个项目用这个 dsh"恰恰是工作区级诉求；且要求用户改 VS Code 的启动环境才能用 DSH，门槛明显更高。**保留。**

### 2.2 `openTarget` —— 有价值，保留

**为什么不算"没必要"**：它管的是**默认落点**——没有它，"每次启动都要手动点一次形态按钮"就变成固定成本；两个命令（`openChatView` / `openPanel`）能表达"这一次开在哪"，但**无法表达"以后默认开在哪"**（`src/extension.ts:84-87` 是唯一自动路由点）。

**为什么便宜**：枚举两值、非法值回落默认、不引入上游契约。判据 D 成本≈0。

**反方意见**：若目标是"设置项越少越好"，删掉它、只保留两个命令是**可接受的简化**——代价是所有用户都要多点一次按钮，且失去"像 Cursor 一样默认在右侧"的开箱体验（这正是产品定位的一部分，见 [README.md](../../../README.md)）。**结论：保留。**

### 2.3 `themeSync` —— 建议整改（P1）

**问题重述**：`off` 时扩展停止写 DSH 的 `ui-theme.preference`（`src/themeSync.ts:18-19`），但**页面仍被另外两条无条件通道强制跟随 VS Code 主题**：`bridge.dark` 注入（`src/documentAssembly.ts:236` → `media/bridge-client.js:71`）与 `theme-preference` 推送（`src/dshPanel.ts:47-53`、`src/chatView.ts:55`）。判据 C **不成立**。

**两条整改路线，先摆取舍**：

| 路线 | 做法 | 收益 | 代价 |
|---|---|---|---|
| **(a) 补齐语义** | `off` 时：① 不再推送 `theme-preference`；② 组装文档时**不注入** `dark`（`documentAssembly.ts:236` 已经支持 `themeDark === undefined` 就不注入，改动点只在两个调用方 `src/dshPanel.ts:179`、`src/chatView.ts:174` 读一次设置） | 保留"尊重 DSH 自身外观设置"的能力 | 需要一次真机验证（见下） |
| **(b) 删除设置** | 改为永远跟随 VS Code，移除该配置项 | 少一个设置、少一处分支 | 砍掉真实诉求；属**破坏性变更**（老用户设置失效），需进 CHANGELOG |

**推荐 (a)**，理由：诉求真实（有人希望面板跟 DSH 自己的主题走），且改动面小、默认行为不变（`follow` 仍是默认）。

**⚠️ (a) 有一个必须先验证的前提**：VS Code webview 自身的 `prefers-color-scheme` 是否**天然跟随**编辑器主题。若天然跟随，则不注入 `dark` 也依然会跟随，**(a) 就达不成目标，只能走 (b)**。这属于 VS Code 侧契约，**本轮未实测**，落地前必须用真机探针确认（可复用 `npm run probe:composer` 的 playwright 手法，读页面里 `matchMedia("(prefers-color-scheme: dark)").matches`）。

**若走 (a)/(b)，必须同步**：`package.nls.json:8` 的描述、[README.md](../../../README.md) §配置 的表、`CHANGELOG.md`（若属破坏性）。

## 3. 该补的开关

### 3.1 版本检查开关（P2）

**现状**：唯一的外网请求硬编码且**无法关闭**（`src/versionCheckService.ts:12-13,61`，由 `src/extension.ts:146` 在 dsh 就绪后自动触发）。

**建议**：新增 `deepseekHarness.updateCheck`（boolean，**默认 `true`**），`false` 时在 `checkForUpdates()` 入口直接返回。

**取舍与反方意见**：
- 支持方：企业/离线/审计环境需要"零外联"的可证明状态；现在是"无法关闭"。
- 反对方：这个请求是**上游跟随生存线**的支撑（[AGENTS.md](../../../AGENTS.md) §8：本项目产品定义就是跟随上游），关掉它会让部分用户长期看不到升级提示。默认 `true` 已保证行为不变，因此**净收益为正**。
- 替代方案（不加设置）：靠防火墙/hosts 屏蔽 `registry.npmjs.org`。可行但对用户不友好，且用户无从知晓这个请求的存在。

### 3.2 内核遥测开关的透传（P2）

**现状**：dsh 内核**默认挂载** OTel 会话遥测（`dsh-base/cordis.patch.yml:184-197`，`mode: FEEDBACK_ONLY`），唯一关闭方式是环境变量 `DSH_TELEMETRY_DISABLED`（任意非空值即禁用，`profile-boot-Dk-7KqJc.js:174-190`）。扩展 spawn 时只是 `env = {...process.env}`（`src/serverManager.ts:495-496`）——**用户无法在 IDE 内关闭**。细节见 [03-分析_数据外发与网络边界.md](03-分析_数据外发与网络边界.md) §5。

**建议**：新增 `deepseekHarness.dshTelemetry`，取值 `inherit`（**默认**，不设任何环境变量）/ `off`（设 `DSH_TELEMETRY_DISABLED=1`）。

**取舍与反方意见**：
- 默认必须是 `inherit`：**不要擅自默认关闭**——那会让上游失去改进依据，也可能与其产品预期冲突；本插件的职责是"不新增外发、把选择权交给用户"，不是替上游改默认。
- 命名与语义必须跟随上游：环境变量是"任意非空值即禁用"，包括 `"0"` / `"false"`，实现时**不要**写成 `if (value === "1")`。
- 这一项与"是否外发"直接相关，对**企业用户**的优先级可提到 P1。

## 4. 不该加的配置（反面清单）

这一节比"该加什么"更重要——[AGENTS.md](../../../AGENTS.md) §2 明确"不加没被要求的可配置性"。

| 候选 | 为什么不加 |
|---|---|
| **端口**（`--port`） | 现在是 `--port 0` 由 OS 分配（`src/serverManager.ts:498`）。让用户指定端口会引入冲突、多实例互踩与暴露面，收益为负 |
| **监听地址 / `--host`** | [AGENTS.md](../../../AGENTS.md) §7 安全约束明确禁止 `--host 0.0.0.0`。开放成设置等于把安全基线做成可选项 |
| **`extraArgs`（任意 CLI 参数透传）** | 会把内部契约暴露成公共 API。上游 flag 一个月内变过数次（[dsh-baseline.json](../../02-Areas/dsh-baseline.json) 记录 3 次破坏性变更），透传出错时表现为"面板白屏"这类难查故障 |
| **`dshHome`** | 改动它会**分裂会话与凭据**（多份 `~/.dsh` 状态），风险远大于收益；多工作区共用一个家目录本就是预期行为 |
| **`readyTimeoutMs`** | 调大只在慢机器上掩盖症状；真问题是启动失败，应该看到报错而不是等更久 |
| **CSP / 桥的开关**（"允许跨源"之类） | 那是围栏本身，不是配置项 |
| **主题同步的更多取值**（如 `light` / `dark` 强制） | 问题是 `off` 的实现不完整，不是取值不够；先把语义修诚实 |

## 5. 建议动作汇总

| 编号 | 动作 | 优先级 | 触及文件 | 破坏性 |
|---|---|---|---|---|
| **C1** | `themeSync` 语义补齐（或按验证结果改为删除该设置） | **P1** | `src/dshPanel.ts`、`src/chatView.ts`、`src/dshUi.ts`、`package.nls.json`、`README.md` | 无（默认 `follow` 行为不变） |
| **C2** | 新增 `deepseekHarness.updateCheck`（默认 `true`） | P2 | `src/versionCheckService.ts`、`src/extension.ts`、`package.json`、`package.nls.json`、`README.md` | 无 |
| **C3** | 新增 `deepseekHarness.dshTelemetry`（`inherit` 默认 / `off`） | P2（企业可提 P1） | `src/serverManager.ts`、`src/commands.ts`、`package.json`、`package.nls.json`、`README.md` | 无 |
| **C4** | `relayHttp` 增加 URL 校验（见 [03 §4.2](03-分析_数据外发与网络边界.md)） | P2 | `src/bridgeCore.ts` | 无 |
| — | `dshPath` / `openTarget` 保持原样 | — | — | — |

> 落地任一项前按 [特性管线规范](../../02-Areas/20260914-04-特性管线规范.md) 走门禁；`package.json` 的配置增删**必须**同步 `package.nls.json` 与 `README.md` / `README.en.md` 的配置表。
