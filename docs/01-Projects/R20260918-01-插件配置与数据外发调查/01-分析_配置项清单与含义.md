# 分析：配置项清单与含义

**日期**: 2026-09-18 ｜ **状态**: 当前
**定位**: 把本扩展**全部**配置项一次列清——类型、默认、读取点、生效路径，以及每项**管不到什么**（边界往往比功能更重要）。

> 用户面向的表述在 [README.md](../../../README.md) §配置；本文件是**带代码来源**的同一份清单，用于判断行为与取舍。两者定位不同，不互为副本。

---

## 1. 结论速览

- `contributes.configuration` 只声明了 **3 个**设置（`package.json:84-111`），全部是 `string` 类型，其中 2 个是枚举。
- 三项**都没有声明 `scope`**（`package.json:84-111`）。按 VS Code 扩展清单契约，未声明时默认作用域是 `window`——即**用户级与工作区级都能覆盖**，工作区级会写进 `.vscode/settings.json` 并影响该工作区的所有窗口。
- 三项的读取点各自**只有一处**（`themeSync` / `dshPath` / `openTarget` 各一），因此不存在"设置在一部分路径生效、另一部分被忽略"的历史问题（这条曾是本项目的真实缺陷类型，见 [AGENTS.md](../../../AGENTS.md) §7）。
- 真正影响行为的旋钮远多于 3 个：命令、快捷键、视图容器、**环境变量**都在其中，但它们**不是设置**（§4）。

## 2. 完整清单

| 键 | 类型 / 取值 | 默认 | 读取点 | 一句话含义 |
|---|---|---|---|---|
| `deepseekHarness.themeSync` | string，枚举 `follow` \| `off` | `follow` | `src/themeSync.ts:18-19` | 是否把 VS Code 颜色主题写进 DSH 的 `ui-theme` 设置 |
| `deepseekHarness.dshPath` | string（可空） | `""` | `src/commands.ts:20-22` | 手工指定 `dsh` 可执行文件；留空=自动探测 |
| `deepseekHarness.openTarget` | string，枚举 `sidebar` \| `editorTab` | `sidebar` | `src/extension.ts:56-59` | "自动打开"时 DSH 界面落在次级侧边栏还是编辑器标签页 |

清单定义：`package.json:87-109`；描述文案：`package.nls.json:8-10`（注意 `themeSync` 用 `description` 纯文本，另两项用 `markdownDescription`）。

## 3. 逐项详解

### 3.1 `themeSync`（主题同步）

**它做什么**：`syncNow()` 向本机 dsh 发一条 RPC——`POST {serverBase}/api/settings.update`，body 为 `{type:"client-request", method:"settings.update", payload:{ns:"ui-theme", patch:{preference}}}`，`preference` 取 `dark` / `light`（`src/themeSync.ts:15-35`）。值不是 `follow` 时**直接 return，不发这条 RPC**（`src/themeSync.ts:18-19`）。

**何时触发**：① 编辑器主题变化时（`src/themeSync.ts:43-46`）；② 服务器进入 `ready` 时（`src/extension.ts:117`，且**排在打开面板之前**，让页面首屏就是正确配色）。

**它管不到什么（关键）**：内嵌页面里**真正决定深浅色的还有第二条通道**，而这条通道**不受本设置控制**：

| 通道 | 代码 | 是否受 `themeSync` 控制 |
|---|---|---|
| `ui-theme.preference`（DSH 自身设置） | `src/themeSync.ts:22-31` | ✅ 受控 |
| `matchMedia("(prefers-color-scheme: dark)")` shim 的初值 `bridge.dark` | `src/documentAssembly.ts:236` 注入、`media/bridge-client.js:71` 采用 | ❌ **不受控** |
| 主题变化时的 `theme-preference` 推送 | `src/dshPanel.ts:47-53`、`src/chatView.ts:55` | ❌ **不受控** |

三条路径都无条件执行（`isDarkTheme()` 的调用点在 `src/dshPanel.ts:179`、`src/chatView.ts:174`，均未读设置）。

**用户可见后果**：把 `themeSync` 设为 `off` 后，**内嵌 UI 仍会跟随 VS Code 的深浅色**。`off` 只停止了"写 DSH 设置"这一个副作用，看起来像一个不起作用的开关。这不是"文档没写清"，而是**开关语义与实现不一致**，处置建议见 [02-分析_配置项必要性与改进建议.md](02-分析_配置项必要性与改进建议.md) §3.1。

### 3.2 `dshPath`（可执行文件路径）

**它做什么**：`configuredDshPath()` 读取并 `trim()`；**空白等同于未配置**（返回 `undefined`），于是清空设置即可恢复自动探测，而不会去 spawn 一个空字符串（`src/commands.ts:19-23`）。

**怎么生效**：经 `dshStartOptions()` 汇成唯一一份启动参数（`src/commands.ts:30-33`），被**每一条**启动路径复用——命令面板（`src/commands.ts:69`）、重载自动重启（`src/extension.ts:154`）、编辑器面板内的启动按钮（`src/dshPanel.ts:96`）、侧边栏视图（`src/chatView.ts:76`）、启动器两个按钮（`src/launcherView.ts:483,539`）。

**优先级**：`opts.dshBin ?? resolveDshPath().path ?? "dsh"`（`src/serverManager.ts:461-462`）——**配置值优先于探测结果**。

**自动探测顺序**（`src/serverManager.ts:361-374`）：`$DSH_BIN` → `npm prefix -g` 的 bin → `/opt/homebrew/bin`（非 Windows）→ `/usr/local/bin`（非 Windows）→ `~/.npm-global/bin` → `~/.nvm/versions/node/*/bin`（非 Windows）→ npx 缓存（Windows 在 `%LocalAppData%\npm-cache\_npx`，其他平台在 `~/.npm/_npx`）。

**一个容易误解的点**：即使配置了 `dshPath`，`start()` **仍会执行 `resolveDshPath()`**（`src/serverManager.ts:461`）。它的结果只用于日志与失败文案（`src/serverManager.ts:473,554`），**不会**覆盖配置值——所以这只是几十次 `existsSync` 的无害开销，不是 bug。

**配套硬门**：低于 `MIN_DSH_VERSION = "0.1.2-rc.1"`（`src/serverManager.ts:92`）的 dsh 会被**拒绝启动**并给出升级提示（`src/serverManager.ts:479-485`）。这个门与设置无关，配错路径也会走到这条判断。

### 3.3 `openTarget`（默认打开位置）

**它做什么**：`resolveOpenTarget()` 只认 `"sidebar"` / `"editorTab"`，**任何无法识别的值（含旧工作区设置里的 `undefined`）都回落到默认值**而不是抛错（`src/openTarget.ts:45-47`）——"坏设置绝不能让界面打不开"是这里写明的设计意图。

**唯一的自动路由点**：`openUi()`（`src/extension.ts:84-87`）。`sidebar` → 次级侧边栏视图；`editorTab` → 右侧编辑器组（`columnForRightSide()` 保证落在最右，`src/openTarget.ts:30-33`）。

**生效时机**：启动命令、状态栏、点击会话、重载后的自动恢复（`src/extension.ts:111-142`）。

**它管不到什么**：启动器面板里的两个按钮（"在侧边栏打开" / "在编辑器标签页打开"）走**显式**回调，不读本设置（`src/extension.ts:232`）；命令 `openChatView` / `openPanel` 同理（`src/commands.ts:91-96`）。这是有意的：设置只决定"默认落点"，不限制用户随时切形态。

**一个容错细节**：侧边栏可能被主题或布局藏起来，此时 `chatView.show()` 返回不可见，扩展会**弹中文警告并回落到编辑器标签页**，而不是静默无反应（`src/extension.ts:71-79`）。

## 4. 非设置类旋钮（容易被当成"配置"的东西）

| 旋钮 | 位置 | 作用 |
|---|---|---|
| 6 个命令 | `package.json:36-67` | start / stop / openBrowser / openChatView / openPanel / addToContext |
| 快捷键 `ctrl+alt+a`（mac `cmd+alt+a`） | `package.json:76-83` | 把当前文件作为 `@` 引用加入 composer |
| 资源管理器右键菜单 | `package.json:68-75` | 同上（支持多选，是拖拽路径的兜底入口） |
| 两个视图容器 | `package.json:112-143` | 活动栏 `deepseek-harness` + 次级侧边栏 `deepseek-harness-chat` |
| `$DSH_BIN` | `src/serverManager.ts:362` | 自动探测的**首位**候选，优先级低于 `dshPath` 设置、高于其他候选 |
| `$DSH_HOME` | `src/serverManager.ts:495-496`（`opts.dshHome`） | 内核家目录；**扩展没有从设置里传入**，因此只能由启动 VS Code 的环境决定 |
| `$DSH_TELEMETRY_*` | 上游 `dsh-base/cordis.patch.yml:187-190` | 内核遥测开关；**扩展不设置、也不透传**（详见 [03-分析_数据外发与网络边界.md](03-分析_数据外发与网络边界.md) §5） |
| VS Code `telemetry.telemetryLevel` | 全仓 grep 无匹配 | 本扩展**不读取**该设置，也不上报使用数据 |

## 5. 代码里存在、但没有设置入口的参数

这些是 `DshServerManager` 的启动选项，**目前只有内部调用方能传**，用户无法从设置影响：

| 参数 | 位置 | 现状 |
|---|---|---|
| `dshBin` | `src/serverManager.ts:462` | 由 `dshPath` 设置提供（唯一有入口的） |
| `dshHome` | `src/serverManager.ts:496` | 无入口（设置 `env.DSH_HOME`） |
| `extraArgs` | `src/serverManager.ts:507` | 无入口（追加 CLI 参数） |
| `readyTimeoutMs` | `src/serverManager.ts:464` | 无入口（就绪超时） |
| `cwd` | `src/serverManager.ts:463` | 由 `workspaceRoot()` 固定提供：第一个工作区文件夹，无文件夹时用 `os.homedir()`（`src/commands.ts:10-12`） |

要不要给这些开设置口，见 [02-分析_配置项必要性与改进建议.md](02-分析_配置项必要性与改进建议.md) §5（结论：**多数不该开**）。
