# 内核随插件分发的可行性与取舍

**日期**: 2026-09-19 ｜ **状态**: 调查记录（结论已取证，未改动任何代码）
**触发问题**（用户原话）：

> 如果我们希望 harness 随着插件走，作为插件的真实依赖，这种方式是否合适？能不能做得到？
> 因为我们的目标机器有可能连 DS 这些 harness 都没有，在这种情况下，我们也希望它能够使用这个工具；当然，也不能够和它已经安装的这些 harness 发生冲突。

**取证口径**：结论一律来自**读本仓源码 / 读本机已装包内文件 / 实机命令输出**，标注来源。未读过的代码不写结论，**未实测的行为不写成事实**（本文末 §8 列出全部未验证项）。

---

## 0. 结论（先看这段）

| 问题 | 回答 |
|---|---|
| **能不能做到？** | **技术上做得到**，但有三个硬约束绕不开：**体积**（222.6 MiB / 25,471 文件）、**平台**（原生件只装当前平台，单一 vsix 只能覆盖一个平台）、**运行期自管理**（dsh 仍要在 `DSH_HOME` 里用 pnpm 装插件树——**"随插件走"≠"自包含"**）。 |
| **是否合适？** | **取决于你到底要解决哪个问题**。若只要"没装 DSH 的机器也能用" → 有比打包更便宜的做法；若要求"完全离线可用" → 只有打包能做到。 |
| **最难的其实不是打包** | 是"**不与已安装的冲突**"。本机实测发现：`$DSH_HOME/profiles/node_modules` 是一张**跨安装源的 junction 池**，同时链到 npm 全局、DSH Desktop、pnpm 全局、甚至一个开发 checkout（§2）。**两个不同来源的 dsh 共用同一个 `~/.dsh`，会互相改写这棵树的链接。** |

**一句话建议**：**不推荐**把 dsh 塞进 vsix（方案 A/B），**推荐"无内核时按需获取 + 内置仅作兜底"**（方案 C+S1）；除非你明确需要"完全离线"，那才轮到 A/B，并需接受体积与 6 平台打包成本。

## 1. 事实：dsh 到底是什么形状

**本机实测（2026-09-19，全局 `@deepseek-ai/dsh@0.1.5-rc.2`）**：

| 项 | 值 | 怎么测的 |
|---|---|---|
| CLI 包**自身** | **48,910 B / 10 个文件** | `npm view @deepseek-ai/dsh@0.1.5-rc.2 dist.unpackedSize dist.fileCount` |
| **完整依赖树** | **222.6 MiB / 25,471 个文件** | `Get-ChildItem <全局>/@deepseek-ai/dsh -Recurse -File \| Measure-Object Length -Sum` |
| 直接依赖数 | 72 | 读包内 `package.json` |
| 树内 `@deepseek-ai/*` 包 | 239（0.1.5-rc.2 口径） | 列目录计数 |
| 入口 | `bin.dsh = lib/bin.js` | 读包内 `package.json` |
| 许可 | **MIT** | 读包内 `package.json` |

> **关键事实**：CLI 包本身只有 **48 KB**，**222.6 MiB 全在依赖树**。所以"把 dsh 作为真实依赖"= 把 **25,471 个文件**搬进 vsix，而不是搬一个包。
> 许可为 MIT，**再分发本身没有障碍**（这不构成障碍，但也不是"随便塞"的理由）。

### 1.1 原生二进制（体积与平台问题的根源）

本机树内实测（Top 6）：

| 大小 | 文件 |
|---|---|
| 17.75 MiB | `node_modules\@img\sharp-win32-x64\lib\libvips-42.dll` |
| 1.00 MiB | `node_modules\@koromix\koffi-win32-x64\win32_x64\koffi.node` |
| 0.42 MiB | `node_modules\@img\sharp-win32-x64\lib\sharp-win32-x64-0.35.4.node` |
| 0.33 MiB | `node_modules\node-addon-require-builtin-win32-x64-msvc\prebuilt\…napi-v9.node` |
| 0.32 MiB | `node_modules\@img\sharp-win32-x64\lib\libvips-cpp-8.18.6.dll` |
| 0.28 MiB | `node_modules\node-pty\prebuilds\win32-x64\conpty.node` |

**平台覆盖实测**：树内平台目录只有 **6 个**，但**来源不同**——

| 平台目录 | 怎么来的 |
|---|---|
| `@koromix/koffi-win32-x64`、`@img/sharp-win32-x64` | **npm 只装了当前平台**（platform-specific optional/平台包），**只有 win32-x64** |
| `node-pty/prebuilds/{win32-x64, win32-arm64, darwin-x64, darwin-arm64, linux-x64, linux-arm64}` | node-pty **自带**多平台 prebuilds，所以全在 |

→ **这棵树不是通用的**：它是"**在哪个平台 `npm install`，就长成哪个平台的样子**"。
→ **单一 vsix 只能覆盖一个平台**；要覆盖 Windows/macOS/Linux × x64/arm64，需要**分平台打包**（`vsce package --target <platform>`，VS Code 生态的既有做法，见 §9 外部依据）。

## 2. 事实：dsh 运行期会自管理一棵树 —— 冲突的真正来源

这是本次调查**最重要**的发现，也是"不能冲突"这条要求的技术落点。

### 2.1 `DSH_HOME` 里有一个 profile 机制

本机 `DSH_HOME = D:\Users\liaohai1\.dsh`，其中：

```
.dsh/
├── attachments/  backups/  cache/  llm-deepseek/  sessions/  storages/
├── settings.yaml  .credentials.yaml  AGENTS.md  .anonymous-user-id  work-bridge.json
└── profiles/
    ├── acp/  desktop/  headless/  sdk/  sdk-minimal/  web/  work/   ← 每个 profile 一套
    └── node_modules/                                                ← 共享的扁平依赖池
```

`profiles/web/package.json`（**逐字读自本机**）：

```json
{
  "name": "dsh-profile-web",
  "private": true,
  "dependencies": { "dsh-drop-caret": "^0.2.2" },
  "dsh": {
    "profile": {
      "bundles": [
        "@deepseek-ai/dsh-base",
        "@deepseek-ai/dsh-web-app",
        "dsh-drop-caret",
        "dsh-webview-clipboard"
      ],
      "patchReload": "live"
    }
  }
}
```

同目录还有 `cordis.yml`（内容为 `[]`，注释写明"树由 patches 组合而成"）、`cordis.patch.yml`、**`pnpm-lock.yaml`**、**`pnpm-workspace.yaml`**。

→ **dsh 在运行期会在 `DSH_HOME/profiles/<profile>/` 下用 pnpm 装/管理一棵插件树**，其中既有官方 bundle（`dsh-base` / `dsh-web-app`），也有**第三方插件**（`dsh-drop-caret` / `dsh-webview-clipboard`）。

### 2.2 `profiles/node_modules` 是跨安装源的 junction 池

`profiles/node_modules` 下约 250 个条目，**LinkType 全是 `Junction`**（Windows 目录联接），目标**指向 4 个不同的根**（本机实测，逐条列举）：

| 目标根 | 举例 | 说明 |
|---|---|---|
| `%APPDATA%\npm\node_modules\@deepseek-ai\dsh\node_modules\…` | `express`、`koffi`、`ws`、`zod` | **npm 全局安装的 dsh** |
| `%LOCALAPPDATA%\Programs\DSH Desktop\resources\app\node_modules\…` | `react`、`pnpm`、`lucide-react`、`dsh-plugin-desktop` | **DSH Desktop 应用** |
| `%LOCALAPPDATA%\pnpm\global\5\.pnpm\node_modules\…` | `uuid`、`tr46`、`is-stream` | **pnpm 全局** |
| `D:\code\deepseek-harness\node_modules\typescript` | `typescript` | 一个**开发 checkout** |

`profiles/node_modules/@deepseek-ai/dsh` → **解析到** `%APPDATA%\npm\node_modules\@deepseek-ai\dsh`（即全局 CLI 树）。

**推论（这就是"冲突"的具体机制）**：
`DSH_HOME` 是**机器级共享状态**，而 `profiles/node_modules` 是一张"**当前在跑的那个 dsh 指向它自己那棵树**"的链接池。于是——

- **内置 dsh 与全局 dsh 共用同一个 `~/.dsh`** → 谁最后跑，谁就可能把这批 junction 改指向自己；另一个再跑又改回来。**两个内核会互相改写对方的依赖解析结果**；
- 它们还共享同一份 `pnpm-lock.yaml` 与已装插件（用户装的第三方插件在池里），**版本偏斜会直接踩到对方**。

> ⚠️ **待验证**：我确认的是"链接目标指向多个来源"这一**静态事实**。**谁在什么时机重写这张池子，我没有实测写入过程**（未观察 `dsh web` 启动时的写入行为）。这一条必须实测后才能当作定论——见 §8 V2。

### 2.3 一个连带事实

本机 `profiles/node_modules/pnpm` 指向 **DSH Desktop**，而 `@deepseek-ai/dsh` 自身 `package.json` **没有 `pnpm` 依赖**（72 个直接依赖里没有）。所以 pnpm 从哪来、由谁驱动这套 profile 安装，**我没有查清**——见 §8 V3。

## 3. 五个方案对照

| 方案 | 做法 | 体积代价 | 平台 | 冲突面 | 首次需网络 |
|---|---|---|---|---|---|
| **A 打包进 vsix** | 把 `node_modules/@deepseek-ai/**` 等加进 `package.json` 的 `files` 白名单 | **+222.6 MiB**（解包）／**每个编辑器各一份** | **必须分平台打包**，否则只覆盖一个平台 | 取决于 §5 选哪种 home 策略 | ❌ |
| **B 分平台 vsix** | `vsce package --target win32-x64` 等 6 个 target | 同 A，但每个用户只装一份 | 需要 6 条打包/发布链路 | 同 A | ❌ |
| **C 首次运行按需获取**（业界标准做法） | 检测到无内核时，从 npm registry/CDN 取该平台 tarball 解到 `globalStorageUri` | **0**（装完才占，且只占一份） | 按当前平台取，天然正确 | **可隔离 home**（§5 S2） | ✅ 仅首次 |
| **D 引导安装** | 只提示或一键跑 `npm i -g @deepseek-ai/dsh` | 0 | — | 与全局 dsh 同一个（本来就是一个） | ✅ 且**需要机器有 Node+npm** |
| **E 不做** | 维持现状（当前行为） | 0 | — | 无 | — |

> **D 为什么不够**：用户的目标是"**目标机器可能连 DSH 都没有**"。若那台机器**也没有 Node/npm**，D 直接不可行——这正是 A/B/C 存在的理由。

---

## 4. 三个硬约束（选哪个方案都绕不开）

1. **体积**：222.6 MiB 解包 / 25,471 文件。本机实测 **VS Code 与 Cursor 各有一份扩展 globalStorage**；若装 3 个编辑器（VS Code / Cursor / Antigravity）就是 **~670 MiB**，且**每次扩展升级都要重下**。
2. **平台**：原生件（libvips / koffi / sharp / node-pty）只装当前平台。**"一个 vsix 通用三平台"做不到**，必须 6 个 target（§1.1）。
3. **运行期自管理**：内置 dsh **仍然要在 `DSH_HOME` 里装/管理 profile 插件树**（§2.1）。**"harness 随插件走"不等于"harness 自包含"**——它照样写机器上的 `~/.dsh`。这一点最容易被忽略。

## 5. 冲突的三种解法

| # | 解法 | 效果 | 代价 |
|---|---|---|---|
| **S1** | **内置仅作兜底**：有系统 dsh 就用系统的，没有才用内置 | 正常情况**根本不会出现"两个内核"**，冲突面自然消失 | 有 DSH 的用户拿不到"内置那份"的确定性；需要明确优先级规则 |
| **S2** | **隔离 home**：内置内核用 `globalStorageUri/dsh-home` | **零冲突**，且不污染用户的 `~/.dsh` | **丢掉"同一个 `~/.dsh`、同一份会话/设置"** |
| **S3** | **共享 home + 版本对齐**：内置版本与系统版本不一致时拒绝共享并提示 | 兼顾共享与安全 | 复杂度最高：要检测、要提示、要处理"用户先装后装"的时序 |

> ⚠️ **S2 是产品决策，不是技术决策**：`docs/02-Areas/20260914-09-产品定位与边界.md:23` 把"**同一个 `~/.dsh`、同一份会话/设置**；终端/浏览器用户换到 IDE 零学习成本"列为**获客价值（零成本接入）**。选 S2 就是**主动放弃这条卖点**——必须由用户拍板，不能由实现者顺手决定。

**S1 的历史渊源**：早期架构提案 `docs/01-Projects/R20260817-01-桥架构与IDE内嵌/09-架构提案_by-deepseek.md:220` 早就写过二进制解析顺序：

> ① 设置指定的路径 → ② `PATH` 上的全局 `dsh` → ③ **扩展内置依赖 `@deepseek-ai/dsh`（随 vsix 打包，`node_modules` 直跑 `lib/bin.js`）** → ④ 引导安装提示

**该 ③ 从未落地**（现行 `resolveDshPath()` 只有 ① 设置 → ② 本机全局/常见位置/npx 缓存，没有内置路径，见 `src/serverManager.ts:351-380`）。本次是**重新评估这个被搁置的设想**。

## 6. 我的建议

| 你的真实目标 | 建议 | 理由 |
|---|---|---|
| **"没装 DSH 的机器也能用"** | **C（按需获取）+ S1（兜底）** | 达成目标且**不碰 vsix 体积**；C 是 VS Code 生态的既有做法（语言服务器普遍这么干） |
| **"完全离线也要能用"** | 只有 **A/B** 能做到 | 但要接受：6 平台打包、~670 MiB 多编辑器占用、每次升级重下 |
| **"不想动，只是问问"** | **E** | 现状已能用；本议题可以只登记不实施 |

**明确不建议**：在没有"离线"硬需求的前提下选 A/B——付出 222.6 MiB × N 编辑器 + 6 条打包链路的代价，换来的能力（离线可用）在目标场景里未必用得上。

**若最终选 A/B，另有一条必须先解决的问题**：本仓已有一次"vsix 静默缺依赖"事故——`scripts/package.js:24-31` 注释记录：`--no-dependencies` 会**静默丢掉全部 `node_modules/ws/**`**，导致激活即崩（[11-修复_vsix缺少ws依赖](../../01-Projects/R20260817-01-桥架构与IDE内嵌/11-修复_vsix缺少ws依赖.md)）。把 25,471 个文件交给 vsce 的依赖探测，**必须先验证产物完整性**，不能只看"打包成功"。

## 9. 外部依据（非本仓实测，仅作参考）

- Open VSX 的 vsix 体积限制：有资料称服务端配置项 `ovsx.publishing.max-content-size` **默认为 512 MB**（[来源](https://nextguardhq.com/zh/vulnerabilities/cve-2026-89321-eclipse-foundation-eclipse-openvsx)）。**这是服务端可配项，不是对发布者的承诺**，且本文未实测上传，故列为 V5。
- 分平台扩展分发（`--target`）是 VS Code 生态的既有做法（[相关讨论](https://stackoverflow.com/questions/78628338/how-do-vs-code-extensions-automate-distribution-across-different-platform-archit)）。本文未在本仓验证，列为 V6。
