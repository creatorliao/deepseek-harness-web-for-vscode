## 现象

用户实测（2026-09-15，VS Code 内嵌面板）：

1. **「内测声明」每次都会出现**：点「继续」关闭后，下次打开面板/重载仍然弹出。
2. **截图发不回来**：粘贴（截图）后附件缩略图位置显示**破图 + 文件名 `image.png`**；发送后会话里的图片同样看不到。

---

## 根因

### A. 图片不显示：CSP 的 `img-src` 没有放行 `blob:`，而上游的图片预览**全部**用 `blob:` URL

上游两条图片渲染路径都走 `URL.createObjectURL`：

| 环节 | 证据（dsh 0.1.5-rc.2） |
|---|---|
| 输入框待发图预览地址 | `dsh-client-ui-conversation/lib/client.js:2769` — `previewUrl: URL.createObjectURL(file)` |
| 已发出消息的图片 | `lib/client.js:2396-2399` — 有 `createObjectURL` 就用它建 Blob URL（只有没有该函数时才退化 `data:`） |
| 渲染 `<img src>` | `dsh-client-ui-attachment/lib/client.js:707`（输入框缩略图）、`:857`（消息图片） |

我们注入的 CSP（`src/documentAssembly.ts:146-157`，注入点 `:230`）为：

```text
img-src ${cspSource} data: http://127.0.0.1:*
```

**没有 `blob:`**。webview 文档的 origin 是 `vscode-webview://…`，页面内 `createObjectURL()` 产出的是 `blob:vscode-webview://…`，CSP 源列表必须显式写 `blob:` 才放行 → 浏览器拒载 → 渲染成破图 + `alt` 文本（就是用户看到的 `image.png`）。

**自洽性核对**：图片发送**不走**文件上传通道，而是 `encodeImage()` → `base64ImageOf(file)` 内联 base64 进 RPC（`dsh-client-ui-conversation/lib/client.js:3205-3212` 附近），因此"图能发出去、只是看不见"完全对得上——**唯一缺的就是显示**。

### B. 「内测声明」反复出现：嵌入页面的 settings scope 落在 memory 模式，确认只在**进程内**生效

上游的持久化模式由 `isLoopback` 决定：

```js
// dsh-client-ui-settings/lib/client.js:1345（0.1.5-rc.2）
const persistence = ctx.remote.$host.isLoopback ? "host" : "memory";
```

```js
// dsh-client-connection/lib/client.js:6344（0.1.5-rc.2）
isLoopback: transport?.ownsHost === true || pageLocation === void 0 || isLoopbackHostname(pageLocation.hostname)
```

面板页面 origin 是 `vscode-webview://…` → hostname 非回环、`__DSH_TRANSPORT__` 未设 → `isLoopback = false` → `persistence = "memory"`。

于是「内测声明」的确认只会写进**页面进程内的局部变量**，不落盘：

```js
// dsh-client-ui-settings-models/lib/client.js:2496-2506（WelcomeNoticeStore.acknowledge）
if (this.scope.getSnapshot().mode === "memory") {
  this.localAcknowledged = true;   // ← 仅本次文档生命周期有效
  this.derive();
  return true;                     // ← 按钮照常关闭，所以看起来"点了有用"
}
```

面板每次打开都重新组装文档 → `localAcknowledged` 归零 → 弹窗再来一次。

**一手实证（决定性）**：本机 `~/.dsh/settings.yaml:1-2` **已经有**这份持久确认：

```yaml
ui-onboarding:
  welcomeNoticeVersion: 2026-08-13.1
```

即：用户已在能落盘的界面上确认过（当前版本号 `2026-08-13.1`，见 `dsh-client-ui-settings-models/lib/client.js:2444`），**面板仍然每次弹** → 面板根本没读这份持久值。

### C. 这不是孤例：同一根因的已知症状

- `media/bridge-client.js:43-69` 的 `matchMedia` shim 就是**同一根因的第一个补丁**（脚本注释原文：页面 origin 非回环 → settings scope 走 memory 模式 → 永不采用 `ui-theme.preference`）。
- 待办 **G-05**（"嵌入式页面同步 host settings（locale 等）"）说的是同一件事，当时的结论是"优先提上游、本地不做"。
- `dsh-client-ui-settings-general/lib/client.js:540`：`ctx.remote.$host.isLoopback ? new SettingsDocumentStore(...) : undefined` —— 常规设置页的文档编辑能力也依赖它。
- **因此 B 的影响面不止一个弹窗**：面板里的设置写入（含 Models 页保存 provider/API Key）当前都停在内存模式，不会落盘。

### D. 同族（同一处 CSP 收紧的连带面，**未实测**，仅代码证据）

| 面 | 我们的 CSP | 上游用法（0.1.5-rc.2） | 预期症状 |
|---|---|---|---|
| 非图片文件附件上传 | `worker-src 'none'` | `dsh-client-file-upload/lib/client.js:219-224`：`new Worker(URL.createObjectURL(new Blob([...])))`（未设 `__DSH_FILE_UPLOAD__` 时**必走** worker 载体） | 附件卡片报错（图片不受影响，图片走 base64） |
| 工作区文件预览 · HTML | `frame-src 'none'` | `dsh-client-ui-sidebar-documentpreview/lib/client.js:2361`：`URL.createObjectURL(new Blob([html]))` 塞进 iframe | HTML 预览空白 |
| 工作区文件预览 · 图片 | `img-src` 缺 `blob:` | 同文件 `:2525`：`URL.createObjectURL(new Blob([data], {type: mediaType}))` | 图片预览破图 |

## 修复

**已实施**（2026-09-15）。两处都是本项目范围内的改动（零 fork，仍在文档层/注入层）。

### F1 · `img-src` 放行 `blob:`（修现象 2，一行）

`src/documentAssembly.ts` 的 `buildCsp()`：

```diff
- img-src ${cspSource} data: http://127.0.0.1:*
+ img-src ${cspSource} data: blob: http://127.0.0.1:*
```

理由：Blob URL 由页面自己创建，origin 仍是 webview 自身，放行 `blob:` 不引入外部来源；`data:` 本来就已经放行，语义上并不比它更宽。同处补了一段注释，说明 `blob:` 与 `script-src` 里的 `http://127.0.0.1:*` 都是"看着宽、其实承重"的条目（防止后来者当冗余删掉）。

**可选同批**（修 D 的同族面，需单独决策，**本轮未做**）：`worker-src blob:`、`frame-src blob:`。

### F2 · 注入 `__DSH_TRANSPORT__ = { fetch, ownsHost: true }`（修现象 1）

**落地位置**：`media/bridge-client.js` 的 fetch shim 之后，新增 `DSH transport-hook declaration` 段（与已有的 `matchMedia` shim 放在同一个文件——两者都是"因为页面 origin 非回环而补的垫片"）。该脚本整体在 DSH 模块脚本之前执行（`documentAssembly.ts:235`，即定制清单 A9），因此钩子在 shell bundle 读它之前就已就位。

```js
window.__DSH_TRANSPORT__ = { fetch: window.fetch, ownsHost: true };
```

（`window` 即 `globalThis`，上游按 `globalThis.__DSH_TRANSPORT__` 读；写成 `window.` 是为了让 webview 单测能在 stub 上直接断言。）

依据（上游契约，非臆测）：

- `dsh-client-connection/lib/types/client/index.d.ts:37-63`：`ownsHost` 的定义原文 —— "The transport owner declares the page owns the Host outright: the Host runs inside a worker this page spawned, so no other party can reach it and the loopback stand-in for 'the operator's own machine' is vacuous. `ctx.connection.isLoopback` then reports the privileged surface reachable regardless of the page authority. **Only a shell that assembles its own transport can set this; served pages never carry the global at all.**"
- **与本项目的对应关系（这是判断，不是逐字照搬）**：上游那句描述的是"Host 跑在本页 spawn 的 worker 里"的场景；我们是"Host 是扩展 spawn 的独立进程、页面只能经桥到达"。二者共同点是**页面自己组装传输、且只有它到达 Host**（dsh 服务器仅回环监听 + Cookie + `/api` 围栏，没有对第三方页面开放）。
- `isLoopback` 在 0.1.5-rc.2 的客户端消费点**只有两处**（全量 grep）：`dsh-client-ui-settings`（持久化模式）与 `dsh-client-ui-settings-general`（常规设置页文档编辑器）。因此这个改动的影响面是可枚举的，见下方"副作用"。
- `__DSH_TRANSPORT__` 在整份 dsh 安装里**只有一处消费**（`dsh-client-connection/lib/client.js:6307`；`dsh-web-frontend/dist` 里那份是同文件的打包副本），且不传 `loadBundle` 不会影响模块系统（该字段只在该文件被读）。
- 传入的 `fetch` 就是桥自己的 shim，与当前默认（`globalThis.fetch`）**等价**，RPC 通路不变。

**副作用（必须声明）**：面板的设置写入从"内存模式"变为**真的落盘到 `~/.dsh/settings.yaml`**。这与本项目既有的共享边界一致（[02-教程](../R20260914-02-DSH内嵌原理与教程/02-教程_对官方DSH的定制清单.md) §C：扩展与浏览器共用 `~/.dsh`），但属于**行为变更**：面板里改的设置以后浏览器端也看得到。`matchMedia` shim **保留**（`ui-theme.preference` 默认仍是 `system`，仍要靠它跟随 VS Code 主题）。
