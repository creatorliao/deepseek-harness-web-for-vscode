# 需求：目录树拖拽到 Composer

**日期**: 2026-09-17 ｜ **状态**: 待评审（本次按用户一次性授权先执行，见 `01-讨论` §3）
**定位**: 定义"做什么"与"怎样算做成"；**不含实现细节**（实现进 `03-方案`）。

---

## 1. 背景与目标

现状：要把某个文件交给 DSH，用户必须在 Composer 里手打 `@`、等文件选择器弹出、再输入文件名搜索并选中——路径深或文件名相似时很慢。

目标：**把"拖"变成"引用"**。用户从 VS Code 资源管理器（目录树）把文件拖到 DSH 面板上，Composer 里出现该文件的引用，效果等同于手动 `@` 选中它；随后的提问即针对这些文件。

对标：Cursor 的"拖文件进 Chat 即成为上下文"。差异容忍度见 §4。

## 2. 需求清单

### R1 拖拽即引用（核心）

- 从 VS Code **资源管理器**拖拽**单个文件**到 DSH 界面，Composer 里出现该文件的引用。
- 引用必须能被 DSH 解析为**工作区内的真实文件**：发送后 AI 能读到该文件内容，不需要用户再补一句路径说明。

### R2 多选批量

- 一次拖拽资源管理器里的**多个**选中项（多选 / Ctrl 多选 / Shift 连选）时，每一个都产生一条引用，**不遗漏、不重复、不互相覆盖**。

### R3 已有草稿不被破坏

- Composer 里已有文字时，插入**不得清空或替换**已有内容。
- 插入位置合理（当前光标处或末尾），插入后用户能直接继续输入。
- 插入完成后焦点应回到 Composer，用户可直接按回车发送。

### R4 两种界面形态都要生效

- **编辑器标签页面板**（`deepseekHarness.openTarget = editorTab`）与**次级侧边栏视图**（`= sidebar`）都必须支持；不得只在其中一个生效。

### R5 失败必须可见，不得静默

- 拖拽了**无法处理**的东西（例如非工作区的外部文件、空拖拽、纯文本拖拽）时，给出明确提示，不能"什么都没发生"。
- 提示文案为简体中文，且遵循 `AGENTS.md` 的 i18n 约定（用户可见文案进 `src/i18nStrings.ts`）。

### R6 不弱化既有安全基线

- 不得为支持拖拽而放宽 `/api` 信任围栏、不得让 webview 直连 DSH、不得放宽 CSP 到引入新的远程源。
- 拖拽数据只在本机（webview ↔ 扩展宿主）流转，不外发。

### R7 兼容既有编辑器基线

- 在 VS Code **1.105.1** 与 Cursor（内嵌 VS Code **1.128.0**）上均可用；不抬高 `engines.vscode`。

### R8 不回归既有行为

- 不拖拽时，Composer 的一切现有行为（输入、`@` 选择器、粘贴截图、发送、快捷键）保持不变。
- 既有单测全绿；新增逻辑必须有单测覆盖。

## 3. 验收标准

| # | 场景 | 判定 |
|---|---|---|
| A1 | VS Code 1.105.1 真机，从资源管理器拖 **1 个 `.ts` 文件**到编辑器标签页面板 | Composer 出现引用；发送后 AI 能读到该文件（真机肉眼确认 + 会话记录） |
| A2 | 同 A1，拖 **3 个文件**（Ctrl 多选） | 出现 3 条引用，无重复 |
| A3 | Composer 已有草稿时拖入 | 草稿原文一字不少，引用追加其后 |
| A4 | 次级侧边栏形态（`openTarget = sidebar`）重复 A1 | 同样生效 |
| A5 | 拖入非工作区/不可识别内容 | 出现中文提示，无异常抛错、无白屏 |
| A6 | 不拖拽时的既有路径 | 与升级前完全一致（无行为变化） |
| A7 | `npm run compile` / `npm test` | 零 issue、全绿 |
| A8 | 安装到 VS Code 与 Cursor | 扩展列表显示新版本号，功能可用 |

## 4. 与"Cursor 体验"的差异容忍度（重要）

Cursor 里拖进去的是**结构化上下文条目**（一张带文件图标的 chip）。本项目是**在 DSH 既有前端里做注入**，若上游不提供程序化入口，我们能做到的是"**功能等价**"而非"**像素一致**"：

- **必须满足**：AI 确实读到该文件（R1 的功能性要求）。
- **可以从宽**：Composer 里的呈现形态（纯文本 `@路径` vs 富文本 chip）——以最终调查结论为准，差异在 `08-分析` 与 `03-方案` 中明确写出并说明理由。
- 若调查结论是"**连功能等价都做不到**"，必须在 `03-调查` 里给出**可复现的证据**与替代路径，而不是含糊交付。

## 5. 范围外（明确不做）

- 不做"拖拽后自动发送"。
- 不做浏览器版 DSH 页面的拖拽支持。
- 不做 VS Code 之外的编辑器适配（Antigravity 通过同一套代码自然继承，不单独验证）。
- 不修改 DSH 上游源码、不提上游 PR。
- 不做 G-10（聊天路径点击跳转）与 G-11（选区右键提问）——相邻但独立。

## 7. 追加需求（2026-09-17，用户实测后提出）

**背景**：真机实测发现"拖到 composer"这条路被 VS Code 平台挡住（webview 拖拽期间 iframe 被置 `pointer-events:none`，只有 Shift 放行；机制见 `09-事实` §真机补充）。用户追问"如果直接的路径过不去，能有更好的方式吗"。

**追加的验收口径**：同一个目标（把 IDE 里的文件变成 composer 里的 `@` 引用）允许有多个入口；拖拽只是其中之一，**不得把"必须拖拽"当成验收前提**。

| # | 入口 | 状态 |
|---|---|---|
| E-A | **资源管理器右键「添加到 DSH 输入框（@ 引用）」**（支持多选/文件夹） | ✅ v0.5.0 交付，v0.5.2 修掉重复写入 |
| E-B | **快捷键 `Ctrl+Alt+A` / `Cmd+Alt+A`（编辑器有焦点时）→ 加入当前文件** | ✅ v0.5.3 交付 |
| E-C | **TreeView 投放条**（`TreeDragAndDropController`，官方支持、宿主直接拿到 URI 列表、**不受 webview 屏蔽影响**） | ⏳ 待用户决定（新增一块常驻窄条，落点不是 composer） |
| E-D | **Shift + 拖拽到 composer** | ⏳ 待用户复测（`07-待办` T13） |
| E-E | 伪造 workbench 拖拽事件以解除屏蔽 | ❌ 已否决（代价见 `09-事实` §真机补充 6） |

**追加的验收标准**：

| # | 场景 | 判定 |
|---|---|---|
| A9 | 打开一个文件 → 按 `Ctrl+Alt+A`（mac `Cmd+Alt+A`） | composer 里出现该文件的 `@` 引用；面板未打开时给出中文提示而不是静默 |
| A10 | 没有打开文件时按快捷键 | 给出中文提示（指引用右键入口），不静默、不报错 |
| A11 | 快捷键与 VS Code 默认键位冲突 | 无冲突（1.105.1 默认键位表实测零命中）；且用户可在键盘快捷方式里自行改键 |

**明确不做**：把"拖拽"从需求里删掉——它仍然是目标体验，只是**降级为可选入口**，不再作为唯一路径。

## 8. 追加需求（2026-09-17 真机反馈后，第二轮）

**用户原话要点**：① `Ctrl+Alt+A` 没生效；② 命令面板与目录树右键可用；③ 拖拽没生效；④ 想要"编辑器右上角按钮"与"编辑器右键同等功能"；⑤ 侧边栏拖不进去要查根因；⑥ 若侧边栏受技术限制，**拖到编辑器 tab 里会不会更容易**；⑦ **tab 形态体验比侧边栏更好**，希望拖拽也能加上。

> 用户同时明确：**这些反馈"不全部都是问题"** → 必须先逐条定性（缺陷 / 平台限制 / 使用误解 / 新需求），不得一律当缺陷修。定性结果见 [12-分析_入口可达性与拖拽可达性.md](12-分析_入口可达性与拖拽可达性.md)。

### 追加的需求条目

| # | 需求 | 验收标准 | 状态 |
|---|---|---|---|
| R9 | **编辑器标题栏按钮**：打开某文件时右上角有可点入口，一点即把该文件加入 DSH 输入框 | 打开 `.ts` 文件 → 右上角出现 ⊕ → 点击后 composer 出现 `@该文件` | ✅ v0.6.0 |
| R10 | **编辑器右键菜单**与资源管理器右键**同等能力** | 编辑器内右键 → 出现「添加到 DSH 输入框（@ 引用）」→ 行为与目录树右键一致 | ✅ v0.6.0 |
| R11 | **拖拽必须有一个真正可用的落点**（不受平台屏蔽影响） | 从资源管理器拖 1 个/多个文件到**文件树下方的投放条** → composer 出现对应 `@引用`；**无需按 Shift** | ✅ v0.6.0（原生 TreeView） |
| R12 | **两种承载形态都能拿到引用**（侧边栏与编辑器 tab） | 投放条与所有菜单入口在 `openTarget` 两种取值下都生效 | ✅（入口与承载形态解耦，共用 `addUrisToContext`） |
| R13 | **入口可诊断**：用户能自行确认"当前跑的是哪个版本" | `输出 → Extension Host` 里能看到 `[dsh] activate: v<版本>` | ✅ v0.6.0 |
| R14 | **快捷键可用性定性**（不预设它一定是缺陷） | 用 `Developer: Inspect Key Mappings` 或键盘快捷方式界面判定：未重载 / 被全局热键抢 / 焦点不对 | ⏳ 待用户探针（`07-待办` T15） |

### 明确不改的

- **不把"拖到 webview 上"当成可修项**：三处屏蔽监控（编辑器 tab / 侧边栏 view / 通用 WebviewElement）都在 VS Code 侧，跨源页面无权改；唯一放行信号是 Shift。见 `12-分析` §2/§4。
- **不做伪造 workbench 拖拽事件**（会破坏 VS Code 自身拖放）：已在 `09-事实` §真机补充 6 记为否决。
