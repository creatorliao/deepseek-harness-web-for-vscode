## 2. 参考项目：DeepSeek Harness for Obsidian 怎么做的

同族项目（同一作者维护），已经实现了"目录树 → 输入框"的拖拽投递。它的**结构与方法**是本特性的直接参照。

### 2.1 架构分层（值得照抄的分法）

| 层 | 文件 | 职责 |
|---|---|---|
| 翻译层（**纯函数**） | `src/context/dragReference.ts` | 把"拖拽负载"翻译成 DSH 的 `@` 引用语法；不碰 DOM、不碰 vscode |
| 投递层 | `src/context/promptChannel.ts` | **全仓唯一**写 guest 输入框的地方；失败降级到剪贴板 |
| 宿主投放区 | `src/views/dshView.ts` | 在 `<webview>` **之上**盖一层宿主 DOM `.dsh-dropzone`，靠它接 drop |
| 会话捕获 | `src/main.ts` | 宿主 `dragstart` 冒泡阶段抓"拖的是哪个文件"，`dragend`/blur 收尾 |

### 2.2 支撑它的三条事实（与我们的相同）

1. **DSH 的 `@path` 是纯文本提示词**：上游 `dsh-file-reference` 的 `FILE_REFERENCE_PROMPT` 写明"Tokens prefixed with @ are workspace paths the user explicitly referenced…"。模型自己调 `read`，不预读、不附带内容。
2. **DSH 自带的拖放只认真实文件**：判据 `dataTransfer.types.includes("Files")`，命中就上传成**附件**（attachment）；字符串型拖拽直接 `return`，连 `preventDefault` 都不调。所以目录树拖过来的东西 DSH 自己接不住。
3. **宿主侧没有"往草稿里写文本"的 RPC**：只有 `session/prompt`（会**立刻起一轮对话**），没有 `setDraft`。

### 2.3 它的关键取舍（我们要不要跟）

| 它的做法 | 我们的适用性 | 判断 |
|---|---|---|
| 用 Electron `<webview>.insertText()` 写 guest 输入框 | **VS Code 没有这个 API** | ❌ 不可移植，我们必须另找写入面（见 §3.2） |
| 宿主 `dragstart` 抓 `data-path` | Obsidian 文件树特有 DOM 契约 | ❌ VS Code 资源管理器没有对应钩子 |
| 宿主覆盖层接 drop | Obsidian 是"宿主文档 + `<webview>`"两层结构，可以盖 | ❌ VS Code webview 是 workbench 的 iframe，扩展**改不了宿主文档** |
| 引用语法（`@path` / `@"含空格"` / 目录尾随 `/` / 空格分隔 / 上限 20 / 含 `"` 则跳过不转义） | 与上游 `formatFileMention` 同规则 | ✅ **照抄**，这是唯一被上游认可的语法 |
| 失败降级：写不进去就写剪贴板 + 诚实提示 | 通用 | ✅ 照抄 |
| 一个开关 + 一个写入点 | 通用 | ✅ 照抄（只有一个写入函数、只有一个开关） |

**它的未了之事**：其验收清单 §13 的 13-1…13-18 **结果列全空**——"宿主能否收到 drop""insertText 能否落进输入框"两跳**从未实测**。也就是说：**同族项目在这条路上也只有设计，没有已证实的成功**。我们不能把"它做了"当作"它能work"。

## 3. 上游 DSH 侧：写入面到底有哪些

### 3.1 composer 是什么

Lexical 富文本编辑器，挂在 `<div data-composer-input contenteditable role="textbox" aria-multiline="true">` 上；占位符是**兄弟节点** `div[data-composer-placeholder]`；类名是 CSS-module 哈希（**不可依赖**）；`[data-phase]` 同时存在于会话根，**单独用会歧义**。证据：`10-事实_DSH-Composer与提及机制.md` §composer 结构。

### 3.2 四条写入通路（数据见表）

| # | 通路 | 可行性 | 结论 |
|---|---|---|---|
| W1 | **合成 `paste` 事件**打到 `[data-composer-input]` | ✅ 代码级可行 | **选它**。上游把 `PASTE_COMMAND` 注册在编辑器根元素上（`CONV` 绑定 `["paste", …]` → `Nl(e, PASTE_COMMAND, t)`），处理器读 `clipboardData.getData("text/plain")` → `handlers.pasteText(text)` → `keyboard.paste(text)`（`applyEdit(..., discrete: true)`，**同步提交**）。不检查 `isTrusted`，只跳过 `_lexicalHandled` 的事件 |
| W2 | `document.execCommand("insertText")` | ⚠️ 未验证 | 作为 W1 无效时的**兜底** |
| W3 | 直接改 DOM 文本 | ❌ | 下一次 Lexical commit 会覆盖 |
| W4 | 客户端插件 `actx.bail("slash/input-insert-text")` / 直投 `session/prompt` RPC | ❌ / ⚠️ | W4a 要装进 `$DSH_HOME`（上游一升级就坏，同族项目已否决）；W4b **会立刻起一轮对话**，不是"填草稿" |

### 3.3 最关键的结论：**落纯文本 == 走 picker**

文件 `@` 提及的 chip 的 `serialize()` 是**恒等函数**（`ref` 本身即 `@path`），clipboard 投影也是同一个字符串。所以「手打/粘贴 `@src/foo.ts `」与「选一次补全」在**发给模型的消息里逐字节相同**；客户端/服务端**没有任何正则**把 `@path` 解析成结构化引用，语义完全靠模型按系统提示词理解。

→ **这意味着"像素级复刻 Cursor 的 chip"没有任何功能收益，只有视觉差异**。需求 §4 的 C1 由此定案：**接受"纯文本引用"，视觉上不是 chip**。

### 3.4 `@` 语法（照抄参考项目的等价实现）

| 情形 | 形式 |
|---|---|
| 普通文件 | `@src/foo.ts` |
| 含空白的路径 | `@"src/my notes.md"` |
| 目录 | 尾随 `/`：`@src/utils/` |
| 含 `"` 或控制字符 | **跳过该条**（不转义——转义会编出一个不存在的路径） |
| 多条 | **空格**分隔（上游 tokenizer 只在行首/空白后识别 `@`） |
| 路径根 | **工作区相对 + 正斜杠**（`docs/x.md`），不是绝对路径、不是 `file://` |
| 单次上限 | 20 条（防误拖一整个目录刷爆输入框） |

## 4. VS Code 内嵌面：拖拽能不能进到我们的页面

**核心事实（源码级）**：VS Code 在窗口内发生**任何 `dragstart`** 时把 webview iframe 置为 `pointer-events:none`——"Webview break drag and dropping around the main window (no events are generated when you are over them). Work around this by disabling pointer events during the drag."。**只有按住 Shift**，`WebviewWindowDragMonitor` 才会调 `windowDidDragEnd()` 把它恢复。

→ 因此：

| 条件 | 结果 |
|---|---|
| 从资源管理器拖文件 → **不按 Shift** → 落到 DSH 面板 | 面板收不到任何事件，文件被 VS Code 在**编辑器区打开**（用户视角"点了没反应，还多开一个文件"） |
| 从资源管理器拖文件 → **按住 Shift**（须在指针进入面板**之前**按下）→ 落到面板 | 面板内 `dragover/drop` 正常触发，可用 |
| 从 **Windows 资源管理器**拖真实文件进面板 | 与上面无关（窗口内没有 `dragstart`，不触发屏蔽）→ DSH 自己收成**附件**（既有行为，不能被我们破坏） |

**版本锚点**：Shift 恢复逻辑由 PR #209211（2024-06-19 合入 main，June 2024 里程碑）引入，是 issue #182449「Drop files from Explorer to CustomEditor (webview) doesn't work」的**官方修复**；1.92.2 无、1.93.0 有、1.105.1 有。

**官方 API 面**：**没有**任何把 webview drop 交给扩展宿主的 API（`@types/vscode` 1.105.0 只有编辑器的 `DocumentDropEditProvider` 与树的 `TreeDragAndDropController`）。

**风险登记**：microsoft/vscode#237958（1.96.3 / Windows，**至今 open**，`bug`+`webview`）报告"按 Shift 也捕不到"。与源码设计意图冲突，无法在无 GUI 环境下证伪。**这就是必须准备兜底入口的直接理由**。

## 5. 数据：拖拽负载里到底有什么

资源管理器拖拽**不产生 `File` 对象**（`dataTransfer.files` 为空），路径只能从字符串项里取。可用键与覆盖能力：

| mime key（大小写不敏感匹配） | 值形态 | 含目录 | 多选全量 | 备注 |
|---|---|---|---|---|
| `application/vnd.code.uri-list` | `\r\n` 分隔的完整 URI 列表 | ✅ | ✅ | **首选**；可能带 `#L3,5` 片段 |
| `text/uri-list` | **仅第一个** URI | ✅ | ❌ | 上游注释指 Chromium bug 239745 所致 |
| `ResourceURLs` | JSON 数组，`file:///d%3A/…` | ❌ | ✅ | **仅文件** |
| `CodeFiles` | JSON 数组，`fsPath` | ？ | ✅ | 扩展树视图会写；内置资源管理器**未验证** |
| `CodeEditors` | `stringify()` 的对象数组，含 `resource` URI | ✅ | ✅ | 非公开契约 |
| `text/plain` | 标签路径（相对或绝对），`\r\n` 分隔 | ✅ | ✅ | 无协议信息，最后兜底 |
| `Files` | — | — | — | **有它就说明是 OS 真实文件拖拽 → 我们让路给 DSH 的附件通道** |

**webview 内这些键是否真能读到**：规范只要求 drop 阶段可读且**无跨源条款**，但 whatwg/html#12807 称跨源 iframe 的原生 DnD"不可靠"。→ **未实测，必须在目标机验证**（`05-验证` A 组）。

## 6. 可行通路对比与结论

| 方案 | 拖拽手势 | 依赖 | 风险 | 判断 |
|---|---|---|---|---|
| **E1 webview 内接 drop** | ✅ 拖到 composer 上（用户要的体验） | Shift + webview 内可读 DataTransfer | 中高（#237958 未闭环；跨源可读性未实测） | **做**，作为主路径 |
| **E2 资源管理器右键「添加到 DSH 输入框」** | ❌ 非拖拽（但同属"目录树 → composer"） | 官方菜单 API，无 Shift | 极低 | **做**，作为兜底（超出原始诉求，理由见方案 §3.4） |
| E3 侧边栏新增一个 TreeView 当投放区 | ⚠️ 拖到小条上，不是 composer | `TreeDragAndDropController`（官方支持） | 低，但**新增一块常驻 UI** | 本轮**不做**，登记为备选（若 E1 真机不通过则下一轮上） |
| E4 直投 `session/prompt` RPC | ❌ | 端点名与 payload 未验证 | 会**替用户发问**，语义完全不同 | ❌ 否决 |
| E5 DSH 客户端插件 | ❌ | 要装进 `$DSH_HOME` | 上游一升级就坏 | ❌ 否决（与同族项目结论一致） |

**可行性判定**：**可实现，但不是 100% 可靠**——E1 是"用户要的那个手势"，带一个 Shift 前提与一个未闭环的 VS Code 缺陷；E2 保证"目录树 → composer"这条路**无论如何都能用**。两者共用同一套翻译层与写入层，成本主要是 E2 的菜单项。

**与 Cursor 的差距（如实说明）**：Cursor 的 chat 是原生 UI，拖进去是**结构化上下文条目**；我们是在上游前端里按它自己的语法写纯文本 `@path`。**功能等价（模型确实读该文件），视觉不等价（不是 chip）**。这个差距是架构性的——除非上游开放程序化插入 chip 的入口，否则无法消除。
