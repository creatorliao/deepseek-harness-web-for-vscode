## 1. `Ctrl+Alt+A` 没生效 —— 未定性，先给证据与探针

### 已排除的

| 假设 | 证据 | 结论 |
|---|---|---|
| "键位没打进安装包" | 已装扩展的 `package.json`：`keybindings: {"command":"…addToContext","key":"ctrl+alt+a","mac":"cmd+alt+a","when":"editorTextFocus"}` | ❌ 排除：声明**正确随 0.5.3 打包** |
| "被用户自己的键位覆盖" | `%APPDATA%\Code\User\keybindings.json` **不存在**；Cursor 的 `keybindings.json` 只有 `ctrl+i` 与 `ctrl+/` 两条，与 A 无关 | ❌ 排除 |
| "被 VS Code 默认键位占用" | 默认键位表在 bundle 里是**位掩码**，字符串搜不到——**因此我之前"零冲突"的结论只覆盖了字符串层面，不能作为定论**（本轮修正口径） | ⚠️ 未能证实 |

### 仍在怀疑的三种（按可能性排序）

1. **扩展宿主没有重载到 0.5.3**（最可能）。用户看到的"命令面板有命令""目录树右键菜单生效"**都不能证明版本**——这两个入口自 0.5.0 起就存在。
   → **本轮已加可诊断性**：`activate()` 现在打印扩展版本（`[dsh] activate: v0.6.0 …`）。用户可在 `输出 → 选 "Extension Host"`（或"DeepSeek Harness"）里一眼确认**当前跑的是哪个版本**。
2. **全局热键被别的程序抢走**。本机实测：**Snipaste 正在运行**（`ProcessName=Snipaste, Id=16904`）；QQ 未运行（QQ 的截图默认就是 `Ctrl+Alt+A`）。
   → 探针：Windows 下先退出 Snipaste 再试；或换键位试。
3. **焦点不在编辑器**。键位带 `when: editorTextFocus`——**这是故意的**（避免在终端/面板里误触）。若用户当时焦点在资源管理器或 DSH 面板，就不会触发。
   → 探针：点一下代码区域再按。

### 解决方案

- 已加**三个不依赖快捷键的鼠标入口**（#5/#6 与既有的资源管理器右键），把"键位不通"的代价降到接近零。
- 已加**版本自诊断**（上面第 1 条）。
- **给出决定性探针**（见 `07-待办` T15）：`Ctrl+K Ctrl+S` 打开键盘快捷方式 → 搜 `添加到 DSH` → 看它右侧显示的键位；或 `Ctrl+Shift+P` → `Developer: Inspect Key Mappings` → 按 `Ctrl+Alt+A`，看它被判给了谁。**这一步能一次分清"没重载 / 被抢 / 焦点不对"。**
- 若确认是全局热键冲突 → 换默认键（而不是让用户自己找原因）。

## 2 & 3. 拖拽（侧边栏与编辑器 tab 都不行）—— 平台限制

### 根因（本机 bundle 实证）

`WebviewWindowDragMonitor`（bundle 里的 `V9e` 类，L537）：

```js
DRAG_START → windowDidDragStart() → kb() → iframe.style.pointerEvents = "none"
DRAG_END / MOUSE_MOVE(未按键) → lb() → pointerEvents = "auto"
DRAG / DRAG_OVER → e.shiftKey ? 解除 : 屏蔽
```

**它被创建了三处**（`new V9e(` 全量检索）：

| 位置 | 属于哪种承载 |
|---|---|
| bundle **L537** | **编辑器 tab** 的 webview（`workbench.editors.webviewInput`） |
| bundle **L691** | **次级侧边栏 view**（同处还有 `dropTargetElement` 的 DRAG_* 重派发） |
| bundle **L1906** | 通用 `WebviewElement` |

→ **两种形态都被同一个屏蔽覆盖**；屏蔽是 workbench 设在自己文档里的 iframe 元素上的，跨源沙箱页面改不到；唯一放行信号是"workbench 窗口上带 `shiftKey` 的 drag/dragover"，而该信号又要靠 iframe 先收到拖拽事件才能回传——死循环。**没有相关设置项**（`webview.contribution.ts` 无配置注册）。

页面侧链路本身是好的：`npm run probe:composer` 实测 VS Code 形状的 `dragover`/`drop` 被接管、负载正确转发。

### 解决方案（本轮已实现）

**把投放点从 webview 换成原生 TreeView，并放进内置 Explorer 容器**（文件树正下方）：

- 契约（`@types/vscode` 原文）：*"Use `text/uri-list` for resources dropped from the explorer or other tree views in the workbench."* → `dropMimeTypes: ["text/uri-list"]`，值 = `toString()` 的 Uri 串。
- **TreeView 不是 iframe**，workbench 直接把 drop 交给扩展宿主 → **不需要 Shift、不跨源、不受该屏蔽影响**。
- 落点位置的关键：内置 `explorer` 容器**接受第三方视图**（内置 npm 扩展就是 `"views": {"explorer": [...]}`），所以投放条能与文件树**同屏可见**——这是"从树里拖出来"这个动作唯一自然的落点。
- 实现：`src/contextDropView.ts`（新）+ `fileUrisFromUriList()`（`src/referenceDrop.ts`，纯函数、有单测）；**点击该行 = 加入当前编辑文件**（等同快捷键）。

## 4. "拖到编辑器 tab 里会不会更容易" —— 否，证据同上

用户觉得 tab 形态体验更好（宽、可见），这个判断本身没错；但**拖拽能力与承载形态无关**：编辑器 tab 的 webview 同样挂 `V9e`（L537）。所以"把拖拽加到 tab 形态"不会更容易——**要加就得用 #2/#3 的原生投放条**（本轮已加，且它在两种形态下都可用：投放条在资源管理器侧，与 DSH 界面开在哪无关）。

## 5 & 6. 编辑器右上角按钮 / 编辑器右键菜单 —— 新需求，已实现

| 入口 | 贡献点 | 说明 |
|---|---|---|
| 编辑器标题栏按钮 | `menus."editor/title"` + 命令 `icon: "$(add)"` | 打开文件时右上角出现 ⊕，点一下即把**当前文件**加入 DSH 输入框 |
| 编辑器右键菜单 | `menus."editor/context"` | 与资源管理器右键同一命令、同一行为 |
| 资源管理器右键 | `menus."explorer/context"`（0.5.0 起） | 支持多选与文件夹 |
| 快捷键 | `contributes.keybindings` | `Ctrl+Alt+A` / `Cmd+Alt+A`（待探针定性） |
| 投放条 | 内置 `explorer` 容器的原生 TreeView | **真拖拽**，多选可用 |

五个入口**共用同一实现**：`extension.ts` 的 `addUrisToContext()` → `deliverUrisToComposer()` → 翻译层 → 写入层。所以"修一次重复写入"这类问题对所有入口同时生效。

## 6. 顺带发现的操作风险（写给下一个执行者）

**这个工作树里有并发会话在改代码**（2026-09-17 实测）：`src/themeSync.ts`、`src/serverManager.ts`、`test/serverManager.test.js`、`scripts/check-dsh-latest.js`、`package.json` 的版本号（0.5.3 → **0.6.0**）以及一批 `R20260918-*` 文档都处于**未提交**状态，且 `src/extension.ts` 里混着它的一个 hunk（`registerThemeSync(context, manager)` 签名变更）。

→ **后果**：按文件 `git add` 会把它的半成品一起提交，而配套的 `themeSync.ts` 没提交 → 提交出来的是**编译不过的状态**。
→ **纪律**：提交前必须逐文件 `git diff` 分辨归属；只提交自己的显式路径；**永不 `git add -A`**（本仓规则也明令禁止）。本次因此**暂停提交**，等用户裁决。
