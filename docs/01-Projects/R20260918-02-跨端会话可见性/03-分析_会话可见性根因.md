# 分析：会话可见性根因

**日期**: 2026-09-18 ｜ **状态**: 当前
**定位**: 解释"在 VSCode 写的对话到 desktop 只显示一部分"的机制、定位到上游代码行，并说明两端到底共享什么、不共享什么。
**核实基线**: dsh `0.1.5-rc.2`、`dsh-plugin-desktop` `2.0.10`、本机 `DSH_HOME=D:\Users\liaohai1\.dsh`（2026-09-18 实测）

> 逐条事实的来源与命令输出见 [04-事实_本机会话存储取证.md](04-事实_本机会话存储取证.md)。

---

## 0. 一句话结论

**两端读的是同一个地方，这一点用户没理解错；出问题的不是"读不到"，而是"读到了却不列出来"。**
DSH 的侧边栏会话列表**按工作区分组**，一条会话只有在满足「其 `cwd` 经 `realpath` 规范化后**等于**工作区路径，且该路径仍是**现存目录**」时才算工作区成员；不满足的会话**只写一条 `[W]` 日志就被静默剔除**，界面上完全无从进入——而它的 JSONL 文件一个字节都没丢。

本机实测：**386 个会话中，76 个根会话数据完好但界面不可见**。

## 1. 两端到底共享什么（回答 Q3、Q4）

### 1.1 共享的部分

| 维度 | VSCode 扩展侧 | DSH Desktop 侧 | 是否相同 |
|---|---|---|---|
| `DSH_HOME` | 默认共享 `~/.dsh`（`src/serverManager.ts:45` 注释 "MVP shares ~/.dsh by default"；`:496` 仅在传入 `opts.dshHome` 时才覆盖） | 桌面 shim 显式写死 `set "DSH_HOME=D:\Users\liaohai1\.dsh"`（`%APPDATA%\DSH Desktop\host-commands\desktop\bin\dsh.cmd`） | ✅ 同一个 |
| dsh 内核版本 | PATH 上的 `dsh` = npm 全局 `0.1.5-rc.2` | 运行时树 `$DSH_HOME/profiles/node_modules/@deepseek-ai/dsh` = `0.1.5-rc.2` | ✅ 同版本 |
| 会话文件 | `$DSH_HOME/sessions/**` | 同一路径 | ✅ 同一批文件 |
| 工作区注册表 | `$DSH_HOME/storages/workspace.json` | 同一文件 | ✅ 同一份 |
| 投影缓存 | `$DSH_HOME/storages/session_projcache.json` + `session_projcache/sessions/*.json` | 同一份 | ✅ 同一份 |

**结论**：不存在"两端各存一份对话"，也**不存在跨端引用/同步/导入**机制。两端是**同一份存储的两个客户端**。

### 1.2 不共享的部分（这才是差异的来源）

| 维度 | VSCode 扩展 | DSH Desktop |
|---|---|---|
| 界面形态 | 把 dsh 自带 Web UI 内嵌进次级侧边栏/编辑器标签页 | Electron 外壳 + 同一个 Web UI |
| **初始工作区选择** | 面板**绑定 IDE 工作区**：启动时用 `ensureWorkspaceSession(workspaceRoot())` 保证当前文件夹有会话，前端因此选中"IDE 工作区"（`src/extension.ts:104-126`、`src/serverManager.ts:770-799`） | 桌面自己记住上次激活的 profile/工作区（`%APPDATA%\DSH Desktop\profile-selection\state.json` 当前 `{"version":2,"active":"web"}`） |
| 会话列表的取数范围 | 只列**当前 IDE 工作区**的 `workspace.sessionIds`（`src/serverManager.ts:807-841`） | 列**全部工作区**，可切换 |
| 额外失败模式 | 无 | 投影缓存 EPERM / 超大缓存隔离 / 渲染进程看门狗 / Safe Mode 用另一个 home（见 `04` §F7） |

**推论**：两端看到的"清单"天然不同，因为**默认选中的工作区不同、可选范围不同**；再叠加下面 §2 的剔除规则，用户就会感到"desktop 上少了一块"。

## 2. 根因：工作区成员资格闸门

### 2.1 判定规则（上游代码）

会话要成为某工作区的成员，必须同时满足三条：

1. 该会话 id 出现在 `workspace.json` 里该工作区的 `sessionIds` 数组；
2. 会话 header 的 `cwd` 能 `realpath` 规范化成功；
3. 规范化结果**等于**工作区记录的 `path`（且该路径是现存目录）。

代码位置（`@deepseek-ai/dsh-workspace@0.1.5-rc.2`）：

- `lib/index.js:709-727` `indexHeader()`：`realpathNormalize(header.cwd)` + `stat().isDirectory()`；任一步抛错就记 `invalidSessionPaths.set(id, "cwd '…' does not resolve")`。
- `lib/index.js:737-747` `reportFilteredCandidates()`：`if (path === record.path) continue;` 否则**只记一条 warn**：
  ```
  workspace '<id>' filtered session '<id>' from membership: cwd '<…>' does not resolve
  ```
- `lib/index.js:102-104` `get sessionIds()`：对外暴露的成员列表本身就带 `filter(id => sessionPath(id) === record.path)`。
- `lib/index.js:173-191` `mutate()`：**每次写入都会再过滤一遍**并落盘——被剔除的会话不会留在 `sessionIds` 里。

### 2.2 本机实证：日志与数据完全对上

DSH Desktop 的 host 日志里，这条 warn 反复出现（`%APPDATA%\DSH Desktop\logs\host\dsh-2026-09-18.log`）：

```

  filtered session 'session-64ecfd3a-0f2c-43f5-af87-7a559bb15939' from membership:
  cwd 'D:\Users\liaohai1\Desktop\常见问题记录' does not resolve
2026-09-18 11:40:25.322 [W] [workspace-registry] workspace '7381c3cd-b2ad-4db3-8667-b4c2c7012e28'
  filtered session 'session-e4eab95e-4b64-4a17-94f6-23e94e9f2a80' from membership:
  cwd 'D:\obsidian-vaults\项目空间' does not resolve
```

交叉核对 `workspace.json`：

| workspaceId | 登记路径 | 目录是否存在 | 登记会话数 | 结果 |
|---|---|---|---|---|
| `4111d60d-e595-4ec5-a884-9a6264cdc45d` | `D:\Users\liaohai1\Desktop\常见问题记录` | ❌ ENOENT | 4 | 4 个全部被剔除 |
| `7381c3cd-b2ad-4db3-8667-b4c2c7012e28` | `D:\obsidian-vaults\项目空间` | ❌ ENOENT | 2 | 2 个全部被剔除 |

`D:\obsidian-vaults` 现在装的是 `03-工作笔记`、`C01-智能体产品培训课程`、`C07-AI认知与办公效率提升` 等**完全不同的目录名**——说明该目录被**重组/改名**过，旧工作区记录成了孤儿。

→ **可复现结论：把项目文件夹改名、移动或删除，它下面所有会话会从侧边栏消失，而文件仍在磁盘上。**

### 2.3 第二条漏登记成因：一次性收养 + `{cwd}` 形态不登记

即使目录**还在**，仍有大量根会话不在任何工作区的 `sessionIds` 里。本机 71 个。两条代码成因：

**成因一 —— `session/create` 的 `{cwd}` 形态不 attach 工作区。**
`@deepseek-ai/dsh-api-session-controller@0.1.5-rc.2` `lib/index.js:572-591`：

```js
if (request.workspaceId !== undefined && request.cwd !== undefined)
  throw new RemoteError("gateway/bad-request", "session.create accepts workspaceId or cwd, not both", {});
...
const cwd = workspace?.path ?? request.cwd ?? this.defaultCwd;
...
await workspace.attachSession(sessionId);   // ← 只有 workspace 存在时才 attach
```

即：**用 `{cwd}` 建会话，cwd 记对了，但不会进任何工作区的成员表。** 本仓自己的代码注释已经记过这个坑（`src/serverManager.ts:776-777`）：

> NOTE: session.create MUST use workspaceId — the {cwd} form creates a session whose cwd is right but does NOT attach it to workspace.sessionIds

**成因二 —— 历史收养只跑一次，之后不自愈。**
`@deepseek-ai/dsh-workspace@0.1.5-rc.2` `lib/index.js:344-347`：

```js
if (!this.state.initialized) {
  ...
  await this.bootstrap(headers);   // 按 cwd 分组、补建/补并工作区
}
```

而 `bootstrap()` 结束时会写 `initialized: true`（`:662-666`）。本机 `workspace.json` 的 `global.initialized` **已经是 `true`**：

- 收养逻辑**再也不会执行**；
- 之后用 `{cwd}` 形态建出来的根会话**永远不会被补登记**；
- 没有任何"自愈"路径——必须由客户端显式 `attachSession`。

**对照**：全局 `session/list`（不走工作区闸门）会返回冷会话，只要求 `header.cwd !== undefined`（`dsh-api-session-controller/lib/index.js:1831-1846`）。所以这些会话**在数据层是"可见"的，只是工作区侧边栏不列它们**。

## 4. 为什么"两端表现不同"（回答 Q1 的完整版）

存储层没有分叉。差异来自三处叠加：

1. **默认工作区不同**：扩展把面板钉在 IDE 工作区上；desktop 记住自己的选择、且能切到任意工作区。同一批会话，两端默认看到的子集本来就不一样。
2. **剔除规则对两端一视同仁，但暴露面不同**：被剔除的会话在两端都不出现在对应工作区下；desktop 能让你发现"某个工作区空了"，扩展侧则表现为"这个文件夹没有历史"。
3. **desktop 独有的额外故障**（本机日志实证，见 `04` §F7）：
   - 投影缓存写失败 → `cache stays stale`（`EPERM ... rename ... .tmp -> <id>.json`，`logs\dsh-2026-09-16.error.log:17`）；
   - 超大投影缓存被**隔离改名**（阈值 134 217 728 B，`dsh-plugin-desktop/lib/main.js:3489-3520`）；
   - 渲染进程看门狗超时、自动恢复耗尽（`logs\dsh-2026-09-18.error.log`）；
   - **Safe Mode 会用另一个 home**（`main.js:3685`、`:3700-3708`）→ Safe Mode 下看到的是另一套近乎空的库，容易误判成"历史丢了"。

## 5. 影响面与严重级别

| 项 | 评估 |
|---|---|
| 数据安全性 | ✅ **无数据丢失**。386 个会话头部全部解析成功，0 失败；不可见的会话 JSONL 完整在盘上 |
| 可恢复性 | ✅ 属"登记问题"而非"存储问题"：代码上，只要目录以**同一路径**重新出现（成员校验只要求路径存在，`dsh-workspace/lib/index.js:709-727`），登记条目就重新通过校验；`workspace.json` 里那 6 条登记**实测仍在**。⚠️ **恢复动作本身未实测**（本次取证全程只读） |
