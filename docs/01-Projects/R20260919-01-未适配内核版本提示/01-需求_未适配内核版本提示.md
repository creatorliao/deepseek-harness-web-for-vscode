# 未适配内核版本提示 — 需求（req）

**日期**: 2026-09-19
**来源**: 用户 2026-09-19 直接提问（"版本门要不要调整"）→ 同日确认方向 **S3** 与时机（见 §3 D1/D2）
**状态**: ⏳ 待用户批准

> 本文件只定义 **做什么（WHAT）** 与 **验收标准**，不含实现细节（HOW）。

---

## 0. 审题（问题界定卡）

| 项 | 内容 |
|---|---|
| **一句话问题陈述** | 扩展**读的是本机全局安装的 dsh**、能力跟着全局版本走，但扩展运行时**只知道一条硬编码的"太低就拒绝"下限**，对"**比我们验证过的更新**"完全无感知——于是上游一改内部形态，用户拿到的是白屏或静默失效，而不是"你这个内核版本我们没适配"。 |
| **现状（已取证）** | ① 下限硬门：`MIN_DSH_VERSION = "0.1.2-rc.1"`，判定 `compareVersions(version, MIN) < 0` → **只拒绝更旧的版本**（`src/serverManager.ts:92, 479-485`）；② **无上限**：`README.md:62` 原话"对更新的 dsh 版本未设硬上限"；③ 扩展运行时**不知道** `verified[]`——`docs/` 不进 vsix（`package.json:23-34` 白名单），`dsh-baseline.json` 只被开发脚本 `scripts/check-dsh-latest.js` 读取，`src/` 无任何引用；④ 现有唯一的版本提示是**升级提示**（当前 < 最新），不是"未适配"提示（`src/launcherView.ts:515-526, 616-627`；`src/versionCheckService.ts:100-111`；`src/versionCheck.ts:52-59`）。 |
| **递交物长相** | ① 本需求文档；② 方案文档（用户批准后写）；③ 实施计划（方案批准后写）；④ 主题夹 `00-README.md` 索引。 |
| **判定标准** | 见 §6。核心两条：**用户能在不查文档、不开开发者工具的前提下得知"内核未适配"**；**"最新已验证版本"只有一个源，扩展侧不手写第二份版本号**。 |
| **明确不做** | 不抬高也不删除硬版本下限；不新增用户可配置开关；不把 boot `rev` 当版本判据；不修 dist 缓存判据失配（独立议题）；不改 `check:dsh` 的跟踪渠道。 |

## 1. 背景

- **方向澄清（本次结论的前提）**：`MIN_DSH_VERSION` 是**下限**，它挡的是"**太旧**"的 dsh；**新版永远不会被它挡**。因此"上游迭代快"这个痛点**不能靠调整下限解决**——抬高下限只会挡掉更多老用户。缺的是**上限侧**。（取证见 [04-Archives 调查报告](../../04-Archives/20260919-01-插件运行的内核与版本跟随关系调查.md) §2.5、§4）
- **代价已有实证**：上游一个月内 3 次破坏性变更（`0.1.0-rc.8` / `0.1.1-rc.2` / `0.1.2-rc.1`）都让内嵌面板不可用，**报错文案却都是同一句 "Failed to load plugins"**（[上游兼容规范](../../02-Areas/20260914-06-上游兼容规范_跟随最新官方DSH.md) §7 教训 1）。更近的一例：`themeSync` 的 RPC 面在 `0.1.2-rc.1` 就断了，**藏了 5 个版本（v0.3.4–v0.5.3）才被发现**（[13-修复_主题同步静默失效](../R20260820-01-上游DSH版本适配/13-修复_主题同步静默失效_dsh0.1.2起RPC未跟上.md)）。
- **`verified[]` 的含义**：`dsh-baseline.json` 的 `verified[]` 是"我们**实测过**的版本"清单，当前 4 条（`0.1.2-rc.1` / `0.1.5-rc.1` / `0.1.5-rc.2` / `0.1.6-alpha.2`）。它**不是**"上游发过的版本"清单，也不是"我们承诺支持"的完整声明——**这正是需要让用户看见的东西**。

## 2. 范围（4 项需求）

### R1 — 运行时感知"内核版本超出已验证范围"

当**运行中的** dsh 版本高于本扩展已实测通过的最高版本时，用户必须能**在不查文档、不开开发者工具、不读日志**的前提下得知这一点。

**验收**：
- 判定口径**明确且可判定**：以"运行中的 dsh 版本 vs `verified[]` 的最高版本"比较；**相等不算未适配**（等于我们验过的就是适配过的）；
- 提示**不阻断**启动与使用——用户可继续用当前内核（这是"软门"，与下限的硬拒绝语义明确区分）；
- 版本**无法解析**时（自定义构建、非 semver 字符串）**不得误报**；宁可沉默，不可误报；
- 提示内容至少包含：**当前版本**、**我们验证过的最高版本**、**一个可执行的下一步**（例如回退到已验证版本）；
- 提示在**每次内核版本变化后**都能重新出现（换了内核版本就是新的事实，不能被上一次的"我知道了"永久吞掉）。

### R2 — 单一真源：扩展侧不得手写第二份版本号

"最新已验证版本"必须仍以 `dsh-baseline.json` 的 `verified[]` 为**唯一**来源。

**验收**：
- 扩展侧**不存在**手工维护的"最新已验证版本"字面量；
- 上游适配完成、基线更新后，扩展侧的判定结果**随之变化**，无需人工再改一处版本号；
- 若基线与其派生数据不一致，**机器能发现**（构建期或测试期门禁），而不是靠人记得；
- 不产生与 `dsh-baseline.json` 平行维护的第二份真源（[文档与 PARA 规范](../../02-Areas/20260914-03-文档与PARA规范.md) §4）。

### R3 — 不回归既有版本行为

**验收**：
- **下限硬门行为不变**：低于 `0.1.2-rc.1` 仍**拒绝启动**并给出升级提示（`src/serverManager.ts:479-485`）；
- **既有升级提示行为不变**：当前版本低于 registry 的 `latest`/`next` 时，仍提示可升级（`src/launcherView.ts:616-627`）；
- 新提示与既有升级提示**不互相覆盖**。两者**可能同时成立**（例：registry `latest` 已到 `0.1.7`、我们最高只验到 `0.1.5-rc.2`、用户跑 `0.1.6`——既"有更新可升"又"当前这个版本我们也没适配"），此时呈现必须**不矛盾**；
- 两者**都不成立时不得出现任何提示**（用户跑的是已验证版本且已是最新）；
- 已有单测全绿，且**为本次新判定补回归测试**（含"相等不报"、"不可解析不报"两个边界）。

### R4 — 落盘与登记

**验收**：
- 需求、方案、实施计划落在本主题夹，命名与编号符合[文档与 PARA 规范](../../02-Areas/20260914-03-文档与PARA规范.md)；
- 主题夹 `00-README.md` 说明每份文件记什么、当前状态与未闭环项；
- 实施完成后按[上游兼容规范](../../02-Areas/20260914-06-上游兼容规范_跟随最新官方DSH.md) §8 与 [维护时机](../../02-Areas/20260914-03-文档与PARA规范.md) §8 同步 `README.md` / `README.en.md` / `CHANGELOG.md`；
- `npm run check:docs` 通过。

## 3. 决策项

| # | 决策项 | 决定 | 来源 |
|---|---|---|---|
| D1 | 方向 | **S3：下限不动 + 补上限软门** | 用户 2026-09-19 选择（三选一，另两选为"保持现状只订正文档"与"下限改软警告"） |
| D2 | 下限 `MIN_DSH_VERSION` 是否调整 | **不调整**（既不抬高也不删除）。理由：它的技术理由（0.1.2 前后 API 面不同）**永久成立**，且它管的是"太旧"，与"迭代快"无关 | 用户 2026-09-19 选择；事实见 §1 方向澄清 |
| D3 | 动手时机 | **等 v0.6.0 收口后再动** | 用户 2026-09-19 选择 |
| D4 | 落盘位置 | **新建 `R20260919-01-未适配内核版本提示`** | 见下 |
| D5 | 阻断性 | **软门**——提示，不阻断启动与使用 | 与 D1 同源；硬门语义已由下限占用 |

**D3 的理由（协调风险）**：工作树存在**未提交的 v0.6.0**（`package.json` 已 `0.6.0`；`src/serverManager.ts`、`README.md`/`README.en.md`、`CHANGELOG.md`/`CHANGELOG.en.md`、`dsh-baseline.json`、`package.nls.json`、`src/i18nStrings.ts` 等均已修改）。本需求实施必然触碰其中多个文件，**现在动会与在飞改动混在一起、提交时无法分离**。

**D4 的理由（避免平行开夹）**：`R20260820-01-上游DSH版本适配` 是**现场证据夹**（其 `00-README.md` 自述为历史 + 现场记录）；`R20260918-04-上游0.1.6-alpha差距与升级` 是**一次性升级**的差距分析与方案。本项是**长期机制**，与两者定位都不同，且需要自己的管线槽位。三夹分工写进本夹 `00-README.md` 并互相链接，**同一事实只维护一份**。

## 4. 非目标

| # | 项 | 原因 |
|---|---|---|
| N1 | 抬高或删除 `MIN_DSH_VERSION` | D2；且抬高会挡掉更多老用户，对"新版未适配"零帮助 |
| N2 | 新增用户可配置开关（如"忽略未适配提示"） | 未被要求；先验证默认行为是否够用（[AGENTS.md](../../../AGENTS.md) §2 最小实现） |
| N3 | 用 boot `rev` 做版本判据 | 已实测它不是版本指纹——同版本、同 `DSH_HOME` 连续两次启动得到不同值（[03-分析 §3 P5](../R20260918-04-上游0.1.6-alpha差距与升级/03-分析_0.1.5-rc.2到0.1.6-alpha.2差距.md)） |
| N4 | 修 dist 缓存 `rev` 判据失配（每次重启可能重下整棵 dist 树） | 独立议题，已登记在 P5；不静默并入本轮范围 |
| N5 | 改 `check:dsh` 的跟踪渠道（是否纳入 `alpha`） | 另有候选改进（待办总表 G-14 遗留 / G-22），与本需求无关 |

## 5. 约束

- **C1 事实优先**：现状/差距/协议类结论必须带来源（`文件:行号` 或"<版本> 实测"）；**没读过的不写结论，没测过的不写事实**（[文档与 PARA 规范](../../02-Areas/20260914-03-文档与PARA规范.md) §2）。
- **C2 不弱化既有围栏**：不得建议弱化 DSH 的 `/api` 信任围栏、不得建议 `--host 0.0.0.0`（[AGENTS.md](../../../AGENTS.md) §7）。
- **C3 不制造第二份真源**：`dsh-baseline.json` 仍是唯一机器可读源（R2）。
- **C4 版本号不是权威**：任何"看版本号决定行为"的判定都要承认上游可能 CLI 版本与依赖树版本错配（[上游兼容规范](../../02-Areas/20260914-06-上游兼容规范_跟随最新官方DSH.md) §7 教训 2）；方案阶段需说明本判定在错配下的表现。
- **C5 文档门禁**：改完 `docs/` 必须跑 `npm run check:docs`。
- **C6 不混提**：实施时不得把在飞的 v0.6.0 改动一并提交（D3）。

## 6. 验收总则

- **完成 = R1 + R2 + R3 + R4 全部验收通过**。
- **用户视角判据**：一个"刚从上游装了新版 dsh"的用户，打开面板时应当**知道**"这个内核版本本扩展还没适配"，并能看到下一步该做什么——而不是看到白屏、或看到一切正常但功能悄悄没了。
- **不误报优先于不漏报**：版本不可解析、判定依据缺失时，宁可不出提示（R1 验收 3）。
- 未实测项必须在文档中显式登记为"待验证"，不得以推测充当结论。
