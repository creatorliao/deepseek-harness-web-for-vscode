### 2.4 根因（代码级，可直接对照）

`src/documentAssembly.ts` 的两处判据**写死了"根绝对"**，对 `0.2.0-rc.1` 一条都匹配不上：

| # | 代码 | 现有判据 | `0.2.0-rc.1` 实际 | 后果 |
| --- | --- | --- | --- | --- |
| 1 | `PLUGIN_PRELOAD_RE`（旧 `:69`；修复后为 `PLUGIN_REF_RE` `:78`） | `(src\|href)="(\/plugins\/[^"]+)"` —— 要求**前导 `/`** | `src="plugins/??…"`（无前导 `/`） | 引导脚本**不被绝对化**，原样留在文档里 |
| 2 | `rewriteBootPluginUrls`（旧 `:127-132`） | `if (entry.url?.startsWith("/"))` | **65 个 `entries[]` + 3 个 `batches[]` 的 url 全部不以 `/` 开头** | 整个插件图**原样返回**（函数等于空转） |

**为什么这必然导致截图里那句话**：组装后的 webview 文档 origin 是 `vscode-webview://…`，
`<base href="./">` 把相对 `plugins/??…` 解析成 webview 自己的目录 → 404 →
`__ModuleLoader__` 的 `pendingQueue` 里永远收不到 `@deepseek-ai/dsh-client-modules` 的注册 →
`create()` 在 `dsh-client-modules/lib/client.js` 内抛出
`client-modules: HTML did not preload @deepseek-ai/dsh-client-modules/client.js`（该错误原文已在留档 HTML 的引导脚本里逐字核对到）。

> **报错文案与根因无关**：文案说"没有 preload"，而现场 HTML 里 preload 标签**是存在的**（只是 URL 相对）。
> 这正是本仓《上游兼容规范》反复强调的那条：**不要用报错文案判断根因**。

## 六、给接收方的提示

1. **不要用报错文案判断根因。** 本次是第 4 次出现「Failed to load plugins」文案，
   前三次根因分别是：preload 标签未绝对化（rc.8）、boot 正则失配（0.1.1-rc.2）、dist 布局 + 认证全换（0.1.2-rc.1）。
   **本次根因是"上游把插件 URL 从根绝对改成文档相对"**，与文案字面意思不同。
2. **修复方向是"把判据从写死绝对形态改成接受两种形态"**，不是"把 0.2 的形态抄进来"——
   否则下次上游再改回来就又坏一次。落点仅 `src/documentAssembly.ts` 两处。
3. **`<base href="./">` 不必强行改写成 `/`**：资产引用已被改写成同源 webview URI，插件引用绝对化后，
   页面里不再有依赖 `<base>` 的相对引用；改 `<base>` 属于扩大改动面。
4. **待用户确认的推断**：「0.1.7 / 0.2」的版本号对应关系（见 2.1 的 ⚠️）未经逐字确认。
5. **V4b 仍需用户真机确认**——机器已能判定"插件加载这一环修好了"，但整块面板在真实 webview 里长什么样，只有装机能拍板。
