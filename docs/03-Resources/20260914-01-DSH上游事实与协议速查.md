## 0. 上游基本信息

| 项 | 值 |
|---|---|
| npm 包 | `@deepseek-ai/dsh` |
| 官方仓库 | https://github.com/deepseek-ai/deepseek-harness |
| 安装 | `npm i -g @deepseek-ai/dsh`（或 `npx -y @deepseek-ai/dsh@latest`） |
| 查询最新版本 | `npm view @deepseek-ai/dsh dist-tags` 或 `npm run check:dsh` |
| 发布通道 | `latest`（稳定）、`next`（预发布）、`alpha`（实验，**不纳入适配基线**） |
| 状态目录 | 默认 `~/.dsh`，可用环境变量 `DSH_HOME` 覆盖 |
| 本仓库硬版本下限 | `0.1.2-rc.1`（`src/serverManager.ts` 的 `MIN_DSH_VERSION`；更低版本直接拒绝启动） |

**2026-09-14 实查**：`latest=0.1.5-rc.1`、`next=0.1.5-rc.2`、`alpha=0.1.5-alpha.2`。

### ⚠️ 环境陷阱：`dsh --version` 未必是你以为的那个 dsh

2026-09-14 实测本机：

| 你查的 | 实际是 | 版本 |
|---|---|---|
| `dsh --version`（PATH 上的 `dsh`） | 解析到 **DSH Desktop 的 shim**：`%AppData%\DSH Desktop\host-commands\desktop\bin\dsh.cmd` | `0.1.2-rc.1` |
| npm 全局包本体 | `%AppData%\npm\node_modules\@deepseek-ai\dsh` | **`0.1.5-rc.1`** |
| 该包的嵌套依赖（前端与 `dsh-client-ui-*`） | 同上包内 `node_modules` | **`0.1.5-rc.2`** |

→ **排查版本问题时必须说清是"PATH 上的 dsh"还是"npm 全局包"**；扩展的 `resolveDshPath()` 走的是自己那套候选顺序（见 [启动流程教程](../01-Projects/R20260914-02-DSH内嵌原理与教程/03-教程_启动流程全链路.md) 阶段 ②），与 shell 的 PATH 解析**可能不是同一个**。

## 1. 进程启动与输出

| 事实 | 核实版本 | 备注 |
|---|---|---|
| `dsh web --port 0` 由 OS 分配端口，stdout 打印一行启动地址 | `0.1.0-rc.6` 实测 | — |
| 启动行格式 `dsh web: http://127.0.0.1:<port>` | `0.1.0-rc.6` | **已被推翻** |
| 启动行格式 `dsh web: http://127.0.0.1:<port>/?token=<launchToken>` | `0.1.2-rc.1` | **现行**；扩展靠这一行同时拿到端口与启动令牌 |
| `dsh web` 默认打开外部浏览器；`--no-open` 关闭 | `0.1.0-rc.8` 起 | rc.8 之前无此 flag（传了会启动失败，故必须门控） |
| SIGTERM 优雅退出；DSH 自带 5s 宽限 | `0.1.0-rc.6` 实测 | 扩展侧再加 6s SIGKILL 兜底 |
| 默认工作区 = 子进程 `cwd` | `0.1.0-rc.6` 实测；`0.1.2-rc.1` 仍成立 | 扩展 spawn 时传 `cwd: workspaceFolder` 即可 |

### ⏱️ 启动耗时（决定超时预算，2026-09-14 本机实测）

**dsh 每次调用都要加载整棵插件树**，因此所有与它交互的超时都不能按"快 CLI"设。

| 命令 | 实测耗时 | 备注 |
|---|---|---|
| `dsh --version` | **~320 ms** | 唯一一个快的 |
| `dsh web --help` | **4290 / 4396 / 5295 ms** | 曾被 5s 超时切成偶发失败 |
| `dsh web --port 0` 打印启动行（`0.1.2-rc.1`） | 4348 / 4385 / 4567 ms | — |
| `dsh web --port 0` 打印启动行（`0.1.5-rc.1`） | 7379 / 7707 / 7862 ms（另一次 9266 ms） | **0.1.5 明显比 0.1.2 慢近一倍** |

→ 扩展侧相应预算（2026-09-14 调整）：就绪 **60s**、探测 **20s**。详见 [13-修复_dsh启动超时与自动探测失效.md](../01-Projects/R20260817-01-桥架构与IDE内嵌/13-修复_dsh启动超时与自动探测失效.md)。
复现命令：`npm run diagnose:dsh`。

⚠️ **脆弱点**：启动行的正则解析依赖上游输出格式，已变过一次。任何解析失败都必须**大声报错**，不能静默。

## 2. `/api` 信任围栏

| 请求形态 | 结果 | 核实版本 |
|---|---|---|
| Node 式请求（无 `Origin`、无 `sec-fetch-site`） | **200**（放行） | `0.1.0-rc.6` 实测 |
| 同源浏览器请求（`Origin` = Host） | **200** | `0.1.0-rc.6` 实测 |
| webview 式（`Origin: vscode-webview://…` + cross-site） | **403** | `0.1.0-rc.6` 实测 |
| 无 `Origin` 但 `sec-fetch-site: cross-site` | **403** | `0.1.0-rc.6` 实测 |
| 静态 `/plugins/<id>/client.js` | **200**（不受围栏影响） | `0.1.0-rc.6` 实测 |

**结论（架构基石）**：webview **不能**直连 `/api`，必须由扩展宿主以**普通 Node 请求**代发。这是本项目"传输桥"方案的立论依据。

> `0.1.2-rc.1` 之后围栏之上又加了**认证层**（见 §3）。围栏本身的行为在 `0.1.5-rc.2` 上未逐条复核。

## 3. 认证（0.1.2-rc.1 起）

| 事实 | 核实版本 |
|---|---|
| `/` 与**全部** `/api`（含 WebSocket 升级 `/api/remote.mux`）要求浏览器会话 Cookie；无 Cookie 一律 **401** | `0.1.2-rc.1` |
| Cookie 名形如 `dsh-auth-<sha256(authority)>`，由启动 URL 里的 `?token=<launchToken>` 换发，有效期约 30 天 | `0.1.2-rc.1` |
| 扩展必须在**标记服务就绪之前**完成令牌→Cookie 交换，并把 Cookie 附加到每个代发请求 / WS 升级 / 面板组装 | `0.1.2-rc.1`（v0.3.4 的修复要点） |
| "Open in Browser" 必须打开**带 token 的** URL，否则用户落到 401 页面 | `0.1.2-rc.1` |

## 4. RPC 协议

| 事实 | 核实版本 |
|---|---|
| 端点形态 `POST /api/<namespace>/<method>`，请求体信封 `{type:"client-request", rpcId, method, payload:{args}}` | `0.1.2-rc.1`（Typert 重构后） |
| 旧的 `POST /api/<method>` 形态已废弃 | 被 `0.1.2-rc.1` 推翻 |
| `/api/workspace.list` **404**；工作区枚举改走 `workspace/follow` 流基线 | `0.1.2-rc.1` |
| `session/list` 的 `agentPreset` 移入 `projections.values`；`title` 亦在该处（未命名为 `null`） | `0.1.2-rc.1` / `0.1.0-rc.7` |
| `session/create {request:{cwd}}` → `{sessionId}`；`workspaceId` 与 `cwd` 互斥 | `0.1.2-rc.1` |
| 会话重命名方法为 `session/rename`（历史上出现过 `session.rename` 点号形态） | `0.1.2-rc.1` |
| 归档为 **append-only**：只追加 `archivedSessionIds`，不移除 `workspace.sessionIds`；无 `session.delete`、无 unarchive | `0.1.0-rc.7` |

⚠️ **脆弱点**：方法名的点号 / 斜杠形态与字段位置都变过。所有 RPC 调用点都要有回归测试。

## 5. boot manifest 与 dist 布局

| 事实 | 核实版本 |
|---|---|
| `<head>` 注入 boot 清单，形态 `window.__DSH_BOOT__ = {…}` | `≤ 0.1.1-rc.1` |
| 形态改为 `globalThis["__DSH_BOOT__"] = {…}` | `0.1.1-rc.2` |
| HTML 里出现**阻塞式 preload** `<script src="/plugins/…">`（rc.6/rc.7 无） | `0.1.0-rc.8` |
| 前端 dist 引用改为相对路径 `./assets/…`，配合 `<base href="/">` | `0.1.2-rc.1` |
| boot 清单新增 `batches[]` 段 | `0.1.2-rc.1` |
| preload 变为 mux 形态 `/plugins/??pkg/client.js,…&rev=` | `0.1.2-rc.1` |

**扩展侧的改写链**（`src/documentAssembly.ts`）：把 boot / preload / batches 里的资产 URL 绝对化，并以**同源** webview 资源加载（`asWebviewUri`），避免裸跨源 CORS。

⚠️ **最大脆弱点**：整条链建立在"匹配上游 HTML 形态"之上，而前缀已变一次、结构又变一次。要求：① 匹配失败必须大声失败；② 每种已知形态都有锁定测试；③ 形态一变就往本文件与 baseline 里登记。

## 7. 维护规则

1. 任何新事实**必须**写明核实版本与核实方式（实测 / tarball 实证 / 源码行号）。
2. 被后续版本推翻的事实**不要删**，加"已被推翻"标记——它解释了历史代码为什么长那样。
3. 每次上游适配完成后，把该版本的核对结论更新到本文件相应小节。
4. 与 `dsh-baseline.json` 冲突时，**以实际实测为准**，并立即修 baseline。
