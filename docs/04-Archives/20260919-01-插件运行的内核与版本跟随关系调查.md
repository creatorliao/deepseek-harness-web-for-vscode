## 0. 结论（先看这段）

| 问题 | 回答 | 一句话依据 |
|---|---|---|
| 1. 读本机已装 dsh，还是插件自带内核？ | **读本机已装的。** 扩展不打包、不安装、不锁定 dsh 版本 | vsix 白名单里没有 dsh（`package.json:23-34`），`dependencies` 只有 `ws`（`:163-165`）；启动时 `spawn` 的是本机解析出来的二进制（`src/serverManager.ts:461-462, 518-523`） |
| 2. 只做了 UI，全局升级能力就跟着变？ | **"能力跟着全局版本走"——对。** **"仅仅是 UI"——要修正**：是"UI ＋ 一层会随上游变形的适配层"，能力白拿的代价是上游破坏性变更会直接打穿这层适配 | 内嵌界面是**从运行中的 dsh 服务器现抓**的官方前端（`src/documentAssembly.ts:183-217`）；宿主 RPC 全是上游协议（`src/serverManager.ts:721-761`）。历史上一月内 3 次破坏性变更让面板不可用 |

**给用户的实用结论**：
- 想换内核版本 → 只需 `npm i -g @deepseek-ai/dsh@<版本>`，扩展侧**没有版本号可改**，也没有开关。
- 升级后**能力自动跟进**（新 UI / 新工具 / 新模型都会出现在面板里），但**必须回归一次内嵌面板**——上游改过内部形态就会静默失效或直接白屏（见 §3.5、§3.6）。
- 低于 `0.1.2-rc.1` 会被**明确拒绝启动**，不会进入半坏状态（`src/serverManager.ts:92, 479-485`）。

## 1. 问题一取证：它读的是本机已安装的 dsh

### 1.1 扩展里根本没有 dsh 的副本

| 检查项 | 结果 | 证据 |
|---|---|---|
| 运行期依赖 | 只有 `ws` 一个包 | `package.json:163-165` |
| vsix 打包白名单 | `out/**`、`media/**`、`README*`、`CHANGELOG*`、`LICENSE`、`package.nls.json`、`node_modules/ws/**` | `package.json:23-34` |
| 本仓 `node_modules/@deepseek-ai/` | **不存在**（实机检查输出 `(none - no bundled dsh)`） | 2026-09-19 实测 |
| 是否有"下载/安装 dsh"的代码 | **没有**。全仓 `npm i -g` 只出现在**报错提示文案**与**推荐命令字符串**里，没有任何 `execFile('npm', ['install', …])` | `src/serverManager.ts:480, 555`；`src/versionCheck.ts:82-89` |

> 对照：早期架构提案里曾设想"第 ③ 顺位：扩展内置依赖 `@deepseek-ai/dsh`（随 vsix 打包）"（`docs/01-Projects/R20260817-01-桥架构与IDE内嵌/09-架构提案_by-deepseek.md:220`）。**该设想未落地**，现行代码只有 ① 设置路径 → ② 本机全局/PATH，没有第 ③ 条内置路径。

### 1.2 启动时怎么找到本机那个 dsh

`resolveDshPath()` 的探测顺序（`src/serverManager.ts:351-380`）：

1. 环境变量 `$DSH_BIN`（`:362`）
2. **npm 全局 prefix** 下的 `dsh`（`:363`；prefix 由 `npm prefix -g` 现取，`:255-271`）
3. Homebrew `/opt/homebrew/bin`、`/usr/local/bin`（非 Windows，`:364-365`）
4. `~/.npm-global/bin`（`:366`）
5. nvm：`~/.nvm/versions/node/*/bin/dsh`（非 Windows，`:367`）
6. **npx 缓存**：Windows `%LocalAppData%\npm-cache\_npx\*\node_modules\.bin\dsh`，其他平台 `~/.npm/_npx/*/…`（`:368-373`）

其中 `*` 段会展开成**全部匹配**并取 **mtime 最新**的那个（`firstExisting`，`:219-247`）——因为 npx 缓存里会并存多个 dsh 版本，取最新是合理选择（注释原文如此）。

**用户设置优先**：`deepseekHarness.dshPath`（`package.json:96-100`）由 `configuredDshPath()` 读取并 trim，空白视为未配置（`src/commands.ts:19-23`），经 `dshStartOptions()` 统一注入（`:30-33`）——注释明确写"所有启动路径共用，避免配置在某些路径被静默忽略"。

**本机实测**：`Get-Command dsh` → `D:\Users\liaohai1\AppData\Roaming\npm\dsh.ps1`；`npm ls -g --depth=0` → `@deepseek-ai/dsh@0.1.5-rc.2`；`dsh --version` → `0.1.5-rc.2`。即命中的是**第 2 顺位 npm 全局**。

### 1.3 启动动作就是 spawn 那个二进制

`DshServerManager.start()`（`src/serverManager.ts:456-592`）：

```ts
const resolved = resolveDshPath();                       // :461
const bin = opts.dshBin ?? resolved.path ?? "dsh";       // :462
const version = resolveDshVersion(bin);                  // :467  → 跑 `dsh --version`
...
const args = ["web", "--port", "0"];                     // :498
if (passNoOpen) args.push("--no-open");                  // :506
const child = spawn(spawnBin, args, { cwd, env, … });    // :518-523
```

启动行由 dsh 自己打到 stdout，扩展用正则解析端口与启动令牌：

```
dsh web: http://127.0.0.1:<port>[/?token=<launchToken>]
```

`URL_LINE_RE`（`:67-72`）；带 token 时先 `GET /?token=` 换浏览器会话 Cookie（`exchangeCookie`，`:628-667`）再宣告 ready。

→ **面板背后跑的就是本机那个 dsh 进程**，不是扩展内的副本，也不是扩展拉起的另一份安装。

### 1.4 唯一的版本干预是"下限硬门"，不是"版本锁定"

| 机制 | 位置 | 行为 |
|---|---|---|
| 硬版本下限 | `MIN_DSH_VERSION = "0.1.2-rc.1"`（`src/serverManager.ts:92`） | 低于它 → `dsh x.y.z is not supported…`，`setState("error")` 并 reject（`:479-485`），**不进入半坏状态** |
| 版本上限 | **无** | README 原话："对更新的 dsh 版本未设硬上限，但上游迭代极快——升级 dsh 后建议回归一次内嵌面板"（`README.md:62`） |
| 机器可读基线 | `docs/02-Areas/dsh-baseline.json:4-5` | `minDshVersion: "0.1.2-rc.1"`，注释指明它必须与 `src/serverManager.ts` 同步 |

### 1.5 连"升级建议"都不自动执行

`versionCheckService.ts` 每 24h 查一次 npm registry（`REGISTRY_URL = https://registry.npmjs.org/@deepseek-ai/dsh`，`:13`；24h 门 `:46`），命中新版本后弹 QuickPick，**只把命令预填进终端**：

```ts
const terminal = vscode.window.createTerminal("DeepSeek Harness upgrade");
terminal.show();
terminal.sendText(picked.command, false);   // prefill only — user presses Enter
```

（`:163-166`，注释原文 "NEVER executes the command automatically"）

推荐命令按**二进制路径**反推安装方式（npx 缓存 → `npx -y …`，npm 全局 → `npm i -g …`，`$DSH_BIN` 自定义 → 返回 null 不猜），见 `src/versionCheck.ts:74-91`。

## 2. 问题二取证：能力确实跟着全局版本走

### 2.1 连界面本身都是从那个 dsh 现抓的

`assembleDocument()`（`src/documentAssembly.ts:183-249`）流程：

1. `GET <serverBase>/` 拿 **dsh 服务器吐出的** `index.html`（`:193-195`）
2. 用 boot manifest 里的 `"rev"` 当缓存键（`extractRev`，`:107-111`）
3. **rev 变了** → `rmSync` 清空缓存目录 → 把 `/assets/**` 整棵树拉下来（`downloadTree`，`:256-305`），并改写 CSS `url()` 与 shell bundle 的相对 import
4. 改写资源引用为**同源 webview URI**（`:224-228`），把 boot manifest 的插件 URL 绝对化（`:118-147`），注入 CSP 与桥脚本（`:233-246`）
5. 缓存落盘在 `globalStorage/<扩展 id>/dsh-dist/`（`src/dshUi.ts:90-93`）

→ 内嵌的**不是扩展自带的界面，就是那个 dsh 版本自带的官方 Web 前端**。
**本机实测**：`rev.txt` = `aa61aa4746cc`（VS Code 与 Cursor 的 globalStorage 各一份），缓存树里有 `assets/index-BKQ_L1z6.js`、`assets/vendor-CCJJTK99.js`、`assets/fonts`、`assets/langs` 等。

> 设计含义：扩展**不持有 UI**，所以上游一改 UI，面板跟着变——这正是"能力跟着版本走"的最直接体现，也是"零 fork"（不重写官方前端）的落地方式（`docs/02-Areas/20260914-09-产品定位与边界.md:50`）。

### 2.2 宿主 RPC 也全是那个 dsh 的 API 面

| 扩展动作 | 打的接口 | 位置 |
|---|---|---|
| 通用 RPC | `POST /api/<namespace>/<method>`，body `{type:"client-request", rpcId, method, payload:{args}}` | `src/serverManager.ts:721-746` |
| 工作区枚举 | `workspace/follow` 流首帧（0.1.2 起无 unary `workspace.list`） | `:754-761`、`openStreamFirstFrame` `:142-217` |
| 会话列表 / 建会话 / 改名 / 归档 | `session/list`、`session/create`、`session/rename`、`workspace/archiveSession` | `:764-869` |
| 认证 | 启动令牌 → authority 绑定 Cookie | `:628-667` |

会话侧边栏、工作区对齐、多面板编排这些"扩展功能"，**全部建立在上述上游协议之上**——上游一改协议，这些功能一起断。

### 2.3 版本不止一个：三个"版本位"（外加一个**不是**版本位的 `rev`）

`docs/02-Areas/20260915-01-内核升级最佳实践.md:14-18` 定义了三个版本位，本次调查**补第 4 位，但复核后确认它不成立**，故最终口径是"三个版本位 + 一个陷阱"：

| # | 版本位 | 是什么 | 本机实测（2026-09-19） | 怎么读 |
|---|---|---|---|---|
| 1 | **CLI 包版本** | `@deepseek-ai/dsh` 这个 npm 全局包自身 | `0.1.5-rc.2` | `dsh --version` |
| 2 | **依赖树版本** | `dsh-web-frontend` / `dsh-client-*` 等被 caret 范围解析出的实际版本 | `dsh-web-frontend`、`dsh-client-modules`、`dsh-client-ui-layout`、`dsh-client-ui-conversation` **均 0.1.5-rc.2**；树内共 **239 个** `@deepseek-ai/*` 包 | `node -p "require('<全局>/@deepseek-ai/dsh/node_modules/@deepseek-ai/<pkg>/package.json').version"` |
| 3 | **`$DSH_HOME` 运行时树** | `$DSH_HOME/profiles/node_modules/@deepseek-ai/dsh`——dsh 自己拉起的 profile 树 | `DSH_HOME=D:\Users\liaohai1\.dsh`；该处 dsh = `0.1.5-rc.2`（`profiles/` 下有 `web` / `desktop` / `headless` / `work` / `acp` / `sdk` 等） | 读包内 `package.json` |
| ➖ | **dist boot manifest `rev`** | **不是版本位。** 2026-09-18 实测：**同版本、同 `DSH_HOME`、连续两次启动**得到**不同** rev（`2e3cc5aae766` / `474a72b44376`；HTML 均 27,660 B）——它是上游**每次服务进程启动重新生成**的 | `aa61aa4746cc`（扩展侧 `dsh-dist/rev.txt`，仅供缓存比对） | `GET /` 的 HTML 里 `"rev":"…"`；`src/documentAssembly.ts` 的 `extractRev` |

> ⚠️ **本条是对上一轮记录的两处订正**：
> 1. `20260915-01-内核升级最佳实践.md:18` 把 boot `rev` 称作"前端资产的构建指纹"，**该说法已被 2026-09-18 的实测推翻**；同规范的新一代文档 `R20260918-04-上游0.1.6-alpha差距与升级/00-README.md:52` 与 `02-方案…md:45,147,242` 已明确"**不要把它写进任何基线**"。本文上一版照抄了旧说法，现更正。
> 2. 该 `rev` 每次启动都变，意味着 `documentAssembly.ts:198-217` 的 `cached !== rev` 缓存判据**每次重启内核后都会失配**，理论上导致重下整个 dist 树。**该问题已登记但未实测到实际重下行为**，属独立议题、不在本次调查范围：见 [03-分析 §3 P5](../01-Projects/R20260918-04-上游0.1.6-alpha差距与升级/03-分析_0.1.5-rc.2到0.1.6-alpha.2差距.md)。

**两条硬推论（重要）**：

1. **`dsh --version` 不是能力的权威。** 上游出现过 CLI = rc.7 而传递依赖已解析到 rc.8 的错配（`docs/02-Areas/20260914-06-上游兼容规范_跟随最新官方DSH.md:103` 教训 2）。本机 `dsh` 的依赖写的是 caret 范围——实测 `require('@deepseek-ai/dsh/package.json').dependencies['@deepseek-ai/dsh-web-app']` = **`^0.1.5-rc.2`**——所以**同一个 CLI 版本号下，树里的实际前端版本可以漂移**。
2. 因此扩展里凡是"看版本号决定行为"的地方都做了**现场探测优先、版本号兜底**：`--no-open` 是否支持改为读 `dsh web --help` 的输出（`probeNoOpenSupport`，`src/serverManager.ts:287-311`），探测失败才回落 CLI 版本门（`shouldPassNoOpen`，`src/versionCheck.ts:100-105`）。

### 2.4 "仅仅是 UI" 这个说法要修正成什么

产品定位文档的原话是：**"我们是 DeepSeek Harness（DSH）与 IDE 之间的桥"**、**"我们不写 coding agent，我们让 DSH 成为更好的 coding agent"**（`docs/02-Areas/20260914-09-产品定位与边界.md:11`）。

"不做 Agent"是对的（对话/工具/权限/编排引擎全在 dsh 里）。但"仅仅 UI"会低估风险：桥里有一层**必须随上游产物形态变形**的适配代码。按 `dsh-baseline.json` 的 `fragilePoints` 整理：

| 破坏面 | 扩展里的代码 | 上游一改会怎样 |
|---|---|---|
| boot 注入形态 | `BOOT_RE`（`src/documentAssembly.ts:59`） | 正则失配 → **静默** return 原 HTML → 插件 URL 保持相对 → "Failed to load plugins" |
| dist 资产路径 | `ASSET_REF_RE` / `CSS_URL_RE` / `SHELL_IMPORT_RE`（`:53-55`） | 改写链失效 → 资产 404 / 跨源 CORS → 白屏 |
| 插件 preload | `PLUGIN_PRELOAD_RE`（`:69`） | 未绝对化 → 模块队列收不到注册 → "Failed to load plugins" |
| `/api` 认证与 RPC | `URL_LINE_RE` / `exchangeCookie` / `api()` / `workspaceSnapshot()`（`src/serverManager.ts:72, 628, 721, 754`） | 401 或 404 → 面板白屏 + 宿主 RPC 全挂 |
| CLI flags 与启动行 | `probeNoOpenSupport`（`:298`）、`URL_LINE_RE`（`:72`） | 解析不到 → 启动超时；`--no-open` 判错 → 弹浏览器或旧版启动失败 |
| 前端 DOM 锚点 | `media/bridge-client.js`（composer `[data-composer-input]`、粘贴命令、`@` 引用语法） | 拖拽/写入**静默失效**（最坏的一类） |
| 前端 transport 语义 | `media/bridge-client.js` 的 `window.__DSH_TRANSPORT__ = { fetch, ownsHost: true }` | 面板设置静默不落盘 + "内测声明"每次重载复发（无报错） |

（来源：`docs/02-Areas/dsh-baseline.json:46-112` 的 `fragilePoints`）

### 2.5 所以在全局升级版本号，会发生四类事

| 类型 | 触发条件 | 用户感受 | 实例 |
|---|---|---|---|
| ✅ **白拿** | 上游只做加法（新功能 / 新 UI / 新模型 / 新工具） | 重启面板就有，扩展无需发版 | 上游前端就是面板，rev 变了自动重下 |
| ⚠️ **静默失效** | 上游改了 HTML 形态 / DOM 锚点 / `@` 语法 | **不报错，功能就是没了** | 拖拽写入失效、`@` 引用模型读不到文件（`dsh-baseline.json:99-105`） |
| ❌ **直接坏掉** | 认证面 / RPC 面 / dist 布局变更 | 白屏、401、"Failed to load plugins" | 0.1.1-rc.2、0.1.2-rc.1（见 §2.6） |
| ⛔ **被拒绝** | 低于 `0.1.2-rc.1` | 明确报错并提示升级命令，不半坏 | `src/serverManager.ts:479-485` |

## 3. 怎么自己查这台机器（可直接抄的命令）

```powershell

# ④ $DSH_HOME 运行时树
node -p "require(('$env:USERPROFILE\.dsh\profiles\node_modules\@deepseek-ai\dsh\package.json').replace(/\\/g,'/')).version"

# ⑤ 是否跟上了上游最新
npm run check:dsh
```

**换内核版本（唯一动作）**：

```powershell
npm install -g @deepseek-ai/dsh@0.1.5-rc.2   # 显式版本，别用 @latest 漂移

# 然后重启面板 / 重开 dsh web —— 新进程 = 新树，旧进程不会自动切换
```

## 4. 回填用户的两个问题（结论）

**问题 1 —— 是。**
扩展读取并启动**本机已安装**的 dsh：不打包（`package.json:23-34, 163-165`）、不安装、不下载、不锁定版本。启动时按固定顺序探测本机路径（`src/serverManager.ts:351-380`），优先用户设置 `deepseekHarness.dshPath`，然后 `spawn` 那个二进制跑 `dsh web --port 0`（`:461-462, 498-523`）。扩展侧**没有任何"dsh 版本号"可以配置或固定**，唯一的版本干预是一条**下限硬门** `0.1.2-rc.1`（`:92, 479-485`），没有上限。

**问题 2 —— "能力跟着全局版本走"成立；"仅仅是 UI"不成立，应说成"UI ＋ 一层随上游变形的适配层"。**
- 内嵌界面是**从运行中的 dsh 服务器现抓的官方前端**（`src/documentAssembly.ts:183-217`），宿主 RPC 全是上游协议（`src/serverManager.ts:721-761`）——所以全局一升级，**新能力自动出现在面板里，扩展无需发版**。
- 但代价是：上游改内部产物形态时，扩展这层适配会**静默失效或直接坏掉**（§2.4 七个脆弱面；§2.6 三次破坏史）。这就是为什么项目把"上游跟随"定为生存线（`AGENTS.md §8`），并且发版前必须跑 `check:dsh --strict`。
- 另外注意：**`dsh --version` 不足以判断能力**——CLI 版本与依赖树版本可能错配（§2.3），能力判断一律以现场探测为准。
