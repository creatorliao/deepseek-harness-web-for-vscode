# 缺陷修复记录规范

**规范确立**: 2026-09-14 ｜ **状态**: 生效 ｜ **适用**: 一切缺陷修复（上游 dsh 破坏、本项目代码缺陷、平台差异、渠道事故）

> 修复记录不是流水账，它是**下次遇到同类现象时的第一手证据**。本项目已经发生过**三次用户可见报错完全相同、根因完全不同**的事故——记录不规范，下次必然误判。

---

## 1. 什么时候要写记录

| 情况 | 去向 |
|---|---|
| 复杂缺陷（根因非显而易见、跨模块、与上游版本相关、影响发布） | **必须**写主题夹内的 `NN-修复_*.md` |
| 简单缺陷（一行笔误、文案修正） | 只进 CHANGELOG，不建文件 |
| 上游 dsh 破坏性变更 | 必须写记录，且**必须挂到 [上游 DSH 版本适配主题夹](../01-Projects/R20260820-01-上游DSH版本适配/00-README.md)** |

## 2. 归属主题夹

修复记录**不单独建夹**，写进它所服务的主题夹（按主题归类）：

| 缺陷类型 | 落到哪个主题夹 |
|---|---|
| 上游 dsh 版本破坏（boot / dist / 认证 / CLI flags） | `R20260820-01-上游DSH版本适配` |
| 桥架构、IDE 内嵌、启动器/侧边栏 UI、打包 | `R20260817-01-桥架构与IDE内嵌` |
| 工作区锚点联动 | `R20260819-01-工作区对齐` |
| 会话列表 / 多面板 | `R20260819-02-多会话管理` |
| 发布渠道、Marketplace / Open VSX 事故 | `R20260826-01-发布与分发` |

命名：`NN-修复_<一句话现象>.md`（编号接在该夹文件序列之后）。同一缺陷若有外部模型的根因分析，另起 `NN-分析_<现象>_by-<model>.md`，并在元信息区链接。

## 3. 模板（强制）

```markdown
# 修复 — <一句话缺陷>（<用户可见现象关键词>）

**日期**: YYYY-MM-DD
**扩展版本**: 影响 vX.Y.Z → 修复 vX.Y.Z
**dsh 版本**: 适配 <dsh 版本>（上游破坏性变更必填；与 dsh 无关写 N/A）
**影响面**: <用户可见症状 / 受影响功能>
**范围**: <改动文件清单>
**根因归属**: 上游 dsh 版本变更 | 本项目代码 | 平台差异 | 发布渠道
**关联**: [分析文档](NN-分析_….md)（可选）

## 现象
用户实测看到什么（贴原始报错文案）。

## 根因
代码/上游事实，带 `文件:行号` 或 tarball 实证。
> 多缺陷批次用 `### Bug A / B / C` 分组；单一缺陷多面破坏用 `### A. / B. / C.` 分组。**二选一，不要混用。**

## 修复
改了什么、为什么这样改（不是 diff 复述，是决策理由）。

## 验证
单测 / 真实 dsh 集成 / 用户 F5 实测，逐条给结果。

## 后续建议
- [ ] <必须可机械提取的复选项>
```

## 4. 格式硬约束

| 约束 | 原因（真实踩坑） |
|---|---|
| **必须填 `dsh 版本` 字段** | 历史上完全缺失该字段，导致"上游版本 × 适配事件"时间线只能逐份回读正文才能重建 |
| **必须填 `根因归属` 枚举** | 支撑"是否上游强相关"的统计；历史上 3 次报错相同、根因不同，靠人肉判断 |
| `## 后续建议` 一律用 `- [ ]` 复选 | 历史上 9 份记录只有 1 份可机械提取，其余是自然语句，无法汇总 |
| H2 章节名与顺序固定 | 历史上出现 6 种不同的章节集合，检索困难 |
| 结尾统一为斜体 `*关联文档：…*`（非标题） | 保持可预测的收口形态 |
| 多缺陷分组标记二选一 | 历史上 `### Bug A` 与 `### A.` 两种并存 |

## 5. 与上游相关时的额外要求

若 `根因归属 = 上游 dsh 版本变更`，**同一次修复必须同步四处**（缺一不可）：

1. 本夹的修复记录
2. [dsh-baseline.json](dsh-baseline.json) 的 `verified` / `knownBreakingChanges`
3. `README.md` 与 `README.en.md` 的兼容矩阵
4. `CHANGELOG.md`（用户视角描述）

规范见 [上游兼容规范](20260914-06-上游兼容规范_跟随最新官方DSH.md)。

## 6. 教训沉淀（不要只修 bug）

修复完要问一句：**这条教训该不该变成规范？**

- 是通用工程规则 → 写进 [工程规范](20260914-01-工程规范.md)
- 是 UI/webview/时序规则 → 写进 [扩展与 Webview 规范](20260914-02-扩展与Webview规范.md)
- 是流程规则 → 写进 [特性管线规范](20260914-04-特性管线规范.md) 或本文件

**历史上多条后续建议（按钮显式尺寸、`webview.html` 后不得立即 postMessage）当时没沉淀成规范，因此同类问题具备复发条件。**
