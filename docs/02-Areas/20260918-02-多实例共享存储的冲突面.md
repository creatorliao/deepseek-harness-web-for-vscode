# 多实例共享存储的冲突面

**日期**: 2026-09-18 ｜ **状态**: 当前
**定位**: 回答"多个 dsh 实例（多个 VS Code 窗口 / 桌面端 + 扩展）共用同一个 `$DSH_HOME` 时，历史对话与会话数据会不会互相冲突、会不会被写坏"，逐文件给出冲突面与实测证据。
**核实基线**: dsh `0.1.5-rc.2` ｜ 扩展 `0.5.3` ｜ Windows 11 ｜ 隔离空 `$DSH_HOME` 双实例实测 2026-09-18 16:15–16:40

> 事实来源三类，正文逐条标注：**代码事实** → `<包>/lib/index.js:NN`（写当日行号）；**实测** → 当次命令输出（复现见 §9）；**推断** → 明确写"推断"。
> 上游包路径：`%APPDATA%\npm\node_modules\@deepseek-ai\dsh\node_modules\@deepseek-ai\<包名>`（下文只写包名）。

---

## 0. 一句话结论

**对话内容不会被写坏；会被"写没"的是它的归属登记。**

| 对象 | 两个实例共用同一 `$DSH_HOME` 时会怎样 | 性质 |
|---|---|---|
| **对话内容**（`sessions/<cwd>/<会话>/session.v3.jsonl.zstd`） | 每个会话一个目录一个文件；**写所有权有跨进程锁**，第二个实例直接写不进去（实测报 `SessionAlreadyOwnedError`） | ✅ **安全** |
| **会话的工作区归属登记**（`storages/workspace.json`） | 单文件、内存快照、整文件覆盖、**无跨进程锁** → 后写的实例把先写的实例的登记整条抹掉（**已实测复现**） | ❌ **会互相覆盖** |
| 会话标题等投影缓存（`storages/session_projcache/`） | `per-record` 布局（一会话一文件），且同一会话受上面的写锁保护 | ✅ 安全 |
| 设置 / 凭据 / 附件 / 插件预设 | 走跨进程文件锁（`withFileLock`，2 s 超时） | ⚠️ 有保护，但锁残留会一直失败（见 §4） |

**危害的真实形状**：覆盖丢掉的是"这条会话属于哪个工作区"的记录，**不是对话字节**。但在界面上，"登记丢了"就等价于"历史对话不见了"——而且**不会自愈**（登记收养只在首次启动跑一次，见 [R20260918-02 §2.3](../01-Projects/R20260918-02-跨端会话可见性/03-分析_会话可见性根因.md)）。本机历史取证里"71 个根会话数据完好但界面不可见"与这个机制是**同一类现象**。

## 1. `$DSH_HOME` 里有什么、谁在写

| 路径 | 内容 | 写入方式 | 跨进程保护 |
|---|---|---|---|
| `sessions/<转义 cwd>/<会话 id>/session.v3.jsonl.zstd` | 对话正文（zstd 压缩 JSONL，魔数 `28 b5 2f fd`，实测） | 追加写，单会话单写者 | ✅ 会话级写所有权锁（lease） |
| `storages/workspace.json` | 工作区注册表：每个工作区一条记录（`path` / `title` / `sessionIds` / 时间戳） | **整文件原子替换**（tmp + rename），状态来自**进程启动时的内存快照** | ❌ **无** |
| `storages/session_projcache/`（+ `session_projcache.json`） | 会话标题等投影缓存 | `per-record`：一会话一文档 | 随会话锁（同一会话才可能冲突） |
| `settings.yaml` / `.credentials.yaml` / `profiles/agent-presets` / `attachments` | 设置、凭据、预设、附件 | 走 `dsh-atomic-write` 的 `withFileLock` + `writeFileAtomic` | ⚠️ 有（2 s 超时，锁残留不自愈） |

**谁在用跨进程锁**（全包 grep `withFileLock|writeFileAtomic` 的结果）：`dsh-agent-presets`、`dsh-app-boot`、`dsh-credentials-local`、`dsh-fs-local`、`dsh-llm-deepseek`、`dsh-settings-file`。
**注意**：`dsh-storage-json`（也就是 `workspace.json` 的落盘方）**不在这个名单里**。

## 2. 对话内容：为什么不会被写坏（代码 + 实测）

### 2.1 代码事实：每个会话有跨进程写所有权锁

`dsh-session-persistence-jsonl/lib/index.js`：

- `:611-621` 注释：**"Cross-process write-ownership lock for one session's artifact directory"** —— POSIX 用非阻塞 `flock(2)` 锁 `session.lock`；Windows 用**命名内核信号量**（`Local\dsh-session-lock-<sha256(规范路径)>`，`:545-557`），**不落文件**，持有者进程死亡时内核自动释放。
- `:619` 竞争映射为 `SessionAlreadyOwnedError`；`:617` 明确"读者、搜索、目录删除不受影响"（读是免锁的）。
- `:241-247` `ensureLease()`：**在该会话第一次持久化写入之前**取得写锁，并"在重试期间保持独占"。
- `:663-710` 取锁失败 → 抛 `SessionAlreadyOwnedError`。

### 2.2 实测：第二个实例被明确拒绝

隔离 `$DSH_HOME` 起两个实例 A/B（各自一个窗口的等价物），A 建会话 S 并改名成功，然后 B 对**同一条会话**改名：

```
A rename S : {"ok":true,"value":{"title":"A-title","seq":3}}
B rename S : {"ok":false,"error":{"code":"gateway/internal",
   "message":"resume failed for session \"session-df62d9de-…\":
   SessionAlreadyOwnedError: session \"session-df62d9de-…\" is already owned by an active write handle"}}
A 再 rename: {"ok":true,"value":{"title":"A-title-2","seq":4}}
最终标题（读自 A）: A-title-2
```

→ **B 从头到尾没能写进这条会话**；A 的两次写入都正常落盘。这不是"写坏了再修"，而是**根本写不进去**。

### 2.3 存储形状本身也保证了隔离

实测目录（会话 id 就是目录名，`cwd` 转义成目录名）：

```
$DSH_HOME/sessions/--D-code-deepseek-harness-web-for-vscode--/session-2d95ec9a-…/session.v3.jsonl.zstd
```

不同会话 = 不同目录 = 不同文件 → **不同项目的对话在物理上不可能互相覆盖**。

## 3. 会话登记：这里会互相覆盖（已实测复现）

### 3.1 代码事实：注册表是"内存快照 + 整文件覆盖"

1. **布局是 `single`**：`dsh-workspace/lib/index.js:248-260` 的 `workspaceDomainSpec` 没有声明 `layout`；`dsh-storage-json/lib/index.js:575` 对未声明者走 `openSingleUnit` → 整个域一个文件 `storages/workspace.json`（与实测文件形状 `{unit,global,tables}` 一致）。
2. **内存即权威**：`dsh-storage-json/lib/index.js:160-167` —— *"The in-memory state is authoritative; every write primitive mutates it and republishes the whole file atomically."*
3. **只在启动时读一次**：`dsh-storage-domain/lib/index.js:355-389` 在 `open()` 里 `loadAll()` 建内存表；全包 grep 不到任何 reload / watch / mtime 校验 / 版本比对。
4. **上游明确假设"一个文件只有一个进程写"**：`dsh-storage-json/lib/index.js:6-18` —— *"a unit file has exactly one writer per process and **last-write-wins is correct**"*。**多实例共用一个 `$DSH_HOME` 正好打破这个假设。**
5. 落盘用的是 tmp + rename 的原子替换（`:25-40`），**没有** `withFileLock` → 原子性只保证"不会读到半个文件"，**不保证"不会丢更新"**。

### 3.2 实测：一条普通操作抹掉了另一个实例的整条登记

隔离 home，两个实例同时存活（各自持有启动时的空快照），随后：

```
0 起点              : 0 条 ->
1 A 建 wsA 之后      : 1 条 -> wsA(id=65c753fd, sessions=0)
2 A 建会话 S 之后     : 1 条 -> wsA(id=65c753fd, sessions=1)      ← 会话 S 登记进 wsA
3 B 建 wsB 之后      : 1 条 -> wsB(id=b1a12017, sessions=0)      ← 关键：wsA 连同 S 的登记整条消失
```

**B 只是"在自己的窗口里建了一个工作区"**，A 的工作区记录和它名下那条会话的归属就一起没了。

同时实测（实验二）：

- 两个实例的全局 `session/list` **都仍然返回 S**（`含 S 吗: True`）→ 会话数据与全局索引完好；
- `sessions/<cwd>/<S>/session.v3.jsonl.zstd` **文件仍在**（zstd 正文可读）；
- 但 `workspace.json` 里已没有 wsA → 按工作区过滤的侧边栏列表**不会再显示 S**。

> 这就是"历史对话不见了"的完整链路：**内容在、全局索引在、工作区归属没了**。与 [R20260918-02](../01-Projects/R20260918-02-跨端会话可见性/03-分析_会话可见性根因.md) 记的"数据完好但界面不可见"是同一类结果，但**成因多了一条**：不只是 `{cwd}` 建会话与一次性收养，**多实例并发写注册表也会造成它**。

### 3.3 什么时候会触发（日常动作即触发）

注册表的写入发生在任何一次 `mutate`：`workspace/create`、`session/create`（会 attach 到工作区）、`workspace/archiveSession`、`session` 顺序调整等（`dsh-workspace/lib/index.js:105-152,173-191`）。落到扩展的使用面就是：

| 你的动作 | 是否写注册表 |
|---|---|
| 在窗口里 `＋新建会话` | ✅ 写（可能先 `workspace/create`，再 attach） |
| 首次在某文件夹 ready（`ensureWorkspaceSession` 补建工作区） | ✅ 写 |
| 归档会话 | ✅ 写 |
| 只是续聊已有会话 / 打开面板 / 看列表 | ❌ 不写（但会取会话写锁） |

**受害路径**：窗口 A、B 都开着 → B 新建/归档了一个会话 → 只要 A 之后再发生一次注册表写入（哪怕只是 A 首次补建自己的工作区），B 那条新登记就可能被 A 的旧快照覆盖掉。

**实测旁证（真实 home，只读）**：当前注册表 25 条工作区记录，两个开着的文件夹都在（`…web-for-vscode` 10 条会话、`…黄圣碧课程沟通` 2 条）→ 说明**不是"一开两个窗口就全丢"，而是"谁后写、谁说了算"**：没被覆盖的部分照常存在。

## 4. 其它文件

| 文件 | 冲突面 | 依据 |
|---|---|---|
| `session_projcache` | `layout: "per-record"`（一会话一文档）→ 只有同一会话才可能撞，而同一会话受 §2 的写锁保护 | `dsh-session-projection-cache/lib/index.js:89-99` |
| `settings.yaml` / `.credentials.yaml` / agent-presets | 走 `withFileLock`：`wx` 独占创建 `<file>.lock`，重试到 2 s 超时后**失败**（不是静默丢写） | `dsh-atomic-write/lib/index.js` |
| `.lock` 残留 | 注释明说：**"The contender never removes an existing lock … orphan recovery is an operator action"** —— 持有者被强杀会留下永久 `.lock`，之后每次写该文件都超时失败 | `dsh-atomic-write/lib/index.js`（**未实测**） |

## 5. 危害分级：会丢什么、不会丢什么

| 问题 | 答案 | 依据 |
|---|---|---|
| 对话正文会被另一个实例写乱/写坏吗 | **不会**。第二个写者被 lease 拒绝 | §2 实测 |
| 对话正文会丢字节吗 | **不会**（本次所有实验中，文件始终在、可读） | §3.2 实测 |
| 会丢什么 | **会话的"工作区归属登记"**（`workspace.json` 里的 `sessionIds` 与工作区记录本身） | §3.2 实测 |
| 丢了会怎样 | 会话从侧边栏/工作区列表里消失；数据仍在盘上 | §3.2 实测 |
| 会自愈吗 | **不会**。历史收养（bootstrap）只在 `global.initialized=false` 时跑一次，本机早已 `true` | [R20260918-02 §2.3](../01-Projects/R20260918-02-跨端会话可见性/03-分析_会话可见性根因.md) |
| 会波及别的实例吗 | 会：A 的写入抹掉 B 的登记，反之亦然——**两个实例互删** | §3.2 实测（B 抹掉 A） |

## 6. 能做什么

### 6.1 用户侧（今天就能做）

1. **一个文件夹只开一个窗口**（同时避开资源翻倍与会话写锁冲突）；需要第二块屏幕用"在浏览器打开"复用同一实例（见 [多窗口资源占用与省资源实践](20260918-01-多窗口资源占用与省资源实践.md) §5.5）。
2. **要开多个窗口时，把"新建会话 / 归档会话"集中在一个窗口里做**，其他窗口只续聊已有会话——因为续聊不写注册表（§3.3）。
3. **定期备份 `$DSH_HOME`**（至少 `sessions/` 与 `storages/`）：出问题时能拿回登记，而不用手工重建。
4. **发现历史对话从列表消失时：什么都别删。** 先按 §9.3 确认 `sessions/<cwd>/<会话>/session.v3.jsonl.zstd` 还在——文件在就只是登记问题。

### 6.2 扩展侧可做的（本仓）

- 目前**没有**"补登记 / 自检"入口（[R20260918-02](../01-Projects/R20260918-02-跨端会话可见性/02-方案_跨端会话可见性改善.md) 的方案 B/C 仍在待确认）。在它落地前，本文只能提供"别这么用"的规避。
- 可考虑的**降写**优化（推断，未实施）：`ensureWorkspaceSession()` 在每次 ready 都会跑（`src/extension.ts:121`），虽然稳态不写盘，但"首次补建工作区"这类写是可以避免的；减少写次数=减少覆盖窗口。

### 6.3 只能上游修的（建议反馈）

`workspace.json` 的写路径应当满足两条之一：

1. 用现成的 `withFileLock`（`dsh-atomic-write` 已提供）把 **load → 改 → 落盘** 串成临界区；或
2. 在 `mutate` 前重新 `loadAll()`（把 `single` 布局换成 `per-record`，或给单文件域加"写入前刷新"）。

两条都在上游自己的工具包里，**不需要新造轮子**；现状是 `dsh-storage-json` 没接这套锁，注释里还写着"一个文件只有一个写者"的假设。

## 8. 结论一句话（给决策用）

> **对话不会坏，登记会丢；丢登记=界面看不见，而且不会自己回来。**
> 所以：**多窗口可以开，但别在两个窗口里都做"新建/归档会话"**；要稳，就一个文件夹一个窗口。

## 9. 复现命令

### 9.1 双实例冲突 POC（隔离 home，安全）

```powershell
# 0) 隔离 home：空目录即可，dsh 会自举 profiles
$poc = Join-Path $env:TEMP "dsh-conflict-poc"; Remove-Item $poc -Recurse -Force -ErrorAction SilentlyContinue
$pocHome = Join-Path $poc "home"
New-Item -ItemType Directory -Force $pocHome,(Join-Path $poc "wsA"),(Join-Path $poc "wsB") | Out-Null
$env:DSH_HOME = $pocHome
if ($env:DSH_HOME -notlike "$env:TEMP*") { throw "拒绝在非 TEMP 的 DSH_HOME 上做实验" }   # ← 安全闸，别删

# 1) 起 A、B（各自 cwd 不同），从 stdout 抓 ready 行里的端口与 token
# 2) 各自换 cookie：curl -s -c a.jar -o NUL "http://127.0.0.1:<port>/?token=<token>"
# 3) 调 API（信封与扩展一致，见 src/serverManager.ts:721-746）：
#    POST /api/workspace/create  {"request":{"path":"<wsA 的绝对路径>"}}
#    POST /api/session/create    {"request":{"workspaceId":"<id>"}}
# 4) 每步之后读 $pocHome\storages\workspace.json，看记录是否被对方覆盖
# 5) 结束务必：taskkill /pid <launcher-pid> /T /F
```

> ⚠️ 踩过的坑：**不要**把 `$DSH_HOME` 变量命名为 `$home`（PowerShell 里 `$HOME` 是只读自动变量，赋值会静默失败，实例会以"用户主目录"为 home 启动并在那里自举 `profiles/`）。本次已发生并已清理（只生成了一个可删的 `profiles` 副本，未产生 `storages/`）。

### 9.2 观察写所有权冲突

```
A: POST /api/session/rename {"request":{"sessionId":"<S>","title":"A-title"}}   -> ok
B: POST /api/session/rename {"request":{"sessionId":"<S>","title":"B-title"}}   -> SessionAlreadyOwnedError
```

### 9.3 确认"只是登记丢了、文件还在"

```powershell
Get-ChildItem "$env:USERPROFILE\.dsh\sessions" -Recurse -Filter "session.v3.jsonl.zstd" |
  Where-Object { $_.FullName -like "*<会话 id 片段>*" } | Select-Object FullName,Length,LastWriteTime
```
