# 特性管线规范（Feature Pipeline）

**规范确立**: 2026-09-14 ｜ **状态**: 生效 ｜ **适用**: 一切"需求驱动"的功能开发（对应 `01-Projects/R…-<主题>/`）

> 管线的价值在于**门禁**：每个阶段必须产出物、必须经用户确认才进下一阶段。跳过阶段不是"效率高"，是把返工推到后面。
> 落盘位置与命名见 [文档与 PARA 规范](20260914-03-文档与PARA规范.md)；缺陷类工作走 [缺陷修复记录规范](20260914-05-缺陷修复记录规范.md)。

---

## 1. 阶段与门禁

```
01-讨论 → 02-需求 → 03-方案 → 04-实施计划 →（实现）→ 05-验证 → 计划回填 → 06-总结 + 07-待办
           ⛔门禁      ⛔门禁       ⛔门禁                  自动      自动       自动
```

| 阶段（夹内文件名） | 门禁 | 回答什么 | 禁止内容 |
|---|---|---|---|
| `01-讨论_*.md` | — | 头脑风暴、会议、代码审计的**原始记录** | — |
| `02-需求_*.md` | **用户必须批准** | 做什么：需求清单 + 验收标准 | **不得含实现细节** |
| `03-方案_*.md` | **用户必须批准** | 怎么做：架构、文件变更清单、数据契约 | 写方案时若发现新需求 → **先补进需求**，不得静默扩大范围 |
| `04-实施计划_*.md` | **用户必须批准** | RTTM 追溯矩阵 + 任务清单 | 不得是方案的复述；执行者不应需要回头重读方案 |
| *（实现）* | 自动 | 写代码 | 每完成 2–3 个任务，对照需求做一次轻量自审 |
| `05-验证_*.md` | 自动 | 收口审计 | 必须：① 用 RTTM 复查需求→计划覆盖；② 逐项确认 ✅ 的代码**存在且被调用**（不是死代码）；③ 列出每个缺口与严重度 |
| `04-实施计划` 回填 | 自动 | 按验证结果更新任务状态 | — |
| `06-总结_*.md` | 自动 | 结果记录：做了什么、改了什么 | — |
| `07-待办_*.md` | 自动 | 机械提取计划中的 `❌` + `⏭️` | **禁止手写** |

**`01-讨论` 一旦需求成立即转为只读**：新需求直接写进 `02-需求`，不要回填讨论稿。

## 2. 任务状态

| 标记 | 含义 |
|---|---|
| `✅` | 完成且已验证 |
| `❌` | 未完成——尝试过但被阻塞（**必须带阻塞原因**） |
| `⏭️` | 本轮明确不做（**必须带决策原因**） |
| `⏳` | 尚未开始 |

`❌` 与 `⏭️` 都流入 `07-待办`。`❌` 项通常直接进下一轮；`⏭️` 项需重新评估。

## 3. `04-实施计划` 的格式（强制）

**自包含**——执行者不应需要重读方案。

| 部分 | 规则 |
|---|---|
| 标题 | `# <名称> — 实施计划` |
| 头部 | `**日期**: YYYY-MM-DD` + `**来源**: 讨论 / 需求 / 方案` |
| RTTM | `\| 需求 \| 任务 \| 验证方式 \|`——每条需求都必须有任务承接 |
| 任务 | `### T# — 描述`，含**文件路径 + 行号** + `- [ ]` 子任务 + 代码片段 + `**完成标准**: …` |
| 状态 | 每个任务标 `✅`/`❌`/`⏭️`/`⏳` |
| 顺序 | ASCII 依赖图 |
| 页脚 | `*关联文档：…*` |

**已知反模式**（本项目真实发生过）：任务小节标题标 ✅ 而子项全是 `- [ ]` → 机械提取时被误判为未完成。**要么勾上子项，要么不要用 `- [ ]` 子任务结构。**

## 4. `07-待办` 的意义

- **非空 = 特性未完成**。这是事实信号，不是形式。
- 人（用户）看 `07-待办` 决定：关闭该特性、下轮继续、还是放弃。
- 跨主题的优先级排序**不写在这里**，写到 [待办总表](../01-Projects/R20260914-01-演进总览/03-待办总表.md)。

## 5. 方案文档的结构（强制）

写任何方案前，先按下面四步基于**代码事实**（不是假设）落笔：

1. **Goal** — 目标架构 / 期望行为
2. **Facts** — 读遍相关源码，列出当前实际支持的类型、方法、路径。**绝不假设"代码应该支持 X"，去验证它确实支持**。特别注意**影响面宽度**：当根因是共享组件失效（认证过期、HTTP 超时、凭据为空、会话失效）时，grep **所有**依赖该组件的页面/流程，修复范围必须覆盖完整爆炸半径，而不只是报 bug 的那个页面。
3. **Gap** — Goal 与 Facts 的差集，**这个差集才是要解决的问题**
4. **Call-site Audit（条件必需）** — 当任务会改变共享函数的契约（新增异常、改变返回语义、新增前置条件）时：grep 该函数的全部引用，逐条列文件与行号，逐条判定 **兼容** / **冲突**。**只要有一条冲突，方案必须重新设计**，不得带着已知会破坏调用方的设计进入任务清单。

**规则**：方案里每一句"改为 xxx"都必须由第 2 步核实过的代码事实支撑。**没有事实核查，就没有方案。**
