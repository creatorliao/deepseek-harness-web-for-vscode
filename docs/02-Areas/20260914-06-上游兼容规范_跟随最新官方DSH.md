# 上游兼容规范 —— 始终跟随最新官方 DeepSeek Harness

**规范确立**: 2026-09-14 ｜ **状态**: 生效 ｜ **适用**: 一切与 `@deepseek-ai/dsh` 版本相关的工作

> **本项目的产品定义就是"DSH 的 IDE 合作层"。上游一变，我们就有失效风险。** 上游在约一个月内走完 `0.1.0-rc.6 → 0.1.1-rc.2 → 0.1.2-rc.1 → 0.1.5-rc.2`，其中 **3 次是破坏性变更**，每次都让内嵌面板不可用。本规范把"跟上"从人的记忆变成可执行的检查。

---

## 1. 什么叫"跟上了"

同时满足三条才算跟上：

1. **`latest` 与 `next` 两个渠道**上最新发布的 dsh 版本，都在 [dsh-baseline.json](dsh-baseline.json) 的 `verified` 里；
2. 基线里每个版本都注明**核实深度**（协议探针 / VS Code 实测）；
3. 若期间有破坏性变更，兼容矩阵（`README.md` + `README.en.md`）、`CHANGELOG.md`、修复记录、`dsh-baseline.json` **四处一致**。

一键判定：

```sh
npm run check:dsh          # 人看；离线不阻断
npm run check:dsh -- --strict   # CI 用；有未适配版本则退出码 1
```

## 2. 四个破坏面（每次升级必查，一个都不能跳）

历史上三次事故分别命中不同的面，**报错文案却高度相似（都表现为 "Failed to load plugins"）**。因此**不能靠报错判断**，必须逐面主动核对。

| # | 破坏面 | 历史上怎么坏的 | 怎么核对 |
|---|---|---|---|
| **A** | **boot 注入形态** | `window.__DSH_BOOT__ = {…}` → `globalThis["__DSH_BOOT__"] = {…}`（0.1.1-rc.2）；后又新增 `batches[]`（0.1.2-rc.1） | `GET /` 取 HTML，看 `<script>` 里 boot 的**赋值前缀**与 JSON 结构（是否有 `batches`）。正则失配会静默 return 原 HTML，插件 URL 保持相对 → 插件全挂 |
| **B** | **dist 资产路径** | 绝对 `/plugins/…` → 相对 `./assets/…` + `<base href="/">`；preload 变 `/plugins/??pkg/client.js,…&rev=` mux 形态（0.1.2-rc.1） | 拉 `index.html` 看资源引用形态；确认 `documentAssembly` 的改写链能覆盖；确认资产经**同源** webview 资源加载（不得裸跨源） |
| **C** | **`/api` 认证与 RPC** | 启动行加 `/?token=<launchToken>`，`/` 与全部 `/api`（含 WS 升级）要求 authority 绑定签名 Cookie（缺失即 **401**）；RPC 改 Typert `POST /api/<namespace>/<method>` + `{args:{…}}`，旧的 `/api/workspace.list` **404**（0.1.2-rc.1） | 起服务后：① 无 Cookie 请求是否 401；② 用启动令牌换 Cookie 是否成功；③ 一个已知 RPC 方法是否可用；④ WebSocket 升级是否也需要 Cookie |
| **D** | **CLI flags 与输出格式** | `dsh web` 默认打开外部浏览器（rc.8 起，`--no-open` 关闭）；启动行加了 token 段 | `dsh web --help` 看可选 flag；起一次看 stdout 的实际格式。**注意：不要用 CLI 版本号推断能力**——历史出现过 CLI=rc.7 而传递依赖已解析到 rc.8 的错配，因此 `--no-open` 已改为**现场探测 `--help` 优先、版本判断兜底** |

**次要面（顺手核对）**：`session/list` 的字段位置（`agentPreset` 曾挪进 `projections.values`）、会话 RPC 的方法名形态（`.` 与 `/` 混用过）、`$DSH_HOME` 默认目录行为。

## 3. 什么时候查

| 触发 | 动作 |
|---|---|
| **每次开工前** | `npm run check:dsh`（10 秒，纳秒级成本换掉一次白屏事故） |
| **每次发版前** | `npm run check:dsh -- --strict`；未适配**不得发版** |
| 每周一（自动） | CI `upstream-watch` 定时跑 `--strict`，未适配即失败 → 把"该做适配了"摆到台面上 |
| 用户报"升级 dsh 后面板坏了" | 直接进第 4 步流程 |

## 4. 操作流程（发现上游有新版本时）

> ⚠️ **先看这一条**：升级动作 = **换掉正在跑的那棵树**。**不要在活跃会话上热升级**——2026-09-15 实测：安装成功，但该会话的子进程工具链立刻失效（见 [事件记录](../01-Projects/R20260820-01-上游DSH版本适配/11-事件_热升级内核导致会话工具链失效.md)）。
> **安全顺序与具体命令（停会话 → 显式版本安装 → 重启内核 → 四破坏面核对 → 回滚预案）**：见 [内核升级最佳实践](20260915-01-内核升级最佳实践.md)。下面这条流程是它的上位版本。

```
1. 查明差异
   npm run check:dsh                     # 看是哪个渠道、哪个版本未覆盖
   npm view @deepseek-ai/dsh dist-tags   # 原始 dist-tags
   本地装来实测：npm i -g @deepseek-ai/dsh@<version>

2. 逐面核对四个破坏面（§2 表格，A→D 一个都不能跳）
   拿真实 HTML / 真实 API 响应说话，不看报错猜

3. 判定
   ├─ 四面全过 → 只需"登记"：把该版本加进 baseline 的 verified，注明核实深度
   └─ 有面破了 → 走修复：
        · 在 docs/01-Projects/R20260820-01-上游DSH版本适配/ 新增
          NN-修复_<dsh版本>-<现象>.md（用 20260914-05 的模板）
        · 代码修复 + 回归测试（务必补一条锁定该形态的单测）

4. 四处同步（缺一不可）
   · dsh-baseline.json 的 verified[] / knownBreakingChanges[] / audit
   · README.md 与 README.en.md 的「版本兼容」矩阵
   · CHANGELOG.md（用户视角：升级 dsh 后会发生什么、现在修好了）
   · 本主题夹 00-README.md 的文件清单

5. 验证（见 §5）

6. 收口
   · 更新 01-Projects/R20260914-01-演进总览/01-演进时间线.md
   · 若基线里的旧版本已无意义（如被硬版本下限挡掉的），在 baseline 里注明而非直接删
```

## 5. 验证要求

| 层级 | 命令 / 动作 | 通过标准 |
|---|---|---|
| 静态 | `npm run compile` | 零 issue |
| 单测 | `npm test` | 全绿（当前 93/93）；**必须为本次破坏形态补回归测试** |
| 真实 dsh 冒烟 | `node scripts/smoke.js` | 起服务 + Cookie 认证 + `session/create` + `session/list` 的 cwd 对齐全部通过 |
| 真机 | F5 起 Extension Development Host | 面板渲染、插件加载、对话可用、剪贴板可用、主题跟随 |
| 打包 | `npm run package` | `dist/` 下生成**唯一**一份 vsix |

**真机实测不可省**：历史记录里多次出现"单测全绿但真机面板白屏"（单测用的是 fake dsh，形态覆盖不到真实 HTML）。

## 6. 硬版本下限

`src/serverManager.ts` 的 `MIN_DSH_VERSION` 是**硬门**：低于它的 dsh 直接以清晰错误拒绝启动，而不是进入半坏状态。

当前：`0.1.2-rc.1`。修改它必须同步 `dsh-baseline.json`、兼容矩阵、CHANGELOG。

**为什么要有它**：0.1.2-rc.1 之前与之后的 API 面完全不同，与其让用户看到白屏，不如直接告诉他去升级。

## 7. 三条事故教训（贴在墙上）

1. **不要用报错文案判断根因。** 三次事故 ("Failed to load plugins") 根因分别是：preload 标签未绝对化（rc.8）、boot 正则失配（0.1.1-rc.2）、dist 布局 + 认证全换（0.1.2-rc.1）。
2. **不要用 CLI 版本号当权威。** CLI 版本与传递依赖版本可能错配；能力判断一律以**现场探测**为准。
3. **正则匹配上游 HTML 是脆弱设计。** `__DSH_BOOT__` 的赋值前缀已经变过一次、注入结构又变过一次。任何"匹配上游产物形态"的代码都必须：① 匹配失败时**大声失败**（不要静默 return 原样）；② 有锁定当前形态的回归测试；③ 在本文档登记为"需要随上游核对的脆弱点"。

## 8. 当前基线与兼容矩阵

| dsh4vscode 版本 | 兼容 dsh |
|---|---|
| `0.3.4`（当前） | `0.1.2-rc.1`、`0.1.5-rc.1`、`0.1.5-rc.2` |
| `0.3.3` | `0.1.1-rc.7` 及更早 |

- 硬版本下限：`0.1.2-rc.1`（更早的版本被拒绝启动）。
- 上游 `alpha` 通道（`0.1.5-alpha.2`）**不纳入基线**——它是实验通道，不作为适配目标。
- 机器可读源：[dsh-baseline.json](dsh-baseline.json)。**本表与它必须一致。**
