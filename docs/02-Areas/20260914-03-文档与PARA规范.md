# 文档与 PARA 规范

**规范确立**: 2026-09-14 ｜ **状态**: 生效 ｜ **适用**: `docs/` 下的一切文档、仓库根 `AGENTS.md` / `README*` / `CHANGELOG*`

> 导航入口是 [docs/README.md](../README.md)；本文件是它引用的**写作与落盘细则**。

---

## 1. 语言

| 对象 | 语言 |
|---|---|
| 仓库文档（`docs/**`、`AGENTS.md`、`CLAUDE.md`） | **中文** |
| 代码标识符、代码注释、commit message | **英文** |
| 面向用户的扩展文案（`package.nls.json`、`src/i18nStrings.ts`） | **仅简体中文**（`package.nls.json` 内容即中文，无 locale 变体；见 [扩展与 Webview 规范](20260914-02-扩展与Webview规范.md) §4） |
| `README.md`（对外主档）、`CHANGELOG.md` | **中文**；英文版保留为 `README.en.md` / `CHANGELOG.en.md` |

## 2. 事实优先（最重要的一条）

现状、差距、协议、行为类内容**必须**基于代码与实测事实，并标注来源：

- 代码事实 → `src/xxx.ts:NN`（写当日的行号；行号会漂移，见 §5）
- 协议/上游行为 → 注明**在哪个 dsh 版本上核实过**（上游一个月内变过数次，无版本号的事实等于没有事实）
- 外部数据 → 注明采集日期与来源
- 命令输出 → 贴关键行

**禁止**："应该是"、"通常是这样"、"我记得"、"按惯例"。没读过的代码不写结论，没测过的行为不写事实。

## 3. 四维分流与命名

细则见 [docs/README.md](../README.md) §3，此处只强调三点：

1. **按维落盘，不要混用**：需求/方案/计划/一次性修复记录 → `01-Projects/<主题夹>/`；长期规范 → `02-Areas/`；外部资料 → `03-Resources/`；失效内容 → `04-Archives/`。**另外三维不建主题子文件夹。**
2. **日期取事件起始日**，不是建文件的当天：Projects 主题夹取该主题起始日，Resources/Archives 取内容来源日期，Areas 取规范确立日（迁移既有文档时用迁移日，原始日期写进文件头）。
3. **主题夹必有 `00-README.md`**：说明本夹是什么、每个文件记什么、当前状态与仍未闭环项。

## 4. 交叉引用代替重复

同一事实只在**归属文档**维护一份，其余用相对链接引用。

- 发现两处都在维护同一份事实 → 留一处，另一处改成链接。
- 链接用相对路径（便于本地与 GitHub 双端可点）。
- **改文件名或移动文件后，必须全仓 grep 旧路径并全部更新**——包括代码注释里的路径引用。

## 5. 历史记录不可改写

`01-Projects/` 下的管线文档与修复记录是**当时的事实**：

- **不要**为了让它们"跟现状一致"而改结论、改数字、改行号。行号会漂移是正常现象。
- 明确的错误/冲突**登记**在 [../01-Projects/R20260914-01-演进总览/04-文档勘误台账.md](../01-Projects/R20260914-01-演进总览/04-文档勘误台账.md)，按需增量修正。
- **当前状态的真源只有一个**：`01-Projects/R20260914-01-演进总览/`。

## 6. 每份文档的头部

```markdown
# 标题

**日期**: YYYY-MM-DD ｜ **状态**: 待评审 / 已批准 / 当前 / 生效 / 已收口 / 归档
**定位**: 一句话说明这份文档回答什么问题
```

`**状态**` 不是装饰：它是判断"这份文档还能不能信"的第一信号。发布类、手册类文档**必须**带日期——历史上 `doc/publish/*` 四份文档全部缺日期头，导致渠道级剧变（Marketplace 被移除）没能触发它们更新。

## 7. 命名与类型词表

| 位置 | 格式 |
|---|---|
| Projects 主题夹 | `R{YYYYMMDD}-{两位序号}-{主题名}` |
| 主题夹内文件 | `{两位序号}-{类型}_{标题}.md`（`00-README.md` 固定为索引） |
| 其余三维文件 | `{YYYYMMDD}-{两位序号}-{主题}.md` |

**类型词表（固定，勿自创）**：`讨论`、`需求`、`方案`、`实施计划`、`验证`、`总结`、`待办`、`事实`、`修复`、`分析`、`评审`、`事件`、`架构提案`、`教程`。

> `教程` 用于**面向人的知识文档**（解释"它怎么工作""怎么改"），读者是项目所有者/维护者，允许比规范更长、更图文并茂；与 `事实`（原始实测记录）区别在于：教程的结论会随代码演进而更新，`事实` 是当时的原始证据。

## 8. 维护时机

| 触发 | 必须更新 |
|---|---|
| 上游 dsh 发新版并完成适配 | `dsh-baseline.json` + 兼容矩阵（README 中英）+ `CHANGELOG.md` + 演进时间线 |
| 每个版本发布 | `CHANGELOG.md`（中英）+ 路线图 + 主题夹内相关状态 |
| 新增/关闭待办 | [待办总表](../01-Projects/R20260914-01-演进总览/03-待办总表.md) |
| 文档增删改 | [docs/README.md](../README.md) 导航 + 主题夹 `00-README.md` |
| 发现失效引用/口径冲突 | [文档勘误台账](../01-Projects/R20260914-01-演进总览/04-文档勘误台账.md) |

## 9. 提交前自检

- [ ] 所有新增相对链接目标真实存在
- [ ] 移动/改名过的文件，旧路径在全仓（含代码注释）已无残留
- [ ] 头部有 `**日期**` 与 `**状态**`
- [ ] 事实都带来源（`文件:行号` 或"<版本> 实测"）
- [ ] 没有与既有文档重复维护同一事实
