# 内核升级最佳实践 —— 安全地把官方 dsh 换到新版本（SOP + 流程图）

**日期**: 2026-09-15 ｜ **状态**: 生效 ｜ **适用**: 任何"把上游 `@deepseek-ai/dsh` 换成新版本"的动作（本机、CI、用户机器）
**上位规范**: [20260914-06-上游兼容规范_跟随最新官方DSH.md](20260914-06-上游兼容规范_跟随最新官方DSH.md)（管"**要不要跟**"与四个破坏面）｜ 本文管"**怎么安全地跟**"

> **一句话结论**：升级内核不是改一行配置，而是**换掉正在跑的那棵树**。
> 顺序永远是：**先停活着的会话 → 再装 → 再重启 → 再逐面核对 → 再登记**。
> 在活跃会话上热升级，会让那个进程的子进程工具链立刻失效（2026-09-15 已实测，见 §5）。

---

## 1. 先对齐三个"版本位"（混了就误判）

| 版本位 | 是什么 | 本机实测（2026-09-15） | 怎么读 |
|---|---|---|---|
| **CLI 包版本** | `@deepseek-ai/dsh` 这个 npm 全局包自身 | 升前 `0.1.5-rc.1` → 升后 **`0.1.5-rc.2`** | `dsh --version`；或读 `%AppData%\npm\node_modules\@deepseek-ai\dsh\package.json` |
| **依赖树版本** | `dsh-client-*` / `dsh-web-frontend` 等被 caret 范围解析出的实际版本 | 升前 CLI 是 rc.1，但其 deps 写的是 `^0.1.5-rc.2`，所以树里**早就是 rc.2** | `node -p "require('<...>/@deepseek-ai/dsh-web-frontend/package.json').version"` |
| **dist boot manifest `rev`** | 前端资产的构建指纹，扩展靠它决定要不要重下本地缓存 | 每次升级通常会变 | `GET /` 的 HTML 里 `"rev":"…"`；`src/documentAssembly.ts` 的 `extractRev` |

**两条硬规矩**：

1. **"最新"只以 npm `dist-tags` 为准**（`latest` / `next`；`alpha` 不纳入基线）。
2. **不要用 CLI 版本号推断能力**——上游出现过 CLI=rc.7 而传递依赖已是 rc.8 的错配（[上游兼容规范](20260914-06-上游兼容规范_跟随最新官方DSH.md) §7 教训 2）。

## 3. 升级前检查表（5 分钟）

- [ ] `npm run check:dsh` —— 看是哪个渠道、哪个版本未覆盖（`--strict` 会给退出码 1）
- [ ] **确认这棵树上没有活着的会话**：关掉 IDE 里的 DSH 面板 / 终端里的 `dsh web` / DSH Desktop；确认没有 `node` 进程还在跑 `dsh`
- [ ] 记下**回滚锚点**：`dsh --version`、`npm ls -g --depth=0`、当前 [dsh-baseline.json](dsh-baseline.json) 的 `verified`
- [ ] 看一眼 [dsh-baseline.json](dsh-baseline.json) 里这条版本的 `fragilePoints`，升级后要**优先复核**它们
- [ ] 若升级是为了"跟到最新"，明确**这次的目标版本号**（写下来，别用浮动 tag）

## 4. 升级与重启（关键动作）

```powershell
# 1) 目标版本（示例：next 通道的最新）
npm install -g @deepseek-ai/dsh@0.1.5-rc.2

# 2) 确认装上
dsh --version

# 3) 重启内核：重新打开 DSH 会话 / IDE 面板，或重开终端里的 dsh web
#    新进程 = 新树；旧进程不会自动切换
```

**两个必须知道的副作用**：

| 副作用 | 现象 | 规避 |
|---|---|---|
| Windows 文件锁 | npm cleanup 报 `EPERM unlink … libvips-42.dll`（原生 addon/DLL 被运行中的进程占用） | **升级前停掉所有 dsh 进程**；残留的 `@deepseek-ai\.dsh-XXXX` staging 目录可在停进程后手动删 |
| **半装树（比上一条严重）** | `npm i -g` 以 `EBUSY: resource busy or locked, copyfile … koffi.node` **失败退出**（`exit -4082`），但**新的 `package.json` 已经写进磁盘** → 树变成"JS 包装是新版、原生二进制还是旧版"。此后**每次 `dsh web` 启动即退码 1**（`Mismatched native Koffi modules`），而 `dsh --version` / `dsh web --help` 一切正常 | 升级前停进程；**升级后必须看退出码**，并用 §4.1 的一致性自检确认原生二进制真的换了（2026-09-15 实发，见 [12-修复](../01-Projects/R20260820-01-上游DSH版本适配/12-修复_全局dsh半装koffi错配导致启动即退码1.md)） |
| **热升级打断运行中的会话** | 磁盘树被替换、进程仍在跑旧代码 → 子进程工具链立刻失效（§5） | 升级前后**必须重启内核**；升级期间别指望那个会话还能干活 |

### 4.1 升级后自检：原生二进制与 JS 包装必须同版本

npm 的"成功"只保证它自己写完了，不保证**每个文件**都换成了新版本——被锁住的原生模块会被跳过。装完跑一次：

```powershell
# 取全局 dsh 的树根（默认 %AppData%\npm\node_modules\@deepseek-ai\dsh）
$dsh = "$env:APPDATA\npm\node_modules\@deepseek-ai\dsh"

# koffi：JS 包装版本 vs 原生二进制自报版本，二者必须相等
node -e "const p=process.argv[1];const {createRequire}=require('node:module');const r=createRequire(p+'/node_modules/koffi/src/koffi/src/static.js');console.log('koffi pkg :',require(p+'/node_modules/koffi/package.json').version);console.log('koffi native:',r('@koromix/koffi-win32-x64').version)" $dsh

# 最终判据：起一次真服务，看有没有打印启动行（--help / --version 不算数）
dsh web --port 0 --no-open
```

期望：两行版本号相同，且最后一条打印 `dsh web: http://127.0.0.1:<port>[/?token=…]`。

## 5. 实战事故（2026-09-15，一手记录，务必读）

**做了什么**：在一个**正在运行的 DSH 会话里**执行 `npm install -g @deepseek-ai/dsh@0.1.5-rc.2`（0.1.5-rc.1 → rc.2）。

**装的结果**：`added 64 packages, and changed 520 packages in 54s` —— 成功。同时出现 cleanup 警告：

```
npm warn cleanup EPERM unlink
  …\@deepseek-ai\.dsh-YBMFo6rE\node_modules\@img\sharp-win32-x64\lib\libvips-42.dll
```

**随后，那个正在运行的会话里，一切需要"起子进程"的工具全部失效**，且报错有三种、彼此不同：

| 现象（原文） | 出现在什么操作上 |
|---|---|
| `Error [ERR_MODULE_NOT_FOUND]: Cannot find package 'tsx' imported from D:\code\deepseek-harness-web-for-vscode\` | 任何以 Node 启动、带 `--import tsx` 风格加载器的子进程 |
| `subprocess-local: Windows Job runner exited with exit code 1 before proving its managed range empty` | 宿主起 shell / 子进程管理 |
| `ripgrep provider failure` | 文件搜索类工具（grep / glob） |

**根因（分两层，第二层是假设，已标注）**：

1. **确定**：升级把**正在运行的那棵树的文件换掉了**。运行中的进程内存里是旧代码，落盘的是新树；Windows 又因 DLL 占用拒绝清理，于是"新旧混用"。
2. **假设（未完全确证）**：运行中的进程按旧树的期望去加载/解析某个包（实测报错指向包 `tsx`），而新树里没有它、全局也没有（已核实：`%AppData%\npm\node_modules\tsx` 不存在、工作区与 `dsh/lib` 都无 `tsx` 引用）。当时用于取证的 grep / npm 日志通道随后也一起失效，因此**这条只能记为"已观察 + 待复核"**，不要当结论传播。

**恢复办法（用户侧执行，按顺序）**：

```powershell
# 1) 重启内核：关掉 DSH / IDE 面板 / 终端里的 dsh web，然后重新打开
#    —— 新进程加载新树，绝大多数情况下这一步就好了
# 2) 若重启后仍报 Cannot find package 'tsx'
npm i -g tsx
# 3) 若新内核本身起不来，回退到已适配的版本
npm i -g @deepseek-ai/dsh@0.1.5-rc.1
```

**这条事故的教训（要变成规则）**：

> **不要在活跃会话上热升级内核。** 升级前停会话，升级后重启；升级动作与"继续用那个会话"互斥。

## 6. 升级后：四个破坏面怎么现场核对

表格与判定口径见 [上游兼容规范](20260914-06-上游兼容规范_跟随最新官方DSH.md) §2（A boot 注入形态 / B dist 资产路径 / C `/api` 认证与 RPC / D CLI flags 与输出格式）。本文只补"**用什么命令拿证据**"：

| 面 | 现场取证 |
|---|---|
| A | 起服务后 `GET /`，看 boot 赋值的**前缀形态**（`window.__DSH_BOOT__` vs `globalThis["__DSH_BOOT__"]`）与 JSON 里是否有 `batches[]` |
| B | 同一份 HTML 里看资产引用是 `/assets/…` 还是 `./assets/…` + `<base href="/">`；看有没有 `<script src="/plugins/…">` 阻塞式 preload |
| C | ① 不带 Cookie 请求 `/api/...` → 应 401；② 用启动行里的 `?token=` 换 Cookie → 应成功；③ 一个已知 RPC 方法可调；④ WS 升级是否也要 Cookie |
| D | `dsh web --help`（**现场探测优先、版本号兜底**）；起一次看 stdout 启动行格式（端口 + token 段） |

**不要用报错文案判断根因**：历史上三次事故的报错都是 "Failed to load plugins"，根因分别是 preload 未绝对化、boot 正则失配、dist+认证全换。

## 7. 回滚

| 什么时候回滚 | 怎么回滚 |
|---|---|
| 新内核起不来、或四个破坏面里有面破了且**当天修不完** | `npm i -g @deepseek-ai/dsh@<上一个已适配版本>`，然后重启内核 |
| 只是想让"最新"信号停下 | 不动安装，只在 [dsh-baseline.json](dsh-baseline.json) 里如实登记未适配（`check:dsh --strict` 会红） |

**回滚锚点从哪来**：升级前的 `dsh --version` 输出 + baseline 的 `verified[]`。**升级前一定要抄下来**。

## 10. 常见故障对照表

| 现象 | 先查什么 | 常见根因 |
|---|---|---|
| 面板白屏 / "Failed to load plugins" | 四破坏面 A、B | preload 未绝对化、boot 形态变了、dist 布局变了 |
| 面板起来但请求全 401 | 破坏面 C | 启动行 token 段变了 / Cookie 的 authority 绑定变了 |
| 启动超时、解析不到端口 | 破坏面 D + `src/serverManager.ts` 的 `URL_LINE_RE` | 启动行格式变了、`--no-open` 探测失效 |
| 内嵌面板里设置不生效、弹窗反复 | [修复记录 14](../01-Projects/R20260817-01-桥架构与IDE内嵌/14-修复_面板内图片不显示与内测声明反复出现.md) | 页面 origin 非回环 → settings memory 模式（已用 `__DSH_TRANSPORT__.ownsHost` 修） |
| 升级后**本机工具链**坏了（起不了子进程） | §5 | **热升级正在运行的树**——重启内核 |
| 面板报 `dsh exited before ready (code=1, signal=null)`、终端里 `dsh web` 也起不来 | §4.1 的自检 | **全局树被半装**：原生二进制与 JS 包装版本错配（`Mismatched native Koffi modules`）。**注意 `dsh --version` 是好的**，别用它排除故障 |
| `npm i -g` 报 EPERM / EBUSY | §4 | 运行中的进程锁住原生 DLL；或沙箱不允许写工作区外的 npm 缓存/全局目录 |
